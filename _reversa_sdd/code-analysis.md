# Code Analysis — cad-modelling-service

> Generated by the Reversa Archaeologist (`doc_level = completo`).
> Confidence markers: 🟢 CONFIRMED (read from code) · 🟡 INFERRED (pattern-based)
> · 🔴 GAP (not determinable — also listed in `questions.md`).
> Every claim carries a `file:line` reference where practical.

**da3Dalus / cad-modelling-service** is a layered FastAPI backend for parametric
aircraft design. The request flow is
`endpoint → service → model / schema / converter`, with a separate CAD engine
(`cad_designer/`, CadQuery) and an aerodynamic stack (AeroSandbox + NeuralFoil +
a vendored AVL binary). Persistence is SQLAlchemy 2.x over SQLite (WAL) or
PostgreSQL, migrated with Alembic.

Two invariants dominate the whole codebase and are repeated in every module
section below because violating them is the single most common source of bugs:

1. **Unit duality.** The DB and AeroSandbox speak **metres**; `WingConfig` and
   the `cad_designer` topology speak **millimetres**; `wing_xsec_spares`
   dimensional columns are an explicit **mm exception inside the metre DB**
   (gh-402). Conversion happens only in `app/converters/` and in the
   `_convert_spare_to_*` helpers of `wing_service`.
2. **Transaction ownership.** `get_db()` (`app/db/session.py:55-64`) commits on
   success and rolls back on exception. Services call `db.flush()` / `db.add()`
   but never `db.commit()` / `db.begin()`. 🟢 CONFIRMED

Cluster-A modules covered here: `aeroplane-core`, `wing-design`,
`fuselage-design`, `airfoil-catalog`.

### Non-trivial rules

**R1 — Every new aeroplane is born as a complete versioning node.**
`create_aeroplane` performs a three-step flush dance to satisfy the circular
`aeroplanes ↔ branches` FK pair: insert aeroplane → `flush()` for the id → set
`root_id = self.id` → create `BranchModel(root_id=id, head_id=id, name="main",
is_main=True, created_by="human")` → `flush()` → back-fill
`aeroplane.branch_id`. 🟢 CONFIRMED (`app/services/aeroplane_service.py:75-100`)
The circularity is resolved at DDL level by `use_alter=True` on both FKs
(`app/models/aeroplanemodel.py:629-638, 691-706`), and a **partial unique index**
`uq_branches_one_main_per_root` guarantees exactly one main branch per lineage
(`app/models/aeroplanemodel.py:616-624`).

**R2 — Eager materialisation before serialisation.** `get_aeroplane_schema`
walks `wing.x_secs → detail → spares / trailing_edge_device.servo_data` purely
to force the lazy loads *inside* the session, because FastAPI serialises the
response after the `get_db()` generator has closed
(`app/services/aeroplane_service.py:141-149`). 🟢 CONFIRMED — this is a
deliberate workaround, not dead code.

**R3 — `AirplaneConfiguration` export requires a mass.** Missing
`total_mass_kg` raises `ValidationError` → HTTP 422 before any conversion is
attempted (`app/services/aeroplane_service.py:263-267`).

**R4 — NumPy leakage guard.** `_to_json_compatible` (l.33-44) recursively
converts `np.ndarray` → `list` and `np.generic` → Python scalars so the CAD
payload is JSON-serialisable. 🟢 CONFIRMED

**R5 — Delete is cascade + side-effect.** The ORM cascade removes wings,
fuselages, weight items, assumptions, copilot messages, scenarios and stability
results; afterwards `openvsp_step_export_service.cleanup_aeroplane_step_files()`
is called in a bare `try/except` that only logs
(`app/services/aeroplane_service.py:191-198`) — orphaned STEP files are
tolerated rather than blocking the delete. 🟢 CONFIRMED

### Component tree — algorithms 🟢 CONFIRMED

Three node types, discriminated by the free-text `node_type` column:
`"group"` (structural), `"cad_shape"` (Creator-pipeline or uploaded part),
`"cots"` (catalogue component). 🟢 CONFIRMED
(`app/models/component_tree.py:12-16`)

**A1 — Tree assembly** (`_build_tree`, `component_tree_service.py:58-79`):
single pass into an `id → node` map, second pass attaching children to
`parent_id`; anything whose parent is missing from the map becomes a **root**
(orphan-tolerant). Children and roots are sorted by `sort_index`. No depth limit
and no cycle detection at read time. 🟡 INFERRED risk: a cycle introduced
out-of-band would make `_build_tree` silently drop the nodes from `roots` (they
would attach to each other), and `_roll_up_weights` would recurse infinitely.
Writes are protected — see A3.

**A2 — Weight roll-up** (`_roll_up_weights`, l.82-120) — post-order traversal:

```
total_weight_g(node) = (own_weight_g or 0) + Σ total_weight_g(children)

weight_status:
  leaf      → "valid" if own source ≠ "none" else "invalid"
  non-leaf  → all children valid            → "valid"
              all children invalid          → "partial" if own present else "invalid"
              mixed                         → "partial"
```

Own weight resolution is a strict precedence chain
(`_calculate_own_weight`, l.461-474):

1. `weight_override_g` → source `"override"`
2. COTS: `component.mass_g × quantity` → source `"cots"` (l.432-439)
3. CAD shape via material density → source `"calculated"` (l.442-458):
   * surface print: `area_mm2 × print_resolution_mm × density_kg_m3 / 1e6 × scale_factor`
     (`print_resolution_mm` defaults to **0.4**)
   * volume print: `volume_mm3 × density_kg_m3 / 1e6 × scale_factor`
4. otherwise `(None, "none")`

`get_tree` pre-computes all own weights in one dict before recursing so the
traversal does not issue N queries (l.133-137). 🟢 CONFIRMED

**A3 — Move-node cycle guard.** `move_node` rejects a move whose new parent is
a descendant of the moved node, via an ancestor walk `_is_descendant`
(l.324-325, l.339-359). This is the **only** structural integrity check; the
walk itself is unbounded and would not terminate on a pre-existing cycle.
🟡 INFERRED

**A4 — Aircraft total weight** (`get_aircraft_total_weight_kg`, l.381-403):
sums own + recursive children weight over all `parent_id IS NULL` roots, in
grams, then `/1000`. Returns `None` for an empty tree so the caller can *clear*
the mass `calculated_value` rather than write a zero. 🟢 CONFIRMED

**A5 — Mass sync is fire-and-forget.** `_sync_aircraft_mass` (l.362-378)
lazy-imports `mass_cg_service.sync_component_tree_to_mass` and swallows every
exception — a failed mass sync must never block the tree CRUD operation.
🟢 CONFIRMED (deliberate, documented in the docstring)

**A6 — Construction-part snapshot.** When a node is created with
`construction_part_id`, `volume_mm3` / `area_mm2` / `material_id` are copied
from the referenced part, but **only for fields the caller did not explicitly
set** — explicit values always win, detected via
`data.model_dump(exclude_unset=True)`
(`_snapshot_construction_part_fields`, l.162-187). 🟢 CONFIRMED

**A7 — Auto-sync groups.** Creating a wing or fuselage creates a matching
component-tree group; deleting removes nodes by the `synced_from` prefix
(`wing:<name>` / `fuselage:<name>`), see `wing_service.create_wing:298-300`,
`fuselage_service.delete_fuselage:179-181`. 🟢 CONFIRMED (gh#108)

### The station/segment model — the module's central rule 🟢 CONFIRMED

A wing is a list of **stations** (`wing_xsecs`, ordered by `sort_index`).
N stations describe N−1 **segments**. All segment-scoped data (spars, TED,
turbulator, `x_sec_type`, `tip_type`, `number_interpolation_points`) hangs off
the **inboard** station of its segment, in the 1:1 `wing_xsec_details` side
table. The **terminal station carries geometry only** and this is enforced in
three places:

* schema: `AsbWingSchema.validate_last_xsec_has_no_segment_details`
  (`aeroplaneschema.py:666-680`) raises on any segment field present on the last
  x-section;
* model: `WingModel.from_dict` blanks all six segment fields when
  `index == len(xsec_dicts) - 1` (`aeroplanemodel.py:489-490`);
* service: `_assert_non_terminal_xsec_or_raise` (`wing_service.py:151-156`)
  raises `ValidationError` for writes targeting the terminal index.

Related converter subtlety: ASB emits N+1 x-secs for N segments, and
`x_sec[i]`'s control surface belongs to segment *i−1*. `_build_segment_details`
therefore **overwrites** the x-sec-derived control surface with the segment's own
TED-derived one, otherwise `_merge_ted_with_control_surface` would resurrect a
phantom TED on round-trip (`model_schema_converters.py:960-995`). 🟢 CONFIRMED

**Spar geometry preservation (gh-1053).** `_resolve_spare_vectors_and_origins`
normally *clears and recomputes* every spar's origin/vector on model→config
conversion — this is the gh-352/gh-362 unit-leak guard. That would collapse a
solver-produced front/rear spar couple onto the default quarter-chord station,
so `should_preserve_normal_spare` exempts spars that are `spare_mode == "normal"`
**and** carry a fully explicit 3-component `spare_origin` **and** `spare_vector`
(`spare_origin_preservation.py:43-59`). Everything else
(`standard` / `follow` / `*_backward`) still goes through the recompute path.
🟢 CONFIRMED

**Recompute round-trip.** `_recompute_spare_vectors` (`wing_service.py:854-873`)
rebuilds a `WingConfiguration` at `scale=1.0` (metres), reads back each segment's
computed `spare_vector` / `spare_origin`, and writes the origin back **×1000**
as mm. It degrades silently on `ImportError` (aarch64 without CadQuery) or
`FileNotFoundError` (missing airfoil `.dat`) — logging a warning only.
🟢 CONFIRMED

### Dihedral persistence (gh-951) 🟢 CONFIRMED

The terminal rib's local-x rotation moves no outboard station, so it leaves no
trace in `xyz_le` and cannot be reconstructed from positions. It is therefore
persisted explicitly in `wing_xsecs.dihedral`
(`aeroplanemodel.py:219-225`). The write path is `_station_dihedral`
(`model_schema_converters.py:998-1015`):

```
station i airfoil = segments[i].root_airfoil        for i < N
station N airfoil = segments[-1].tip_airfoil        (terminal rib)
dihedral = airfoil.dihedral_as_rotation_in_degrees
```

`NULL` on legacy rows → consumers fall back to the geometry-derived dihedral.

### Structural pipeline — the real formulas

**Stage 1 — section-modulus sizing** (`app/services/spar_sizing.py`, gh-1008,
reference: *kirch Hauptholm*). Units: `M` in N·m, `σ` in MPa (= N/mm²),
dimensions in mm, `W` in mm³, mass in kg. 🟢 CONFIRMED

```
M_design(y) = |M(y)| · g_limit · j                     (l.9-13 docstring)
erf_W       = M_design · 1000 / σ_allow                (required_section_modulus, l.78-88)
outer(y)    = chord(y) · (t/c)(y) · packing_factor     (l.13)

Section moduli (mm³):
  rectangular  W = b·h²/6                              (l.40-45)
  capped (I/C) W = b·(H³ − h³)/(6·H)                   (l.48-54)
  solid rod    W = d³/10                               (l.57-62)
  tube         W = π·(Da⁴ − Di⁴)/(32·Da)               (l.65-70)

Inverse solves (solve_dimension, l.96+):
  tube         Di = (Da⁴ − 32·erf_W·Da/π)^(1/4)        (l.137-146)
  rod          d  = (10·erf_W)^(1/3)                   (l.159)
  rectangular  b  = 6·erf_W / h²                       (l.182)
  capped       h  = (H³ − 6·H·erf_W/b)^(1/3)           (l.196-208)
```

Guard: `σ_allow ≤ 0` raises `ValueError` — the material schema permits 0, so the
division is protected at the formula (`spar_sizing.py:86-87`). 🟢 CONFIRMED
Fallback `t/c` when airfoil data is unavailable: `_TC_FALLBACK = 0.12` (l.32).

Defaults from `SparSizingParams` (`app/schemas/spar_sizing.py:12-51`):
`safety_factor_j = 1.5` (`> 0`), `packing_factor = 0.8` (`0 < x ≤ 1`),
`shape ∈ {tube, rod, rectangular, capped}`, `cap_width_mm` required only for
`capped`. `material_id` must point to a `Component` of type `material` carrying
`allowable_bending_stress_mpa`.

**Stage 2 — station sampling** (`spar_solver.build_stations_from_geometry`,
l.681-746). For `n_span` stations root→tip (default 6):

```
y_spans = linspace(0, 1, n_span);  y_spans[0] → _ROOT_EPS = 1e-3
   (the y_span=0 slice is a pinched, zero-thickness section on a real loft and
    would poison the governing max-moment root station — gh-1037 #4)

x_c        = requested x/c, else the section's max-thickness location
clr        = (1 − packing_factor)/2 · thickness
band_lo    = bottom_z + clr ;  band_hi = top_z − clr
M_design   = |moment_fn(y_span)| · g_limit · j     (defaults g=3.0, j=1.5)
required_od = solve_dimension("rod", erf_W, outer = band_hi − band_lo)
```

**Rear-spar clearance (gh-1059)** — a *computed* rear/torsion spar must never
overlap the movable surface:

```
rear_spar_x_c_with_clearance(requested, hinge_x_c, clearance = 0.03):
    if hinge_x_c is None: return requested
    return max( min(requested, hinge_x_c − 0.03), 0.05 )
```

`_REAR_CLEARANCE_FRACTION = 0.03`, `_MIN_REAR_X_C = 0.05`
(`spar_solver.py:181-221`). The guard is explicitly documented as applying only
to computed spars — a designer may still place a reinforcing spar inside a
control surface manually. 🟢 CONFIRMED

**Stage 3 — layout solve** (`plan_spar` / `solve_spar_plan`,
`spar_solver.py:342, 619-672`). Per half-span: greedy straight-piece fit, split
into telescoping runs where the strength-required OD exceeds the containment
band. Then:

* **front joint**: `_inboard_collinear` compares the two halves' root
  `center_z` within `tol_mm = 5.0`; equal → `"continuous"`, otherwise
  `"reinforcement+joiner"` with a generated reinforcement piece. A single-half
  surface (e.g. a vertical stabiliser, gh-1091) is forced to `"continuous"`
  rather than indexing into the empty half.
* **rear joint**: `"continuous"` when a straight collinear rod through `y=0`
  stays inside the band on both halves, otherwise `"bent-pin"`.
* **utilisation** is reported honestly and may exceed 1.0:
  `utilisation = od / max(tightest_band, 1e-6)`; `feasible = od ≤ tightest`
  (`_piece_from_run_with_od`, l.490-529). The infeasibility message names the
  governing station and suggests a capped/box spar.
* **negligible-load tip (gh-1076)**: `NEGLIGIBLE_OD_FLOOR_MM = 1.0` — a tip
  station whose required OD falls below 1 mm produces **no piece**; the region
  is reported as `front_no_spar_from_y` / `rear_no_spar_from_y` instead of a
  degenerate Ø≈0 tube (`spar_solver.py:44-53, 438-457`).
* **bore**: `_bore_for` reconstructs `erf_W` from the governing rod OD via
  `required_section_modulus_from_od(od) = od³/10` and solves the tube path;
  falls back to `wall_factor = 0.6` of the OD when strength wants a solid
  (l.460-487). `telescope_clearance_mm = 0.5` is the radial slip-fit gap.

🟢 CONFIRMED. The whole solver is deliberately **CAD-free decision logic** so
every branch runs on the CI fast tier with hand-built `StationData`
(`spar_solver.py:1-24`).

**Stage 4 — section geometry seam** (`cad_designer/airplane/geometry/section_geometry.py`).
`SectionGeometry` recovers `(y/span, x/c)` points in two modes (gh-1046):
`"analytic"` (default — blends segment airfoils via
`WingConfiguration.get_points_on_surface`, no solid built) and `"solid"` (builds
the RIGHT-half loft once via `WingLoftCreator` and slices it; `sample` groups
requests by `y_span` so each plane is cut once). `points_per_edge` is clamped to
`[8, 4096]`. Raises `SectionGeometryUnavailableError` when CadQuery is absent.
The docstring records the analytic path exists to avoid the **~13 s**
`WingLoftCreator` bottleneck. 🟢 CONFIRMED (l.160-219)

### Control-surface mixing (gh-772) 🟢 CONFIRMED

`app/services/control_surface_mixing.py` is the single source of truth shared by
the AVL geometry builder, the AeroSandbox airplane builder and the
trim-enrichment service.

```
_DUAL_ROLE_AXES = { "elevon":     ("pitch", "roll"),
                    "flaperon":   ("lift",  "roll"),
                    "ruddervator":("pitch", "yaw") }      (l.29-33)
PRIMARY_AXES   = {"pitch", "lift"}   # symmetric component
SECONDARY_AXES = {"roll", "yaw"}     # antisymmetric component
```

A **dual-role** surface emits **two** AVL `CONTROL` variables on the same
section (AVL sums multiple CONTROL lines per section):

| axis | `sgn_dup` | gain | `symmetric` | baseline deflection |
|---|---|---|---|---|
| primary | `+1.0` | `mix_gain_primary` | `True` | the surface's deflection |
| secondary | `−1.0` | `mix_gain_secondary` | `False` | **`0.0`** |

The secondary baseline is 0 so the AeroBuildup fallback never feeds a roll/yaw
deflection into the single-axis ASB model (l.126-128). A single-axis role keeps
its existing tagged name and `±1` sign verbatim (l.134-146).

Naming: `axis_control_name` produces `[{role}]{axis}_{wing_key}_{xsec_index}`,
e.g. `[ruddervator]pitch_htail_1` (l.76-84). Names **must be globally unique** —
AVL silently collapses same-named CONTROL variables into a single DOF, so
`assert_unique_control_names` raises on any duplicate (l.149-164).

Two invariants are called out explicitly in the module docstring:
`SgnDup` is a **sign flag, never a differential magnitude**, and
`differential_ratio` is a **reporting-only kinematic** applied post-trim for
left/right display — it never alters the aero/trim solution
(l.14-15; `aeroplaneschema.py:372-381`).

Cross-validation on write (`_validate_mix_fields`, `aeroplaneschema.py:51-78`):
`differential_ratio ≠ 1.0` is only legal for
`DIFFERENTIAL_ROLE_VALUES = {aileron, elevon, flaperon, ruddervator}`;
`mix_gain_secondary ≠ 1.0` only for
`DUAL_ROLE_VALUES = {elevon, flaperon, ruddervator}`. Comparison uses
`math.isclose(..., rel_tol=1e-9, abs_tol=1e-9)`, and a `None` role (partial
patch) skips the check entirely. 🟢 CONFIRMED

### Turbulator optimiser (gh-934) 🟢 CONFIRMED

`app/services/turbulator_optimizer_service.py` finds, per wing section, the
forced-transition location that **minimises section drag** at the section's
operating `(CL, Re)`.

```
XTR_GRID = linspace(0.2, 0.9, 15)          # x/c sweep (l.53)
_ALPHA_GRID = linspace(-4.0, 14.0, 37)     # α grid for cd-at-CL lookup (l.60)

i_opt      = argmin over FINITE cd values
xtr_opt    = XTR_GRID[i_opt]
delta_cd   = cd_tripped − cd_clean

ΔCD0 = symmetry_factor · Σ (Δcd_i · S_i) / S_ref ,  symmetry_factor = 2 for a
       symmetric wing (section_aoa_service returns half-span sections only)
```

Warnings — never silent failures — are emitted for: all-NaN cd (no optimum),
mean `analysis_confidence < 0.80`, and a boundary optimum
(`i_opt ∈ {0, len−1}` → the true minimum may lie outside `[0.2, 0.9]`)

### The superellipse — exact definition 🟢 CONFIRMED

Shape law in the cross-section plane (Y lateral, Z vertical):

```
|y/a|^n + |z/b|^n = 1
```

`a`, `b` are **half-axes**, not diameters. Axis convention (gh-706):
`a → ASB FuselageXSec.width` (Y), `b → ASB FuselageXSec.height` (Z)
(`app/schemas/aeroplaneschema.py:711-723`). `n = 2` gives an ellipse; larger `n`
approaches a rectangle. The polar form used by the code is

```
r(θ) = ( |cos θ / a|^n + |sin θ / b|^n )^(−1/n)
```

(`cad_designer/aerosandbox/slicing.py:585-586`). Derived quantities:

```
perimeter(a,b,n) = ∫₀^{2π} sqrt(r² + (dr/dθ)²) dθ           (quad, limit=200)  (l.588-598)
area(a,b,n)      = 4·a·b·Γ(1 + 1/n)² / Γ(1 + 2/n)                             (l.600-602)
polygon_area     = shoelace formula on the sliced outline                      (l.604-608)
```

### Superellipse fitting 🟢 CONFIRMED

`fit_symmetric_superellipse` (`slicing.py:610-661`) is the one used for
fuselages (the asymmetric `fit_superellipse` at l.663 exists as well):

1. The centre is **forced onto the Z axis**: `center = [0, mean(z)]`.
2. Points are shifted, converted to `(θ, r)`, then **mirrored**
   (`θ → −θ`, same `r`) to enforce left/right symmetry.
3. Objective minimised over `(a, b, n)`:

```
radius_loss = mean( (r_i − r_fit(θ_i))² )
length_loss = (perimeter_fit − perimeter_actual)²
objective   = radius_loss + 0.01 · length_loss
```

4. `scipy.optimize.minimize`, method `L-BFGS-B`,
   `x0 = [1.0, 1.0, initial_n=2.0]`,
   bounds `a,b ∈ (1e-3, ∞)`, **`n ∈ [0.5, 8.0]`**.

The `0.01` perimeter weight and the `n` bounds are the two magic numbers of the
fuselage pipeline.

`_parse_dat_file(path) -> (name, [[x, y], ...])`

names, per-file `try/except` that increments `errors` and calls `db.rollback()`

`AIRFOILS_DIR = REPO_ROOT / "components" / "airfoils"`, with a comment recording

### Family classifier 🟢 CONFIRMED

`classify_family(coords) -> AirfoilFamily`
(`airfoil_low_re_service.py:120`). Five frozen labels:
`flat_bottom | semi_symmetric | symmetric | cambered | reflexed`
(`app/schemas/airfoil.py:69`). Evaluation order is load-bearing:
**reflexed → symmetric → flat_bottom → semi_symmetric → cambered** — the
symmetric test must fire before flat_bottom because a perfectly symmetric
section also passes the lower-surface linearity test (l.102-105).

| Threshold | Value | Meaning |
|---|---|---|
| `_SYMMETRIC_MAX_CAMBER_PCT` | `0.5` | below → `symmetric` |
| `_SEMI_SYMMETRIC_MAX_CAMBER_PCT` | `2.0` | below → `semi_symmetric` |
| `_FLAT_BOTTOM_Y_THRESHOLD` | `0.002` | strict legacy lower-surface flatness |
| `_FLAT_BOTTOM_AFT_X_LO` | `0.30` | start of the aft linearity window |
| `_FLAT_BOTTOM_QUAD_THRESHOLD` | `0.005` | max quadratic coeff of the aft lower-surface fit → flat |
| `_REFLEX_AFT_CAMBER_RATIO_MAX` | `0.06` | Signal A: `camber(x=0.9)/max_camber` below → reflexed |
| `_REFLEX_AFT_CONCAVITY_MIN` | `0.015` | Signal B: min positive quadratic coeff of the camber line over `x∈[0.5,1]` |
| `_REFLEX_B_MIN_CAMBER_PCT` | `2.0` | Signal B guard — only fires above 2 % camber |

**Reflex detection (gh-834)** is the most heavily documented rule in the file
(l.46-88). The original code used the camber-line **endpoint** `camber[-1]`,
which is ≈0 for *every* sharp-TE airfoil, so only blunt/open-TE supercritical
shapes were labelled reflexed while real flying-wing sections (MH60, E184, EH
series) were missed. The fix uses camber-line **shape** over the aft chord:
Signal A (sharp-TE reflex, ratio < 0.06 — NACA 4412 scores 0.31, Clark Y 0.28)
plus Signal B (open/upturned TE, positive quadratic coefficient > 0.015 —
Clark YH ≈ +0.039, NACA 4412 ≈ −0.11). `camber_at_te` is now **stored as the
camber value at x = 0.9**, not at the TE. 🟢 CONFIRMED

Consequence recorded in the code: stored `family` values change after this fix,
so a `--force` re-backfill is required post-merge.

### NeuralFoil sweep 🟢 CONFIRMED

`compute_airfoil_low_re(name, coords, re_grid, *, model_size="xxxlarge",
n_crit=9.0, confidence_gate=0.90, alpha_start=-5.0, alpha_end=18.0,

### The three scoring lenses — exact formulas 🟢 CONFIRMED

Only three `active_lens` values are legal: `re_agnostic | mission |
target_cl_cruise`. **Glide points never auto-rank** — `target_cl_best_glide`
and `target_cl_min_sink` are display-only, so the default sort is never driven
by an engine-out / min-sink contingency point (`app/schemas/airfoil.py:71-84`).

**Lens 1 — `score_re_agnostic(polar)`** (l.831-891). Weighted sum of normalised
metrics, renormalised by the weights actually present:

| Component | Normalisation | Weight |
|---|---|---|
| `ld_max` | `min(ld_max / 60.0, 1)` | 0.35 |
| `cl_max` | `min(cl_max / 1.5, 1)` | 0.25 |
| `drag_bucket_width` | `min(bucket / 0.8, 1)` | 0.20 |
| `stall_gentleness` | `clamp(1 + stall/0.15, 0, 1)` → 0 at `stall ≤ −0.15` | 0.10 |
| `cd_min` | `min(0.008 / cd_min, 1)` | 0.10 |

`score = Σ(v·w) / Σw`, clamped to `[0,1]`; `None` when no component is available.

**Lens 2 — `score_mission(...)`** (l.894-940):

```
score_mission = re_agnostic × family_bonus × thickness_match × cl_bonus

family_bonus    = 1.0 if family ∈ preferred_families else 0.7
thickness_match = 1.0 inside [t_min, t_max]; outside: max(0, 1 − gap/5.0)
cl_bonus        = (1 − cl_max_weight) + cl_max_weight · min(cl_max/1.5, 1)
```

Mission bands (`app/settings.py:19-56`):

| mission | t_min % | t_max % | `cl_max_weight` | preferred families |
|---|---|---|---|---|
| trainer | 11 | 14 | 0.70 | flat_bottom, semi_symmetric |
| sport | 9 | 13 | 0.55 | semi_symmetric, cambered |
| aerobatic | 8 | 12 | 0.40 | symmetric |
| glider | 10 | 14 | 0.50 | cambered, semi_symmetric |
| flying_wing | 8 | 13 | 0.50 | reflexed, symmetric |
| slope_soarer | 8 | 12 | 0.45 | semi_symmetric, cambered |

**Lens 3 — `score_target_cl(...)`** (l.943-1009): `Match × Efficiency`.

```
cl_star   = best_ld_cl(cd0, k, cl0) = sqrt(cl0² + cd0/k)      (closed form, l.715-760)
r         = CD(cl_target) / cd0                                (relative drag rise)
r_poor    = settings.low_re_score_r_poor = 2.5
tolerance = (drag_bucket_width / low_re_bucket_tolerance_ref=0.6) × 0.5

Match:  r ≤ 1        → 1.0
        within tol   → 1 − (r−1)/(r_poor−1)
        r ≥ r_poor   → 0.0, unless the CL_max fallback applies

CL_max safety fallback (r ≥ r_poor and cl_max present):
        Match = clamp( (cl_max − cl_target) / 0.30 , 0, 1 )
        (low_re_score_cl_max_safety_band = 0.30)

Efficiency = min( re_cd0_reference / cd0 , 1.0 )
Final      = clamp(Match × Efficiency, 0, 1)
```

`best_ld_cl` returns `None` for `cd0 ≤ 0` or `k ≤ 0` — the derivation is written
out in full in the docstring (l.715-760). The CL_max fallback exists because
glider min-sink CLs (`CL ≈ √3 · CL_md`) sit far above `cl_star`, so the pure
drag-rise Match collapses to 0 even for excellent glider sections (l.977-997).

**Fleet reference.** `compute_re_cd0_reference(polars_by_name, re_query,
percentile=20.0)` (l.771-823) interpolates every airfoil to `re_query` and
returns the **20th percentile** of the finite `cd0` values — a robust
"best achievable at this Re" reference rather than the absolute minimum. Falls
back to `_CD0_REFERENCE_FALLBACK = 0.020` on an empty fleet.

**Level-flight CL helper**: `CL = (m·g) / (0.5·ρ·V²·S)`, raising `ValueError`
for non-positive `V` or `S` (`_level_flight_cl`, l.686-707).

**Tie-breaking.** Ranking sorts by `(confidence tier, −score)` — a confidence
tier is the primary key so a high-scoring low-confidence airfoil never outranks
a trustworthy one (`suitability_service.py:629, 632`). 🟢 CONFIRMED

**Tip-stall caveat.** The score treats section CL as whole-wing CL (ideal
elliptic, untwisted). This ignores the tip-Re CL_max collapse that governs
tip-stall onset on tapered wings, so the contract *always* sets
`ignores_tip_re_clmax_collapse = True` and exposes `tip_re_flag` plus
`cl_max_margin = cl_max − max(target CLs)` (negative = stall risk)
(`app/schemas/airfoil.py:6-17, 174-187`). `tip_re_flag` fires when
`Re_tip < low_re_tip_re_abs_floor = 80 000` or the root→tip drop exceeds
`low_re_tip_re_rel_drop = 50 000` (`app/settings.py:109-114`). 🟢 CONFIRMED

### Execution model — process pool, and why 🟢 CONFIRMED

`cad_service` runs CAD in a `ProcessPoolExecutor(max_workers=4,
mp_context=multiprocessing.get_context("spawn"))`, lazily created by
`_get_executor()` (l.72-78) and torn down by `shutdown_executor()` (l.81-95)
from the FastAPI lifespan (`app/main.py:193`) and from the test fixture.

The module docstring (l.7-20) states the reason explicitly: **OCCT is not
thread-safe** — the same `.intersect().clean()` call that takes ~100 ms on the
main thread hangs indefinitely in a worker *thread* because OCCT holds global
state (BRepCheck messaging, memory pools, interrupt handlers). `spawn` is
chosen for platform consistency; `fork` is unsafe with OCCT bindings already
loaded.

**Everything that crosses the process boundary must be picklable**, and
`WingConfiguration` is not (it holds `cq.Vector` / OCCT `gp_Vec`). The parent
therefore ships an `AsbWingSchema` pickle and the worker rebuilds the
configuration with `asb_wing_schema_to_wing_config(schema, scale=1000.0)`
(`cad_service.py:303-307`, `tessellation_service.py:81-82`). `ServoInformation`
is rebuilt in the worker for the same reason (`cad_service.py:319-342`).

**Task registry.** `tasks: Dict[str, Dict[str, Any]]` + `tasks_lock`
(`cad_service.py:62-63`) is **parent-process, in-memory only** — it does not
survive a restart and is not shared across replicas. Keys are the aeroplane
UUID for exports and `f"{uuid}:tessellation:{wing_name}"` for tessellation
(`tessellation_service.py:180`). 🟡 INFERRED consequence: a task started before
a reload becomes unqueryable (`GET /status` → 404) even though its worker may
still be running.

### The export blueprint 🟢 CONFIRMED

`build_wing_blueprint` (l.206-262) synthesises a **three-node plan tree** in
exactly the `$TYPE` dialect the `GeneralJSONDecoder` expects — the same format
stored in `construction_plans.tree_json`:

```
ConstructionRootNode  creator_id "eHawk-wing.root.root", loglevel 50
├── ConstructionStepNode  creator_id = <wing_name>, loglevel 50
│     creator: WingLoftCreator | VaseModeWingCreator
│             offset 0, wing_index <wing_name>, wing_side "BOTH", loglevel 10
│             (+ leading/trailing_edge_offset_factor for vase mode)
└── ConstructionStepNode  creator_id "output-wing", loglevel 50
      creator: <exporter class>, file_path "./tmp/exports",
               tolerance 0.1, angular_tolerance 0.1, loglevel 20
```

Defaults: `leading_edge_offset_factor = 0.1`, `trailing_edge_offset_factor =
0.15` (`cad.py:266-271`), `wing_scale = 1000.0` — metres → millimetres
(`cad_service.py:517`).

**R1 — the 3MF export path is broken.** `map_exporter_type` (l.185-203) maps
`ExporterUrlType.THREEMF → "ExportTo3MFCreator"`, but the real class is
`ExportTo3mfCreator` (lower-case `mf`,
`cad_designer/airplane/creator/export_import/ExportTo3mfCreator.py:10`). The
decoder resolves `$TYPE` with `getattr(module, name)`, so a 3MF export raises
`AttributeError` inside the worker and the task ends `FAILURE`. The existing
test asserts the wrong string
(`app/tests/test_cad_service_extended.py:130`), which locks the defect in.
`construction_plan_service.py:563` uses the correct spelling. 🟢 CONFIRMED

**R2 — `amf` is advertised but unsupported.** `ExporterUrlType.AMF = "amf"`
exists (`app/schemas/AeroplaneRequest.py:58`) but has no entry in the mapping,
so the request fails with `ValidationError` → 422. 🟢 CONFIRMED

**R3 — `./tmp/exports` is a shared mutable directory.** The worker zips
*everything* in `./tmp/exports` into `./tmp/{aeroplane_id}.zip` and then
`os.unlink`s *every* file in it (`cad_service.py:368-377`).
`check_task_available` only serialises tasks **per aeroplane**
(l.159-176), while the pool has 4 workers — two concurrent exports for
*different* aeroplanes will therefore capture each other's files and delete
them. 🟢 CONFIRMED (race by construction). `zipf.write(file.path)` also keeps
the `tmp/exports/` prefix inside the archive.

**R4 — the download path re-homes files under `tmp/`.**
`_ensure_file_under_tmp` (`cad.py:59-76`) resolves the recorded path and, if it
is not already under `CWD/tmp`, copies it to `tmp/{aeroplane_id}/zip/<name>`
before serving. 🟢 CONFIRMED

### Tessellation 🟢 CONFIRMED

`_run_tessellation_worker` (`tessellation_service.py:53-165`):

```
wing_schema  = pickle.loads(...)
wing_config  = asb_wing_schema_to_wing_config(wing_schema, scale=1000.0)
creator      = WingLoftCreator(creator_id="tessellation", wing_index=wing_name,
                               wing_side="BOTH", wing_config={wing_name: wing_config})
shapes       = creator._create_shape(shapes_of_interest={}, input_shapes={})
part_group, instances = to_ocpgroup(shape, names=[wing_name],
                                    colors=["#FF8400"], alphas=[1.0])
params       = {"deviation": 0.1, "angular_tolerance": 0.2}
instances, shapes, _ = tessellate_group(part_group, instances, params, progress=None)
shapes["bb"] = combined_bb(shapes).to_dict()
```

Result envelope: `{"data": {"instances", "shapes"}, "type": "data", "config":
{"theme": "dark", "control": "orbit"}, "count": <n>}`. All NumPy values are
flattened by `_numpy_to_list` (l.36-50) before serialisation.

Two things worth flagging:

* The worker calls the **private** `_create_shape` hook directly rather than
  the public `create_shape` template method, bypassing
  `return_needed_shapes` / the log-level dance. Harmless here (no upstream
  shapes) but it means `WingLoftCreator` is used off-contract. 🟡 INFERRED
* Failures are reported as `{"status": "FAILURE", "error": f"Tessellation
  failed: {type(err).__name__}"}` — deliberately **type-only**, no detail
  leakage (l.162-165).

**Debounce and cancellation** (`trigger_background_tessellation`, l.240-300):
`_DEBOUNCE_SECONDS = 2.0`; a new request cancels both the pending
`threading.Timer` and any in-flight `Future` for the same
`f"{aeroplane_id}:{wing_name}"` key. When the worker finishes,
`is_hash_current` re-checks the stored `geometry_hash` and **discards** the
result if the geometry changed meanwhile (l.366-368). 🟢 CONFIRMED

### Cache 🟢 CONFIRMED

### `AbstractShapeCreator` — the exact contract 🟢 CONFIRMED

```python
__init__(creator_id: CreatorId,
         shapes_of_interest_keys: list[ShapeId] | None,
         loglevel: int = logging.FATAL)

identifier                      # property → creator_id; also the output-dict key
shapes_of_interest_keys         # property → the declared upstream keys
_create_shape(shapes_of_interest, input_shapes, **kwargs) -> dict   # abstract
create_shape(input_shapes=None, **kwargs) -> dict                   # template method
```

`create_shape` (l.49-61) is the template method:

1. If `shapes_of_interest_keys is not None`, call `return_needed_shapes`.
2. `return_needed_shapes` (l.79-95) fills every `None` slot from
   `reversed(input_shapes.keys())` — the input dict is ordered **most
   significant last** — and raises `KeyError` when there are fewer inputs than
   `None` slots.
3. `check_if_shapes_are_available` (l.63-77) raises
   `KeyError(f"shapes are missing in step '{identifier}': {missing}")`.
4. The **root logger level is mutated** to `self.loglevel` when it is lower
   than the effective level, then restored after `_create_shape`
   (l.53-60). 🟡 INFERRED: process-wide and not thread-safe — two concurrent
   plan executions in the same process interleave log levels.

Output-key convention (docstring l.43-46): `<identifier>` for a single shape,
`<identifier>.<known_name>` for named outputs, `<identifier>[i]` for indexed
ones. A repeated identifier **silently overwrites** the earlier shape (l.25).

Author-facing contract, from `_creator_template.py`:
`suggested_creator_id` may contain `{param}` placeholders; the first docstring
line becomes the gallery description; an `Attributes:` block of
`name (type): text` lines becomes per-field tooltips; runtime-injected config
must be stored as `self._private` so the encoder skips it; a new Creator must
be registered in its subpackage `__init__.py`.

### The construction tree 🟢 CONFIRMED

`ConstructionStepNode` and `ConstructionRootNode` are both
`AbstractShapeCreator` **and** `MutableMapping` over their `successors`
`OrderedDict`.

`ConstructionStepNode._create_shape` (l.48-76):

```
output_shapes = self.creator.create_shape(input_shapes, **kwargs)
_input_shapes = input_shapes.copy()            # never mutate the caller's dict
for key in output_shapes: _input_shapes.pop(key, None)
_input_shapes.update(output_shapes)            # newest keys land LAST
kwargs.update(output_shapes)
for succ in self.successors.values():
    kwargs.update(succ.create_shape(_input_shapes, **kwargs))
return kwargs                                  # every shape produced so far
```

`ConstructionRootNode._create_shape` (l.48-58) differs in one significant way:
it hands each top-level successor `input_shapes={}` — only `kwargs` carries the
accumulated registry. So positional (`None`) slot resolution works *within* a
branch, never *across* top-level branches. 🟢 CONFIRMED

`JSONStepNode` (24 l.) loads a whole sub-tree from a file with
`GeneralJSONDecoder` and adopts its `creator` / `successors`.

`AbstractConstructionStep` (11 l.) declares
`construct(input_shapes: list[Workplane], **kwargs) -> list[Workplane]` and has
**no implementers** — dead interface. 🟢 CONFIRMED

### `GeneralJSONEncoder` / `GeneralJSONDecoder` — the exact rules 🟢 CONFIRMED

* Marker: `JSON_CLASS_TYPE_ID = "$TYPE"` = `o.__class__.__name__` (l.18-25).
* The encoder writes **only public attributes** — anything starting with `_` is
  dropped. That is why runtime-injected config is stored privately.
* The decoder resolves the class with
  `getattr(sys.modules["cad_designer.airplane.GeneralJSONEncoderDecoder"],
  name)` (l.196-198). The resolvable universe is therefore exactly what that
  module imports: `ConstructionRootNode`, `ConstructionStepNode` and
  `from cad_designer.airplane.creator import *`. **Topology classes are not
  resolvable** and never appear in a plan JSON.
* If `__init__` accepts `**kwargs`, the whole JSON dict plus all decoder kwargs
  are passed; otherwise the dict is intersected with the `__init__` parameter
  names and the matching decoder kwargs are overlaid (l.201-210).
* `_coerce_params` (l.125-176) coerces JSON strings to the annotated base type,
  unwrapping `NewType`, `Annotated`, pydantic `confloat`, and string
  annotations from `from __future__ import annotations`. A `list[...]`
  annotation receiving a bare string is wrapped into a one-element list —
  the guard against iterating a shape-key string character by character
  (l.147-149). Numeric strings are normalised locale-aware
  (`_normalize_numeric_string`, l.95-122): `"0,1"`→`0.1`,
  `"1.234,56"`→`1234.56`, `"1,234.56"`→`1234.56`. Failures log a warning and
  keep the raw value.
* `creator_id` placeholders `{param}` are substituted from sibling parameter
  values with `re.sub(r"\{(\w+)\}", …)`; unresolved placeholders are left
  verbatim (l.212-223).

**Consequence:** renaming or deleting a Creator invalidates every stored plan
that references the old `$TYPE`.

### Domain model 🟢 CONFIRMED

A **construction plan** is a serialised `ConstructionRootNode` tree stored in
`construction_plans.tree_json`. `plan_type` discriminates:

* `"template"` — reusable, `aeroplane_id` is `NULL`;
* `"plan"` — a deep copy bound to one aeroplane.

`instantiate_template` (l.207-232) validates `plan_type == "template"`, verifies
the aeroplane exists, and `copy.deepcopy`s the tree into a new row named
`"{template.name} — Plan"`. `to_template` (l.235-251) does the reverse
(`"{plan.name} — Template"`). There is **no version chain and no back-link**:
after instantiation the two rows evolve independently. 🟢 CONFIRMED

There is no status column and no state machine — the only lifecycle is
`plan_type` plus the artefact directories an execution leaves behind.
Execution is **not idempotent**: every run creates a new
`<aeroplane>/<plan>/<execution_id>` directory, except template runs, which
`rmtree` the previous run first (`artifact_service.create_template_execution_dir`).

A **construction part** is unrelated to a plan: it is an uploaded STEP/STL file
scoped to an aeroplane, with extracted geometry metadata and a `locked` flag
that blocks deletion. `component_tree.construction_part_id`
(`alembic/versions/7cc3eaf27d6b_…py`) links a tree node to one.

Validation on write is deliberately thin — `_validate_tree_json` (l.72-81)
only requires `$TYPE` and `creator_id` at the root. Everything else fails at
decode time. 🟢 CONFIRMED

**Silent legacy migration.** `_migrate_tree_json` (l.113-133) rewrites a root
whose `$TYPE` is `ConstructionStepNode` into `ConstructionRootNode`, drops the
`creator` key, `flag_modified`s the JSON column and flushes — **on every read**
via `get_plan`. 🟢 CONFIRMED

### Streaming execution 🟢 CONFIRMED

`execute_plan_streaming` (l.725-885) is a generator of SSE frames:

```
event: shape     data {"name": <shape id>, "tessellation": {...}}
event: complete  data {"duration_ms", "shape_keys", "tessellation",
                       "artifact_dir", "execution_id"}
event: error     data {"error", "duration_ms", "artifact_dir", "execution_id"}
```

Mechanism: `set_display_callback(on_display)` +
`os.environ["DISPLAY_CONSTRUCTION_STEP"] = "1"` arm the
`@conditional_execute`-gated `Workplane.display` plugin, so **every
`display()` call inside a Creator emits a shape event**. The work runs on a
daemon thread; the generator drains a `queue.Queue` with `timeout=300` →
`event: error {"error": "Execution timed out"}` on starvation, then
`thread.join(timeout=5)`. The `finally` block restores the previous env-var
value and clears the callback.

> 🔴 Both the display callback and the env var are **process-global**. Two
> concurrent streams (or a stream concurrent with a non-streaming execution)
> will cross-deliver shape events and can re-enable/disable each other's
> display gate. There is no lock and no per-execution context. 🟢 CONFIRMED

### Pipeline 🟢 CONFIRMED

`import_vsp3` (l.324-420) follows a sequence the gh-640 acceptance criteria
call critical:

```
_ensure_handlers_loaded()          # lazy, once per process
vsp.ClearVSPModel()                # without this, ReadVSPFile MERGES into current state
vsp.ReadVSPFile(path)
source_unit = _read_source_length_unit(vsp, vsp.GetVehicleID())
if hasattr(vsp, "SetLengthUnit"): vsp.SetLengthUnit(vsp.LEN_M)   # legacy only
vsp.Update()
for gid in vsp.FindGeoms(): dispatch or warn
for fn in _POST_PASSES: fn(aeroplane, ctx, vsp)
```

`_read_source_length_unit` does `FindParm(vehicle_id, "LengthUnit",
"Vehicle_Info")` and treats `""` as "not found" — OpenVSP prints
`Can't Find Parm` to stderr but returns an empty string rather than raising.

docstring and l.352-368 record explicitly. `LEN_UNIT_TO_METERS` (l.63-71) maps
the legacy enum (`0 mm … 6 unitless`).

**Type canonicalisation.** `GetGeomTypeName(gid)` returns Title-Case display
names (`"Wing"`, `"BodyOfRevolution"`) while `AddGeom` / `GetGeomTypes` use
UPPERCASE tokens. `_DISPLAY_TO_CANONICAL` (l.194-211, 16 entries) normalises,
falling back to `.upper()` for unknown names — verified against OpenVSP 3.50.4.
🟢 CONFIRMED

**Warning discipline.** `ImportContext` (l.98-141) collects `ImportWarning`
records (`component_type`, `component_name`, `reason`, `severity ∈ {info,
warning, error}`), a de-duplicated `lossy_components` list, weight items, and

### Wing planform derivation — the actual maths 🟢 CONFIRMED

`_read_section_parm` (l.109-121) tries group `XSec_{i}` first and falls back to
`XSec_{i-1}`, returning `0.0` when absent. The root x-section is
`{xyz_le: [0,0,0], chord: XSec_1.Root_Chord, twist: 0, x_sec_type: "root"}`;
`Root_Chord ≤ 0` warns and defaults to `1.0 m` (l.902-910).

Per section `i ∈ 1..n_sec` (each describes the segment outboard of
`XSec[i-1]`), reading `Span`, `Tip_Chord`, `Sweep`, `Sweep_Location`,
`Dihedral`, `Twist`:

```
Span ≤ 0                → warning + mark_lossy + skip the section

dihedral (gh-755): relative flag → cum_dihedral += Dihedral
                    absolute      → cum_dihedral  = Dihedral
twist    (gh-755): relative flag → cum_twist    += Twist
                    absolute      → cum_twist     = Twist

Λ_LE = sweep_at_le(Sweep, Sweep_Location, Span, c_root=prev_chord, c_tip=Tip_Chord)
       where tan(Λ_to) = tan(Λ_from) − (xref_to − xref_from)·(c_root − c_tip)/span
       (returns Λ_from unchanged when span ≤ 0)

cum_x += Span · tan(Λ_LE)
cum_y += Span · cos(cum_dihedral)      ← VSP's own rad·cos(angle), not `+= Span`
cum_z += Span · sin(cum_dihedral)
```

The small-angle shortcut `cum_y += span` was the pre-gh-755 bug, visible on
winglets and V-tails above ~5° dihedral (l.985-989). Sweep is **absolute per
section** in VSP — no flag, no accumulation (comment cites `WingGeom.cpp:1111`).
The last x-section gets `x_sec_type = None` so the
`AsbWingSchema.validate_last_xsec_has_no_segment_details` validator passes
(l.994-1005). Other parms read: `XForm` group `X/Y/Z_Location`,
`X/Y/Z_Rotation`; `Sym` group `Sym_Planar_Flag` → `wing.symmetric`; `EndCap`
group for tip caps.

### Scaling and source-unit detection 🟢 CONFIRMED

Bounds (`openvsp_import_service.py:78-81`): `SCALE_FACTOR ∈ (0.001, 10.0)`,
`TARGET_SPAN ∈ (0.1, 50.0) m`; the two options are mutually exclusive and a
violation raises `ScaleValidationError` (→ 400 mutex / 422 range).
`_compute_max_wing_span` uses `2·max|y_le|` for a symmetric wing, `max|y_le|`
otherwise.

`_scale_aeroplane_lengths` (l.254-293) scales wing `xyz_le` and `chord`,
`aeroplane.xyz_ref`, and weight-item `x_m/y_m/z_m`. It deliberately does **not**
scale twist (angular), masses (per the RC-scope decision — Variante B), or
fuselages (they are scaled later, after the slicer refinement, so the slicer
stays in the unscaled STEP frame — gh-765). A scaling run always appends an
`info` warning stating that masses were left untouched.

**gh-808 unit detection** (`_detect_source_scale_to_meters`, l.147-201): OpenVSP
3.50 stores no in-file unit, so a feet model would import 3.28× too large. The
importer exports the largest-X-span fuselage to STEP (which VSP writes metric),
measures its bounding box (`bb.xlen / 1000.0` — OCC normalises STEP to mm), and
compares against the raw handler span. `_snap_to_unit_scale` (l.108-126) snaps
that ratio to `{m 1.0, yd 0.9144, ft 0.3048, in 0.0254, cm 0.01, mm 0.001}`
within `_UNIT_SNAP_TOL = 0.02`; metres or no match → import unchanged. On a hit
the whole aeroplane is converted first, before target-span resolution. The
throwaway `_unitdetect_*` STEP directory is removed in a `finally`.

### Fuselage refinement gates 🟢 CONFIRMED

* `_is_x_dominant_fuselage` (l.494-520): refine only when the **handler** xsec
  positions give `extent_x ≥ 1.2·extent_y` and `≥ 1.2·extent_z`. Using the
  handler schema rather than the STEP bounding box is essential — a
  `symmetric=True` geom's STEP contains both halves and looks Y-dominant.
* Station budget: `min(80, max(15, n + 5·(n−1)))` for `n` handler xsecs, fed to
  `vsp_anchored_x_stations` — VSP-defined stations are mandatory anchors and
  intermediates are distributed weighted by shape change (gh-732).
* `_select_xsec_slice_source` (l.562-575) prefers the **surface** STEP over the
  sewn solid, because the solid carries internal seam faces at sharp fillets
  that fragment a section cut (gh-812; open bug #814).
* `_slicer_frame_matches_handler` (l.543-559): accept only when
  `0.5 ≤ x_span(refined)/x_span(handler) ≤ 2.0` (`_SLICER_FRAME_RATIO_MIN/MAX`,
  gh-803). Otherwise the handler schema wins.
* `_MM_TO_M = 0.001` (l.491) converts the slicer's mm output.

### REST surface 🟢 CONFIRMED

`POST /api/v2/import/openvsp` (201, `OpenVspImportResponseModel`) and
`POST /api/v2/import/openvsp/stream` (SSE). The stream emits
`event: progress {step, pct, detail}` at `parsing 5` → `parsing 15` →
`units 16` → `scaling 18` → persistence steps → `finalising 95`, then a single

the stream. The uploaded temp file is unlinked in a `finally` via
`asyncio.to_thread`.

# Cluster C — aerodynamic analysis, AVL & sizing

Modules covered: `aero-analysis`, `avl-integration`, `mission-and-sizing`.

Two cross-cutting invariants govern this whole cluster and are repeated in each
section because breaking either produces plausible-looking but wrong numbers:

1. **One aero truth per aircraft (gh-924).** `cd0` (parasite, *not* total CD),
   `e_oswald`, `(L/D)max` and `x_np` are produced **once** by
   `assumption_compute_service.recompute_assumptions` at the cruise point and
   cached on `aeroplanes.assumption_computation_context` (a JSON column). Every
   downstream consumer — speed polar, V-n envelope, matching chart, mission
   KPIs, endurance, spar sizing — **reads that context**; none re-derives its
   own. 🟢 CONFIRMED
2. **AeroSandbox is the default solver; AVL is the exception.** All defaults
   (`analyze_alpha_sweep`, `analyze_simple_sweep`, strip forces, retrim,
   assumption recompute, OP generation) run AeroBuildup or the in-process
   `VortexLatticeMethod`. AVL is only reached when the caller explicitly asks
   (`analysis_tool=avl`, `solver="avl"`) or uses the dedicated AVL trim
   endpoint. 🟢 CONFIRMED

### Algorithms — characteristic points from an α sweep 🟢 CONFIRMED

`_compute_alpha_sweep_characteristic_points` (`analysis_service.py:219-250`)
returns a fixed six-key dict; each entry is `None` when its inputs are absent.

| Point | Rule (`analysis_service.py`) |
|---|---|
| `maximum_lift_to_drag_ratio_point` | `argmax(CL/CD)` with `CD` guarded at `|CD| > 1e-12` (l.107-118) |
| `minimum_drag_coefficient_point` | `argmin(CD)` (l.120) |
| `maximum_lift_coefficient_point` | `argmax(CL)` (l.129) |
| `drag_at_zero_lift_point` | **linear interpolation** at the first `CL` sign change: `t = −CL_i/(CL_{i+1}−CL_i)`; falls back to `argmin(|CL|)` when no crossing (l.143-164) |
| `stall_point` | first index after `argmax(CL)` where **both** `CL` drops and `CD` rises; else `i_clmax+1` clamped (l.167-184) |
| `trim_point_cm_equals_zero` | same interpolation on the first `Cm` sign change; `CD` interpolated at the same `t` (l.187-216) |

**A1 — Speed polar from a drag polar** (`_compute_speed_polar`, l.430-583).
Pure function (no DB, no solver), so it is unit-testable:

```
for every point with CL > 0:
    V = sqrt(2·m·g / (ρ·S_ref·CL))
    w = V · (CD/CL)                      # sink rate
V, w ∝ sqrt(m)   →  one curve per mass, base mass always present (is_base)
V_stall      = sqrt(2·m·g / (ρ·S_ref·CL_max))
i_min_sink   = argmin(w);  i_best = argmax(CL/CD)  ( = argmax(V/w) )
```
Display bounds (gh-799): `v_axis_min = 0.7·min(V_stall)`,
`v_axis_max = 1.3·V_dive` (or the largest V present); if either is missing or
inverted **both** are dropped so Plotly autoranges. gh-871 converts the
characteristic `CL`s to α via the cached linear lift curve
(`_cl_to_alpha_deg`), so the chart can label α at stall / min-sink /
best-glide. Glue (`_build_speed_polar`, l.604-669) is deliberately best-effort:
any failure logs and returns `None` rather than breaking the sweep. 🟡 INFERRED
risk: a missing `mass` assumption silently defaults to **1.0 kg** with only a
log warning (l.617-623) — the returned polar is then physically meaningless
but structurally valid.

**A2 — VLM strip forces without AVL** (`vlm_strip_forces.py`, gh-674).
Reconstructs AVL-equivalent per-strip data from a `VortexLatticeMethod` solve
using only *public, version-stable* VLM geometry:

* `_strip_index_ranges(is_trailing_edge)` — panels are emitted
  chordwise-fastest, so every `is_trailing_edge` flag closes one strip.
* `_wing_strip_counts` — expected strips per wing =
  `segments · spanwise_resolution · (2 if symmetric else 1)`. If the sum does
  **not** match the actual strip count the code degrades to a *single aggregate
  surface* rather than crashing (l.239-243).
* Force decomposition: `d_hat = vlm.steady_freestream_direction` (normalised),
  `l_hat = [−d_z, 0, d_x]` normalised — i.e. lift ⟂ freestream in the x–z plane.
  `lift = f_strip · l_hat`, `drag = f_strip · d_hat`,
  `cl = lift/(q·A)`, `cd = drag/(q·A)`,
  `ai = degrees(atan2(drag, lift))`, `cl_norm = cl·chord/c_ref`.
* VLM is **inviscid**: `cdv`, `cm_c/4`, `cm_LE` are emitted as `0.0` and
  `C.P.x/c` as a constant `0.25`. 🟢 CONFIRMED — the Trefftz chart therefore
  shows no viscous component on the ASB path.

**A3 — Uniform-density remesh** (gh-855/gh-857, `_panels_per_segment`,
`remesh_uniform_density`, `_remesh_airplane`). Instead of giving every segment
the same `spanwise_resolution` (which over-resolved a 5 cm segment as much as a
95 cm one and spiked the `cl(y)` plot), the wing is rebuilt with inserted
sections so panels are distributed **∝ segment span**:

```
budget = _SPANWISE_PANELS_PER_HALF = 40 panels per half wing
n_i    = max(_MIN_PANELS_PER_SEGMENT=2, round(budget · span_i / Σspan))
span_i = hypot(Δy, Δz)                 # dihedral-inclusive true span
```
Intermediate sections are produced by `_blend_xsec`: linear `chord`, `twist`,
`xyz_le`, and `Airfoil.blend_with_another_airfoil` for the profile (falling
back to the inboard airfoil on any blend exception). The VLM then runs with
`spanwise_resolution=1`. `_remesh_airplane` re-asserts `s_ref`, `b_ref`,
`c_ref` and `xyz_ref` from the original airplane so the gh-788 main-wing
reference geometry survives the remesh. 🟢 CONFIRMED

**A4 — Spanwise loads → spar sizing** (`analyze_airplane_spanwise_loads`,
l.1987-2091). Reuses whichever strip-force path was selected, injects
`q = ½·ρ·V²`, then calls the pure `compute_spanwise_loads` integrator. With
`spar_params` it additionally resolves material, `g_limit` and real local
`t/c`:

* material must be a `ComponentModel` with `component_type == "material"` and a
  **positive** `allowable_bending_stress_mpa` (or an explicit
  `sigma_allow_mpa_override`) — zero is rejected with a 422 rather than
  dividing by zero (l.2129-2150).
* `g_limit` from `get_effective_assumption`; missing ⇒ `_G_LIMIT_DEFAULT = 3.0`
  with `g_limit_fallback=True`.
* `_surface_to_stations` sizes on the half with the **larger root bending
  moment** (`max(|M_sb|, |M_pt|)`).
* `_get_tc_by_y_for_surface` (gh-1022) builds real `t/c` from the built CAD
  section; unresolvable stations are simply omitted so `compute_spar_sizing`
  applies its documented `_TC_FALLBACK = 0.12`.

### The single-source-of-truth aero context (gh-924) 🟢 CONFIRMED

`recompute_assumptions(db, aeroplane_uuid)`
(`assumption_compute_service.py:59-809`) is a **sync** function; async callers
must wrap it in `asyncio.to_thread`. Pipeline:

```
0. build ASB airplane; skip silently if it has no wings
1. main_wing = argmax(wing.area())        →  s_ref / c_ref / b_ref OVERRIDDEN
   (ASB defaults to wings[0], which may be a tail — the gh-788/F1 bug class)
2. seed_defaults()  +  _load_or_create_config()  (both idempotent)
3. _stability_run_at_cruise      → x_np, MAC, cd0_parasite, S_ref
4. _coarse_alpha_sweep           → stall_alpha (argmax CL)
5. _fine_sweep_cl_max            → CL_max, cl[], cd[], v[], cdi[]
6. cg_x = x_np − target_SM · MAC          → written back as CALCULATED
7. parabolic fit (+ auto-refinement)      → cd0_fit, e_fit, R²
8. e from AeroBuildup Trefftz             → e_oswald_ab   (preferred)
9. per-config polars {clean, takeoff, landing}
10. Re-band table (gh-493)  → polar_re_table  (+ gh-924 backfill)
11. V-speeds, CG/loading/stability envelopes, landing field length
12. _cache_context()  →  aeroplanes.assumption_computation_context
```

**R1 — CD0 is the parasite drag, not the total drag.** The whole gh-924 fix.
`_parasite_cd0` (l.1098-1112):

```
CD_induced = CL² / (π · AR · e)          # e = AeroBuildup's own oswalds_efficiency
CD0        = CD_total − CD_induced       # only when CL/AR/e are sane AND result > 0
```
On a cambered wing α = 0 already carries lift (CL ≈ 0.55 for a glider), so
publishing `coefficients.CD` as CD0 double-counts induced drag and collapses
`(L/D)max` (17 instead of 24 on a high-AR glider). Ratified against
Anderson §6.7.2. 🟢 CONFIRMED

**R2 — `(L/D)max` is published from the self-consistent scalars, not the
sweep argmax.** (l.282-300)

```
E_max        = ½ · sqrt(π · AR · e / CD0)          # Scholz eq. 5.39
CL_at_E_max  = sqrt(CD0 · π · AR · e)
```
The raw flattened-sweep `argmax(CL/CD)` mixes Reynolds bands and lands on a
spurious high-CL sample (documented eHawk case: 18.8 @ CL 0.98 vs the correct
23.4 @ CL 0.55). The measured argmax is kept only as the fallback when the
parabolic scalars are unavailable.

**R3 — Oswald factor provenance chain.** `aerobuildup_trefftz` → `fit` →
`fallback`, recorded in `polar_by_config[*].e_oswald_provenance` and mirrored
by `context["e_oswald_fallback_used"]`.

```
e = CL² / (π · AR · CDi)   at the (L/D)max sample        # _e_oswald_from_sweep
CDi = D_induced / (q · S_ref)                            # collected in the fine sweep
sanity clip: reject unless 0 < e ≤ 1.10
```
`D_induced` comes free with the vectorised fine sweep, so this costs **zero**
extra AeroBuildup calls (gh-636). The effective value used by the V-speed
formulas is `e_oswald_effective = e or 0.8`.

**R4 — The parabolic fit has six rejection gates and never loosens a
threshold.** `_fit_parabolic_polar` (l.1417-1610) fits
`CD = CD0 + k·CL²` by OLS over the window
`CL ∈ [max(0.10, 0.10·CL_max), 0.85·CL_max]`, then `e = 1/(π·AR·k)`.

| Gate | Condition | Category |
|---|---|---|
| `insufficient_points` | ≥ 6 samples in the window (also fires on `AR ≤ 0`) | `sweep` |
| `non_monotonic_polar` | `dCD/d(CL²) ≥ −1e-6` (laminar-bubble / stall guard) | `data` |
| `negative_slope_k` | `k > 0` | `design` |
| `non_positive_cd0` | `cd0_fit > 0` | `consistency` |
| `unphysical_e_oswald` | `0.4 < e ≤ 1.0` | `design` |
| `cd0_stability_mismatch` | `|cd0_fit − cd0_stability| / cd0_stability ≤ 0.20` | `consistency` |

`PolarRejection` enforces the canonical gate→category pair with a model
validator, and only `category == "design"` is surfaced to the user — this is
the *design-error-feedback* rule in code: a `k ≤ 0` or unphysical `e` becomes a
visible warning instead of a silent `0.8` fallback. Hints are still written in
German (see 🔴 GAPs).

`_fit_parabolic_polar_with_refinement` (l.1618-1694) retries **only** for
`_REFINABLE_REJECTION_GATES = {insufficient_points, non_monotonic_polar}`,
halving the α step and multiplying the margin by 1.5 per attempt (max 2), and
sets `auto_refined=True` only when a refinement actually produced a fit.
Resolution goes **up**, thresholds never move. 🟢 CONFIRMED

**R5 — The fit is always gated against the *natural-transition* baseline.**
When a turbulator is enabled (gh-935) the stored `cd0` gets
`+ ΔCD0` (`apply_turbulator_delta_to_cd0`, l.2099-2168, area-weighted, ×2 for a
symmetric wing), but `raw_cd0` is preserved and passed as `cd0_stability` to
every fit — otherwise a meaningful ΔCD0 would spuriously trip the 20 % gate.

**R6 — Vectorised sweeps (gh-690).** `_coarse_alpha_sweep`,
`_fine_sweep_cl_max` and `_extract_cl_alpha_from_linear_sweep` each issue **one**
`AeroBuildup.run()` over an array-shaped `OperatingPoint` (was ~150 calls per
polar config). `_fine_sweep_cl_max` builds the grid with
`np.meshgrid(alphas, velocities, indexing="xy")` — V-outer / α-inner ravel
order, which downstream consumers index against.
`v_stall_approx = max(0.5·V_cruise, 3.0)`, `velocities = linspace(v_stall_approx,
v_max, fine_velocity_count)`, `alphas = arange(stall_α ± margin, step)`.

**R7 — Lift-curve regression with a hard quality gate (gh-487/gh-871).**
`_extract_cl_alpha_from_linear_sweep` fits `CL = CL_α·α + CL_0` by least
squares over α ∈ [−2°, +6°] and returns `(None, None)` when
`R² < 0.995`, when `CL_α ≤ 0`, or when fewer than 3 finite points survive.
`α₀ = degrees(−CL_0 / CL_α)`. Consumers (`compute_vn_curve`) then fall back to
Helmbold-Diederich.

**R8 — Picard refinement of the Re-dependent speeds (gh-493 A7).**
`_picard_iterate_speed` does exactly **one** pass: look up `cd0`/`e` at the
scalar `V₀` in `polar_re_table`, re-solve, accept `V₁` (logging a warning when
`|ΔV|/V₀ ≥ 5 %`). Applied to `V_md`, `V_min_sink`, `V_max`.

**R9 — Sub-stall clamp (gh-683).** `V_md` and `V_min_sink` are clamped to
`max(V, V_stall)` because the closed-form optimum CL can exceed `CL_max` on
high-AR/draggy polars and back-solve a physically unreachable speed.

**R10 — Re-table fallback backfill (gh-924).** When a band's fit is rejected
(laminar bubble at low Re) its `cd0`/`e` are `None` and the lookups would fall
back to a hard-coded `0.03 / 0.8` that contradicts the authoritative cruise
values. `recompute_assumptions` therefore overwrites every row with
`fallback_used or cd0 is None` with the single-source parasite `cd0` and the
Trefftz `e` (l.444-449), so every Re-dependent consumer reads the same value.

**Closed-form V-speeds** (all sea-level, `ρ = 1.225`, `g = 9.81`):

```
V_stall  = sqrt(2·W / (ρ·S·CL_max))                CL_max floored at 0.5
V_md     = sqrt(2·W / (ρ·S·sqrt(CD0/k)))           k = 1/(π·AR·e)
V_ms     = sqrt(2·W / (ρ·S·sqrt(3·π·e·AR·CD0)))    ( = V_md / 3^¼ ≈ 0.760·V_md )
w_min    = V_ms · 4·sqrt(CD0/(3·π·e·AR))           gh-692
V_max     solves  a·V⁴ − P_η·V + b = 0             a = ½ρS·CD0
                                                    b = 2k·W²/(ρS)
                                                    P_η = (P/W)·m·η_prop
V_a      = min(V_s1·sqrt(n_max), V_C)              CS-25.335(c) / Scholz §6
V_dive   = 1.4 · V_max                             heuristic; flutter out of scope
Re       = ρ·V_cruise·MAC / μ,  μ = 1.81e-5
```
`V_x` / `V_y` are **read back** from the `best_angle_climb_vx` /
`best_rate_climb_vy` operating-point rows (`_read_vx_vy_from_ops`) — they are
`None` until the OP generator has run. `is_glider = (P/W ≤ 0)`.

### Operating points — status machine and invalidation 🟢 CONFIRMED

```
NOT_TRIMMED ──trim──► TRIMMED ──geometry/assumption change──► DIRTY
                 │                                              │
                 ├──► LIMIT_REACHED   (α/β limit, stall in turn) │
```

* **Marking.** `mark_ops_dirty(session, aeroplane_id)`
  (`invalidation_service.py:26-36`) sets `status='DIRTY'` for every OP **not
  already** `DIRTY`/`COMPUTING`.
* **Triggers.** SQLAlchemy `after_insert/update/delete` listeners on
  `WingModel`, `WingXSecModel`, `FuselageModel` (registered **twice** — once in
  `stability_events.py`, once in `avl_geometry_events.py`) each mark their own
  table dirty, call `mark_ops_dirty`, and publish `GeometryChanged`.
* **Handlers.** `GeometryChanged` → `job_tracker.schedule_retrim` **and**
  `schedule_recompute_assumptions`. `AssumptionChanged` → retrim only for
  `_OP_AFFECTING_PARAMS = {mass, cg_x}`, recompute only for
  `_RECOMPUTE_TRIGGERING_PARAMS = {target_static_margin, mass}`. `cg_x`, `cd0`
  and `cl_max` are deliberately excluded from the recompute set to break the
  `recompute → AssumptionChanged(cg_x) → recompute` loop. 🟢 CONFIRMED
* **Retrim.** `retrim_dirty_ops(aeroplane_id)` (`retrim_service.py:53-158`)
  opens its **own** `SessionLocal` (it runs outside a request, so it owns the
  commit/rollback), finds the first TED whose `role ∈ _PITCH_ROLES =
  {elevator, stabilator, elevon, ruddervator}`, and for each DIRTY OP:
  `COMPUTING` → `trim_with_aerobuildup(Cm = 0)` → `TRIMMED` (writing the
  deflection into `control_deflections`) or `LIMIT_REACHED`. A
  `ValidationDomainError`/Pydantic error marks the row `INVALID` with a warning
  (retrying cannot fix a corrupt row); any other exception reverts to
  `NOT_TRIMMED`. When at least one OP trimmed, stability is recomputed from the
  first trimmed OP. **No pitch control ⇒ every OP stays DIRTY forever**, logged
  as a warning.

**R11 — Trim consistency (gh-577).** `resolve_operating_point`
(`operating_point_resolver.py:138-213`) is the guard that makes a
Trefftz/streamline run reflect one coherent trim state. With no
`operating_point_id` the inline schema passes through (explicit
diagnostic/manual mode). With an id: the row is loaded **constrained to
`aircraft_pk`** (prevents cross-aeroplane OP injection), must have status
`TRIMMED` unless `require_trimmed=False`, and is converted by
`operating_point_model_to_schema` — the single place where two easily-forgotten
translations happen:

* `alpha` / `beta` are stored in **radians** on the model and converted to
  **degrees** for the schema and every `asb.OperatingPoint` consumer.
* `_pick_deflections`: a non-empty `control_deflections` (manual override) wins;
  otherwise `controls` (the trim solver's output) is used. An **empty** override
  dict is treated as a no-op so it cannot silently erase a fresh trim.
* `_require_field` raises rather than substituting `0.0` for a NULL NOT-NULL
  column.

**R12 — Deflection-name validation.** `validate_deflections_against_airplane`
exists because `Airplane.with_control_deflections` **silently drops** unknown
keys: a renamed surface would let the wing run clean while the UI labelled the
plot "trimmed". The validator raises a 422 listing unknown vs available names.
It is called from the streamline, four-view, strip-force and AeroBuildup-trim
paths.

**R13 — AeroBuildup trim** (`aerobuildup_trim_service.py`). Brent root-find
(`scipy.optimize.brentq`, `xtol=1e-6`, `maxiter=50`) on
`residual(δ) = coeff(δ) − target`, one `AeroBuildup.run_with_stability_derivatives()`
per evaluation. If `f(lower)·f(upper) > 0` the root is not bracketed and the
service returns `converged=False` with a detailed warning **instead of raising**.
Name resolution accepts the tagged name, the display name, or a role name — a
role resolves to that surface's **primary (pitch/lift) axis** because
AeroBuildup can only trim the symmetric axis (gh-772).

### Trim enrichment 🟢 CONFIRMED

`compute_enrichment` (`trim_enrichment_service.py:380-572`) is the single entry
point for all three trim paths.

```
usage_fraction = |δ| / (max_pos if δ ≥ 0 else max_neg)      default limits (25, 25)
> 0.95 → critical "near mechanical limit"
> 0.80 → warning  "surface may be undersized"
trim_score > 0.5 → critical "failed to converge";  > 0.1 → warning
LIMIT_REACHED    → critical "optimizer hit a constraint boundary"
static_margin = −Cm_a / CL_a
  ≤ 0    → critical (statically unstable)
  < 0.05 → warning  (marginal)
  > 0.30 → warning  (very nose-heavy)
aerobuildup + mixed surfaces → warning: roll/yaw of mixed surfaces is AVL-only
```
gh-863 reports **every** geometry surface, not only the trimmed one:
`surface_deflections = dict.fromkeys(limits, 0.0)` updated with `controls`.

`decompose_dual_role` reconstructs physical left/right angles from the two
control variables of a mixed surface:

```
d_sym  = mix_gain_primary   · δ_primary        (pitch / lift axis)
d_anti = mix_gain_secondary · δ_secondary      (roll / yaw axis)
right  = d_anti ; left = −d_anti
whichever side is negative is scaled by differential_ratio (up-going side)
deflection_left/right = d_sym + left/right     # differential never scales d_sym
```

### Geometry emission — `repr()` *is* the file format 🟢 CONFIRMED

`app/avl/geometry.py` is a dataclass hierarchy where every `__repr__` emits its
AVL block, so `repr(AvlGeometryFile(...))` produces the complete `.avl` text.

```
AvlGeometryFile(title, mach, symmetry, reference, surfaces[], bodies[], cdp)
├── AvlSymmetry(iy_sym, iz_sym, z_sym)
├── AvlReference(s_ref, c_ref, b_ref, xyz_ref)
├── AvlSurface(name, n_chord, c_space, [n_span, s_space], [COMPONENT],
│              [YDUPLICATE], [SCALE], [TRANSLATE], [ANGLE],
│              [NOWAKE|NOALBE|NOLOAD], [CDCL], sections[])
│   └── AvlSection(xyz_le, chord, ainc, [n_span, s_space],
│                  airfoil, [CLAF], [CDCL], controls[], designs[])
│       ├── AvlNaca(digits) | AvlAfile(filepath) | AvlAirfoilInline(name, coords)
│       ├── AvlCdcl(cl_min cd_min  cl_0 cd_0  cl_max cd_max)
│       └── AvlControl(name, gain, xhinge, xyz_hvec, sgn_dup)
└── AvlBody(name, n_body, b_space, bfile, …)
```
`CDp` is emitted only when non-zero (`math.isclose(cdp, 0, abs_tol=1e-12)`).

**R1 — NACA vs AFIL routing (gh-588).** `_NACA_RE = ^naca\s*(\d{4,5})$` matches
**integers only**. The earlier `\d{4,5}(?:\.\d+)?` over-matched and routed
`naca23013.5` into an `AvlNaca`, crashing AVL with `Read error on line N`.
Decimal-bearing names are custom `.dat` files and fall through to
`_resolve_airfoil_reference` → `AvlAfile`; the last resort is `AvlNaca("0012")`.

**R2 — `CLAF = 1 + 0.77 · max_thickness`** per section, computed from the ASB
airfoil; defaults to `1.0` when the airfoil cannot be built.

**R3 — CONTROL duplication.** `_build_controls_for_wing` appends each xsec's
control(s) to sections `i` **and** `i+1`, replicating what ASB does, so AVL
interpolates the deflection across the panel strip. A dual-role surface emits
**two** CONTROL variables per section (primary symmetric `SgnDup=+1`, secondary
antisymmetric `SgnDup=−1`).

**R4 — Cross-surface name uniqueness is asserted.** AVL silently collapses
identically-named CONTROL variables into a single DOF (avl_doc 778-789), which
would couple unrelated surfaces. `build_avl_geometry_file` dedups **per
surface** (panel duplication legitimately repeats a name inside one surface)
and then calls `assert_unique_control_names` across surfaces, raising
`ValueError` on a collision. 🟢 CONFIRMED

### gh-772 — role → control-axis decomposition 🟢 CONFIRMED

`control_surface_mixing.py` is the single source of truth shared by the AVL
builder, the ASB airplane builder and the enrichment service.

```
_DUAL_ROLE_AXES = { elevon:      (pitch, roll),
                    flaperon:    (lift,  roll),
                    ruddervator: (pitch, yaw)  }
PRIMARY_AXES   = {pitch, lift}     # symmetric      SgnDup = +1
SECONDARY_AXES = {roll, yaw}       # antisymmetric  SgnDup = −1

name = f"[{role}]{axis}_{sanitize(wing_key)}_{xsec_index}"
       e.g. "[ruddervator]pitch_htail_1"
```
Single-axis roles keep their existing tagged name and `±1` sign. The secondary
axis carries `deflection = 0.0` so the AeroBuildup fallback never feeds a
roll/yaw deflection into the single-axis ASB model. `SgnDup` is a **sign flag,
never a differential magnitude** — differential is a reporting-only kinematic
applied in enrichment.

### Panel spacing heuristics 🟢 CONFIRMED

`optimise_surface_spacing` (`app/avl/spacing.py:71-106`) starts from
`SpacingConfig` (`n_chord=12`, `c_space=1.0`, `n_span=20`, `s_space=1.0`,
`auto_optimise=True`) and, when auto-optimising, applies three rules:

1. **Control surfaces present** → `n_chord = max(n_chord, 16)` (hinge-line
   resolution).
2. **Unswept** (`atan2(Δx, sqrt(Δy²+Δz²)) < 5°`) **and no centreline break**
   (no interior section at `|y| < 1e-6`) → `s_space = −2.0` (−sine: panels
   concentrated at root and tip where the induced-drag gradient is steepest).
3. **Tight section density (gh-590)** →
   `n_span = max(n_span, ceil(span / min_gap) + 2)`. AVL otherwise aborts with
   `Cannot adjust spanwise spacing at section N` /
   `Insufficient number of spanwise vortices`. Coincident sections
   (chord/twist discontinuities at the same `y`, gap ≤ 1e-9) are excluded from
   `min_gap` so they cannot force `n_span → ∞`.

### CDCL injection 🟢 CONFIRMED

`inject_cdcl(avl_file, plane_schema, operating_point, cdcl_config)` walks
surfaces and sections **in parallel index order** and mutates in place:

* a section whose `cdcl` is present and **not** all-zero is **preserved**
  (user-edited values win);
* `Re = V · chord / ν(altitude)` (`compute_reynolds_number`, ASB `Atmosphere`);
* `NeuralFoilCdclService.compute_cdcl` fits a **3-point polar** from a NeuralFoil
  α sweep: point 2 at `argmin(CD)` (drag bucket), point 3 at `argmax(CL)`
  (positive stall), point 1 at `argmin(CL)` (negative stall) — in AVL's
  `CL1 CD1  CL2 CD2  CL3 CD3` order;
* the polar is cached with `@lru_cache(maxsize=128)` keyed on hashable
  primitives only (airfoil **name**, Re, mach, α range, model size, `n_crit`,
  `xtr_upper/lower`, `include_360_deg_effects`);
* NaN/Inf from NeuralFoil ⇒ a logged warning and an **all-zero** CDCL.

A surface/wing count mismatch only logs a warning and truncates — injection can
be silently incomplete. 🟡 INFERRED risk.

`CdclConfig` defaults: `alpha_start/end/step`, `model_size="large"` (note: the
airfoil backfill uses `"xxxlarge"`), `n_crit`, `xtr_upper/lower`,
`include_360_deg_effects`.

### AVLRunner — the subprocess lifecycle 🟢 CONFIRMED

`_build_keystrokes` (`avl_runner.py:111-175`) emits, in order:

```
OPER
m  →  mn <mach>, v <V>, d <ρ>, g 9.81, <blank>
a a <alpha>   b b <beta>
r r <p·b/2V>  p p <q·c/2V>  y y <r·b/2V>       # non-dimensional rates
d1 d1 <δ1>    d2 d2 <δ2> …                     # build_control_deflection_commands
<extra keystrokes>                             # trim constraints
x                                              # execute
st <output.txt> o                              # write stability file, overwrite
[fs]                                           # strip forces to stdout
quit
```
`V = 0` with non-zero rates logs a warning and zeroes the rates.
`build_control_deflection_commands` replaces ASB's hard-coded `d1 d1 1`: it
walks `wings → xsecs → control_surfaces`, keeps the **first occurrence** of each
name, applies overrides by name, and emits `d{i} d{i} {δ}` in that order — the
same order `get_control_surface_index_map` assigns 1-based indices, so the two
never drift. Symmetric pairs share one ASB name and therefore collapse to **one**
AVL d-index (gh-529 YDUPLICATE dedup); their `SgnDup` comes from
`build_yduplicate_sign_map` (`symmetric=True → +1`, else `−1`).

Execution (`run`, l.280-368): write `airplane.avl` into a
`TemporaryDirectory` (or a caller-supplied `working_directory`), spawn
`[avl_command, "airplane.avl"]` with piped stdio, `communicate(input, timeout)`;
a `TimeoutExpired` kills the process and raises
`RuntimeError("AVL timed out after Ns")`; a missing `output.txt` raises
`FileNotFoundError` including the first 500 chars of stdout as a hint. A
non-zero return code is only **logged**. 🟡 INFERRED — AVL routinely exits
non-zero, so this is deliberate leniency.

`parse_stability_output` (l.41-83) re-implements
`asb.AVL.parse_unformatted_data_output`: scan for `" = "`, read the key
backwards and the value forwards to the next space/newline, `float()` or `NaN`,
**first occurrence wins**.

`_post_process_results` (l.177-257) then:

```
lowercase Alpha/Beta/Mach ; strip the "tot" suffix (CLtot → CL, Cl'tot → Cl')
p = (pb/2V)·2V/b     q = (qc/2V)·2V/c     r = (rb/2V)·2V/b
L = q·S·CL   Y = q·S·CY   D = q·S·CD
l_b = q·S·b·Cl   m_b = q·S·c·Cm   n_b = q·S·b·Cn
"Clb Cnr / Clr Cnb"  (spiral parameter; NaN on ZeroDivisionError)
F_w = [−D, Y, −L] → F_b → F_g  and  M_b → M_g, M_w   via op.convert_axes
```

### Strip-force parsing 🟢 CONFIRMED

`parse_strip_forces_output` (`avl_strip_forces.py:127-147`) is a line state
machine over AVL's `FS` stdout:

* `Surface\s+#\s*(\d+)\s+(.*)` opens a new surface dict;
* `# Chordwise = N  # Spanwise = M` and `Surface area  Ssurf = X` fill metadata;
* a header line starting with `j` and containing `Xle` **and** `cl` turns on
  table mode; subsequent lines starting with a digit are split into the 15

byte-for-byte what `vlm_strip_forces` mimics, so `_strip_surfaces_from_result`
consumes either unchanged.

### Design assumptions — the ESTIMATE / CALCULATED duality 🟢 CONFIRMED

Every parameter has **two** values and an active selector:

```
effective_value = calculated_value  if active_source == "CALCULATED" and it exists
                  else estimate_value
divergence_pct  = |estimate − calculated| / |calculated| · 100
divergence_level: <5 none · <15 info · ≤30 warning · else alert
```
17 parameters are seeded from `PARAMETER_DEFAULTS`
(`app/schemas/design_assumption.py:72-108`). Seven of them are
`DESIGN_CHOICE_PARAMS` — pure user choices that **never** receive a calculated
value and can never be switched to `CALCULATED`:
`target_static_margin`, `g_limit`, `battery_capacity_wh`,
`battery_specific_energy_wh_per_kg`, `propulsion_eta_motor`,
`propulsion_eta_esc`, `motor_continuous_power_w`.

**R1 — Auto-switch on first calculation.** `update_calculated_value(...,
auto_switch_source=True)` flips `active_source` to `CALCULATED` **only** on the
first calculated value (`row.calculated_value is None`), only from `ESTIMATE`,
and never for a design choice. Afterwards the user's manual choice sticks.

**R2 — Events fire only when the effective value actually changes.**
`update_assumption` publishes `AssumptionChanged` (and marks OPs dirty for
`mass`/`cg_x`) **only** when `active_source == "ESTIMATE"` — editing an estimate
while the calculated value is active changes nothing effective, so the retrim
chain must not fire. `switch_source` always fires, and additionally schedules a
recompute for every parameter **except `cg_x`** (which is the recompute's own
output — scheduling it would loop).

**R3 — `seed_defaults` is idempotent and also seeds
`aircraft_computation_config`.** `recompute_assumptions` calls it
unconditionally because wings can be created before the user ever opens the
Assumptions tab.

`aircraft_computation_config` is per-aircraft sweep tuning stored in its own
table so the surface can grow without churning `aeroplanes`:
`coarse_alpha_min/max/step_deg = −5 / 25 / 1`, `fine_alpha_margin_deg = 5`,
`fine_alpha_step_deg = 0.5`, `fine_velocity_count = 8`, `debounce_seconds = 2.0`.

### Mission objectives and presets 🟢 CONFIRMED

`mission_objectives` is **one row per aeroplane** (unique FK) holding seven
performance targets plus the field-performance inputs migrated out of
assumptions (`available_runway_m`, `runway_type`, `t_static_N`,
`takeoff_mode`) and the optional gh-477 landing inputs (`landing_surface`,
`landing_safety_factor`, `available_field_length_m`).

**R4 — Changing `mission_type` rewrites estimates, never calculations.**
`upsert_mission_objective` → `_apply_preset_estimates` writes the preset's
`suggested_estimates` (`g_limit`, `target_static_margin`, `cl_max`,
`power_to_weight`, `prop_efficiency`) into
`design_assumptions.estimate_value` only — `calculated_value`,
`calculated_source` and `active_source` stay owned by
`assumption_compute_service`. An unknown `mission_type` is a **silent no-op**.

`mission_presets` is a seeded library (`SEED_PRESETS`, idempotent
`seed_mission_presets`) of nine entries: `trainer`, `sport`, `sailplane`,
`wing_racer`, `acro_3d`, `stol_bush`, `slope_soarer`, `motor_glider`,
`flying_wing`. Each carries a `target_polygon` (0–1 score per axis), the
`axis_ranges` used to normalise real values onto that 0–1 scale, and the
`suggested_estimates`. The seven axes are `stall_safety`, `glide`, `climb`,
`cruise`, `maneuver`, `wing_loading`, `field_friendliness`.

### RC flight profiles 🟢 CONFIRMED

`rc_flight_profiles` is a **global library** (unique `name`), optionally
assigned to an aeroplane via `aeroplanes.flight_profile_id`. Four JSON blobs:
`environment` (`altitude_m`, `wind_mps`), `goals`, `handling`, `constraints`.

`_load_effective_flight_profile` returns `(profile_dict, source_profile_id)`;
with no assignment it returns `_default_profile()` and `source_profile_id=None`.
That `None` is load-bearing:

* `_load_flight_profile_speeds` reports `user_set_cruise=False`, so
  `recompute_assumptions` **replaces** the cruise speed with `V_md` (best L/D =
  best range for a prop aircraft) and flags `v_cruise_auto=True`;
* `_resolve_cruise_speed_with_md_fallback` in the OP generator does the same
  from the cached context.

`v_max` fallback when the profile sets no `max_level_speed_mps`:
`max(1.35·V_cruise, V_cruise + 8)`.
Profile deletion is refused (409) while any aircraft still references it.

### Operating-point generation — the sizing sweep 🟢 CONFIRMED

`_build_target_definitions` produces **15 targets** from the profile goals and
the reference stall speeds:

| Target | config | velocity |
|---|---|---|
| `stall_near_clean` | clean | `min_speed_margin_vs_clean (1.20) · V_s1` |
| `takeoff_climb` | takeoff | `takeoff_speed_margin_vs_to (1.25) · V_s_to`, flap 15° |
| `best_angle_climb_vx` | clean | `max(1.35·V_s1, 0.85·V_cruise)` |
| `best_rate_climb_vy` | clean | `max(1.50·V_s1, 0.95·V_cruise)` |
| `cruise` | clean | `V_cruise` |
| `loiter_endurance` | clean | `max(1.15·V_s1, 0.80·V_cruise)` |
| `max_range` | clean | `max(1.25·V_s1, 0.95·V_cruise)` |
| `max_level_speed` | clean | `V_max` |
| `approach_landing` | landing | `approach_speed_margin_vs_ldg (1.30) · V_s0`, flap 30° |
| `stall_with_flaps` | landing | `max(2.0, 1.05·V_s0)`, flap 30° |
| `turn_20 / 40 / 60` | clean | `max(V_cruise, 1.3·V_s1)`, `n = 1/cos φ` |
| `dutch_role_start` | clean | `max(V_cruise, 1.3·V_s1)`, β = 2° |

**R5 — Stall speeds come from physics, not from 0.95/0.90.**
`_estimate_reference_speeds` prefers `v_s1_mps` / `v_s_to_mps` / `v_s0_mps`
from the cached context (`provenance="polar"`); with only the legacy
`v_stall_mps` it uses the clean value for all three configurations — the
historical 0.95 / 0.90 multipliers are **deliberately not applied** (audit
§5.5). With no context at all it falls back to
`max(3.0, V_cruise / min_speed_margin_vs_clean)` with
`provenance="cold_start"`, and `_stamp_stale_no_polar` appends a
`STALE_NO_POLAR` warning to **every** target so the persisted OPs carry the
audit trail. Floors: `vs_clean ≥ 3.0`, `vs_to ≥ 2.5`, `vs_ldg ≥ 2.0`.

**R6 — Flap targets are clipped to the real TED limit (gh-527/gh-536).**
`_clip_flap_to_ted_limit` clips `flap_deflection_deg` to the **most
restrictive** flap-role TED (`min` across all of them, so the smallest surface
never over-deflects) and appends `FLAP_DEFLECTION_CLIPPED`. With no flap-role
TED in the geometry no limit is manufactured — the target passes through and
the trim solver no-ops the missing surface. AVL has no internal hinge clamp and
NeuralFoil silently extrapolates τ(x_h/c) past its training range, so an
unclipped target produces over-attached flow with no warning.

**R7 — Capability gating.** `_detect_control_capabilities` walks the ASB
airplane's `[role]` tags into `{has_pitch_control, has_roll_control,
has_yaw_control, has_flap, available_controls}` using
`PITCH_ROLES = {elevator, stabilator, elevon, ruddervator}`,
`ROLL_ROLES = {aileron, elevon, flaperon}`,
`YAW_ROLES = {rudder, ruddervator}`, `FLAP_ROLES = {flap}`.
Targets are skipped (not failed) when their requirement is unmet:
`turn_*` needs roll **or** yaw, `dutch_role_start` needs yaw,
`stall_with_flaps` needs a flap.

**R8 — Two-stage trim solve.**

```
stage 1  asb.Opti (IPOPT), max_iter=120, max_runtime=0.35 s,
         behavior_on_failure="return_last"
         variables: α ∈ [−8°, max_alpha_deg]; pitch δ ∈ [−25, 25];
                    (turn) roll δ ∈ [−20, 20]; (turn/dutch) yaw δ ∈ [−25, 25]
         objective: 50·Cm² + 3·CY² [+ 15·(CL − CL_target)²]
                    [+ 2·Cl² + 2·Cn² for turns] + 0.001·Σδ²
stage 2  if score > 0.35: grid search over
         velocities × α = linspace(−4°, 20°, 13) × β candidates,
         velocity factors [1.0, 1.05, 1.10, 1.15]  (or descending for max_level_speed)
         → the grid fallback updates BOTH α and the velocity (gh-528)

trim_score = |Cm| + 0.5·|CY| [+ 0.3·|CL − CL_target|]
CL_target  = m·g·n / (q·S_ref)
status     = TRIMMED if score < 0.35 else NOT_TRIMMED
             LIMIT_REACHED when |α| > max_alpha_deg or |β| > max_beta_deg
```
`trim_method` is `"opti"` or `"grid_fallback"` — gh-627: the solver path lives
on `trim_method`, **never** in `trim_residuals`, which is typed
`dict[str, float]` and Pydantic-rejects strings (a `best_residuals["solver_path"]
= "opti"` line once broke every OP enrichment).

**R9 — Turn kinematics and feasibility.** A `bank_deg` target derives
`(p, q, r)` from `turn_kinematics`; `_apply_turn_feasibility` marks the point
`LIMIT_REACHED` with `STALL_IN_TURN` when
`V < V_s1 · sqrt(n)`, `n = 1/cos φ` — otherwise the trimmer would happily
return a solution at the wrong load factor.

**R10 — Parallelism (gh-867).** The CasADi/IPOPT solve does **not** release the
GIL (a thread pool benchmarked at 0.35–0.89×), so the **streaming** generation
path uses a bounded `ProcessPoolExecutor` (spawn context,
`max_workers = max(1, min(4, cpu−1))`) with BLAS pinned to one thread per worker
(`OMP/OPENBLAS/MKL/VECLIB/NUMEXPR_NUM_THREADS=1`, applied both to the parent env
at spawn and in the initializer, then restored) → ≈ 2.9× at 4 workers. Workers
receive a picklable `_WorkerSolveCtx` (the `asb.Airplane` pickles cleanly; the
SQLAlchemy model does not, so only `total_mass_kg` is carried via
`_AircraftMassOnly`) and **never touch the database**. The main thread owns
persistence and streams results in `as_completed` order. The non-streaming batch
path stays **sequential** on purpose so its contract and its mocks are unchanged.

**R11 — SSE contract (gh-865).** `POST /aircrafts/{uuid}/operating_points/generate_default/stream`
emits `targets` → one `op` per solved point → `done`, with `skip` for
capability-filtered targets and `error` for setup failures. Each OP is
committed as soon as it is solved, so a dropped connection still leaves a valid
partial set.

Persistence: `_persist_point_set` optionally clears **all** existing OP sets and
OPs for the aircraft, inserts one `operating_points` row per solved point with
`xyz_ref = [design_cg_x, 0, 0]`, then one `operating_pointsets` row named
`default_operating_point_set` whose `operating_points` JSON column holds the id
list.

### Flight envelope — V-n and gust 🟢 CONFIRMED

`compute_vn_curve` (`flight_envelope_service.py:283-368`) — 60 points from
`V_stall` to `V_dive`:

```
V_stall = sqrt(2·W / (ρ·S·CL_max));   V_dive = 1.4·V_max;   CL_min = −0.8·CL_max
n⁺(V) = min(q·S·CL_max / W,  g_limit)
n⁻(V) = max(q·S·CL_min / W, −0.4·g_limit)
```

Gust envelope — Pratt-Walker discrete sharp-edged gust (NACA TN 2964),
`K_g` per FAR-25.341(a)(2) / CS-VLA.333:

```
c̄    = S_ref / b_ref            # MEAN GEOMETRIC chord, NOT the MAC
μ_g  = 2·(W/S) / (ρ · c̄ · CL_α · g)
K_g  = 0.88·μ_g / (5.3 + μ_g)
Δn   = ½·ρ·V·CL_α·U_gust·K_g / (W/S)
n± = 1 ± Δn        over 60 points from V_stall to V_dive
U_gust: 15.24 m/s (50 ft/s) at V ≤ V_C = V_D/1.4,
        linearly tapered to 7.62 m/s (25 ft/s) at V_D
CL_α : context["cl_alpha_per_rad"] → else Helmbold-Diederich 2π·AR/(AR+2)
```
Explicitly **not** the thin-airfoil `2π` limit, which overestimates `CL_α` at
AR = 6 by ≈ 39 % and inflates gust loads.

Two structured warning types are emitted to the API (not just the log):
`GustCriticalWarning` at the first `V` where `1+Δn > g_limit` (or
`1−Δn < −0.4·g_limit`) — the structure is gust-sized, not manoeuvre-sized — and
`GustValidityWarning` when `μ_g ∉ [3, 200]`, which is the **normal** case for
low-W/S RC models (gh-497), so their gust loads may be optimistic.

`derive_performance_kpis` always returns exactly six KPIs with an explicit
confidence ladder:

```
best_ld_speed / min_sink_speed:
  1. TRIMMED operating-point marker      confidence "trimmed"
  2. ctx["v_md_mps"] / ctx["v_min_sink_mps"]   confidence "computed"
  3. 1.4·V_s / 1.2·V_s                   confidence "estimated"   ← cold start only
stall_speed, max_speed, dive_speed (=1.4·V_max), max_load_factor → "limit"
```
The heuristic tier is documented as wrong by up to 15 % for high-AR airframes
(gh-475 audit §4.1) and is kept only for the pre-polar case.

`flight_envelopes` is upserted (one row per aeroplane) with the serialised
`vn_curve_json`, `kpis_json`, `markers_json` and an `assumptions_snapshot`
(`mass`, `cl_max`, `g_limit`). 🔴 GAP — markers are all written at
`load_factor = 1.0` because the stored OP carries no CL, so turn OPs plot on the
1-g line.

### Loading scenarios and the CG envelope 🟢 CONFIRMED

`loading_scenarios` is a named CG loadout per aeroplane; the min/max CG across
all scenarios is the **Loading-Envelope**, which must sit inside the
**Stability-Envelope**.

```
SM classification (Scholz §4.2), thresholds in loading_scenario_service.py:51-53
  sm < 0.02          → "error"  (Phugoid divergent)
  sm < target_sm     → "warn"
  sm ≤ 0.20          → "ok"
  sm ≤ 0.30          → "warn"  (heavy nose, trim drag)
  else               → "error" (elevator authority)

compute_stability_envelope(x_np, mac, target_sm):
  cg_stability_aft_m = x_np − target_sm · MAC
  cg_stability_fwd_m = x_np − 0.30 · MAC          ← conservative STUB
```
The 0.30·MAC forward stub is **overridden** in `recompute_assumptions` by
`elevator_authority_service.compute_forward_cg_limit` (gh-500); on failure the
stub is kept and the full `forward_cg_result` (confidence, warnings) is stored
in the context either way. A `ValueError` mentioning `x_np=None` / `mac=None`
is demoted to INFO — it is the documented cold-start chicken-and-egg on the
first recompute (gh-685), not a bug.

`compute_scenario_cg` supports four override types — toggles (`enabled=False`
removes the component), mass overrides, position overrides, and additive adhoc
items — over a per-component list, falling back to a `base_mass_kg /
base_cg_x` aggregation for pre-migration aeroplanes.

`enrich_context_with_cg_envelope` adds, **additively** (never disturbing
`cg_agg_m`): `cg_forward_m`, `cg_aft_m`, `sm_at_fwd = (x_np − cg_fwd)/MAC`,
`sm_at_aft`, `cg_stability_fwd_m`, `cg_stability_aft_m`. When `x_np`/`MAC` are
absent the SM values are stored as `None` rather than as deceptive stubs.

### Landing field length (gh-477) 🟢 CONFIRMED

`_compute_landing_field_length` (`assumption_compute_service.py:1797-1848`):

```
V_S0    = sqrt(2·m·g / (ρ·S·CL_max_landing))
V_TD    = 1.15 · V_S0                              # RC rule of thumb
s_ground = V_TD² / (2·g·μ_eff)                     # energy balance; mass cancels
L_landing = safety · (15 m flare + s_ground)
net_recovery → s_ground = 0 (catch/arrester); L collapses to the padded flare

LANDING_SURFACE_MU = grass_short 0.15 · grass_long 0.22 · hard_paved 0.07
                     soft_soil 0.30 · belly_grass 0.40 · net_recovery 0.0
defaults: surface grass_short, safety 1.5 (rejected below 1.0)
```
The result is compared against `mission_objectives.available_field_length_m`
into a tri-state `landing_field_sufficient` (`True`/`False`/`None`) so the UI
can render green/red/neutral. Provenance note in code: these μ values come from
operational RC/UAV practice (Raymer ch. 17 / Roskam P.7 territory), **not** from
Anderson.

### Matching chart — T/W vs W/S 🟢 CONFIRMED

`matching_chart_service.py` implements the classical Loftin/Scholz §5.2–5.4
constraint diagram over `W/S ∈ [10, 1500] N/m²` in 200 steps, with
`T/W = T_static_SL / W_MTOW`. The Loftin/Roskam constants are **imported** from
`field_length_service` (`_K_TO_50FT = 1.66`, `_K_LDG_50FT = 2.73`,
`_K_LDG_HARD = 0.5847`, `_C_TO = 1.21`) rather than re-declared, explicitly to
prevent drift.

```
takeoff (line)      T/W = C_TO·K_TO_50FT·(W/S) / (ρ·g·CL_max_TO·s_TO_50ft)
                    s_runway = 0 → 0  (hand launch: no constraint)
landing (vertical)  W/S_max = s_LDG_50ft·ρ·CL_max_LDG / (K_LDG_HARD·K_LDG_50FT)
cruise  (line)      T/W = q·CD0/(W/S) + (W/S)·k/q          k = 1/(π·e·AR)
climb   (line)      T/W = sin γ + [q·CD0/(W/S) + (W/S)·k/q]   (clean polar)
stall   (vertical)  W/S_max = ½·ρ·V_s_target²·CL_max_clean    (CLEAN, not landing)
V_md                = sqrt(2·(W/S) / (ρ·sqrt(CD0/k)))
```

gh-613 Phase B adds five **RC-additive** constraints and a per-profile
applicability table (`_PROFILE_CONSTRAINT_MAP`), so a sailplane is not
evaluated against a takeoff-field constraint:

| Profile | Applicable constraints |
|---|---|
| `trainer` | stall, climb, power_loading, wcl |
| `sport` | stall, climb, mission_min_tw, power_loading, wcl |
| `wing_racer` | stall, cruise, power_loading |
| `acro_3d` | stall, mission_min_tw, power_loading, vertical_climb |
| `stol_bush` | stall, takeoff, landing, climb |
| `slope_soarer` / `glider` / `sailplane` | stall |
| `motor_glider` / `flying_wing` | stall, climb, cruise |
| `custom` / unknown | **all** (back-compat) |

```
mission_min_tw   acro_3d 1.5 (hover) · wing_racer 0.8 · sport 0.5
power_loading    T/W ≥ (P/m)·η_prop / (g·V_climb),  V_climb = 1.3·V_stall
                 P/m: trainer 125 · sport 200 · wing_racer 275 · acro_3d 400 W/kg
vertical_climb   T/W ≥ 1 + D/W                       (acro/3D)
wcl (vertical)   Lennon wing-cube-loading upper bound, lb/ft^4.5 → SI ×47.88,
                 W/S_max = (WCL·47.88)^(2/3) · AR^0.25
hand_launch      W/S ≤ 80 N/m²   (only when mode == rc_hand_launch)
```
Mode defaults (`s_runway`, `γ_climb`, `V_s_target`): `rc_runway` 50 m/5°/7 m/s,
`rc_hand_launch` 0/5°/7, `uav_runway` and `uav_belly_land` 200 m/4°/12,
`ga_runway` 500 m/1.5°/27.7 (FAR-23.65 / 54 kt). An unknown mode logs a warning

Feasibility: a line constraint binds within 3 % in T/W, a vertical constraint
within 5 % in W/S. `DEFAULT_E_OSWALD = 0.8` exists but the module documents

### Reynolds-banded polar table (gh-493) 🟢 CONFIRMED

`build_re_table` re-bins the **existing** fine-sweep samples into V-bands —
no extra AeroBuildup calls (marginal cost ≤ 200 ms for three OLS fits).

```
Re_aircraft = ρ·V·MAC_main / μ            (ISA SL, μ = 1.81e-5) — a LABEL for
                                           V-based lookup, not an ASB parameter
anchors  = [max(0.5·V_cruise, 3.0),  V_cruise,  min(max(1.3·V_cruise, V_max), V_sweep_max)]
bands    = midpoints between anchors, edges extended by 50 % of the adjacent gap
degeneracy: Re_max/Re_min < 2.5 → single-row fallback, degenerate = True
per band: ≥ 6 samples required, else a fallback row
lookup cd0: LINEAR IN 1/sqrt(Re)          Blasius/Schlichting  cf ∝ Re^(−1/2)
lookup e  : constant MEAN over non-fallback rows (Hepperle/Drela: e is
            insensitive to Re at subsonic speed); extrapolation clamps + warns
```
`_FALLBACK_E_OSWALD = 0.8` is the last resort — gh-924 made `lookup_e_oswald_at_v`
prefer **any** `e` present on the table first, because `recompute_assumptions`
backfills the fallback rows with the authoritative Trefftz `e`.

### Error policy 🟢 CONFIRMED

`recompute_assumptions` is deliberately layered:

* **fatal** — an AeroBuildup failure in the stability run / coarse sweep / fine
  sweep logs and **returns** without writing anything (the previous context
  stays valid).
* **degraded** — per-configuration takeoff/landing polars each sit in their own
  `try` (a takeoff failure must not block the physically independent landing
  pass) and fall back to a clone of the clean polar with
  `provenance="aerobuildup_failed"`; the Re-table, the turbulator ΔCD0, and the
  elevator-authority forward-CG limit are all non-fatal with named fallbacks.
* **guarded** — a schema/ASB **flap-name parity mismatch** (the model reports a
  flap TED but the ASB conversion produced no flap-role control surface) routes
  to the no-flap fallback with an explicit "investigate the converter" warning

# Cluster D — mass, powertrain & versioning

Modules covered: `mass-and-balance`, `powertrain`, `versioning`.

Three cross-cutting rules govern this cluster:

1. **Mass is a design *assumption*, never a raw sum.** The aircraft mass lives
   in `design_assumptions.parameter_name = "mass"` with the ESTIMATE /
   CALCULATED duality described in *Cluster C — mission-and-sizing*. Both mass
   producers (`weight_items` and the component tree) write only the
   **CALCULATED** side via `update_calculated_value(..., auto_switch_source=True)`;
   the user can always flip back to ESTIMATE. A brand-new aircraft therefore
   starts from the seeded estimate `PARAMETER_DEFAULTS["mass"] = 1.5 kg` and
   only becomes bottom-up once components exist. 🟢 CONFIRMED
2. **CG is top-down, not bottom-up.** `cg_x` is *CG_aero* — the CG the
   stability analysis demands (`x_np − SM·MAC`) — and is written by
   `assumption_compute_service`. The aggregated CG from mass items (`CG_agg`)
   is **never** written back into `cg_x`; it is exposed for comparison only
   (`get_cg_comparison`, `assumption_computation_context.cg_agg_m`). gh-465
   made this explicit and `sync_weight_items_to_assumptions` carries the rule
   in its docstring. 🟢 CONFIRMED
3. **Every aeroplane row is a versioning node.** Since gh-903 there is no
   "unversioned" aircraft: `create_aeroplane` writes `root_id = self.id`,
   creates a `main` branch (`is_main=True`, `created_by='human'`) and points
   `branch_id` at it. The migration backfilled the same shape for every
   pre-existing row. 🟢 CONFIRMED (`aeroplane_service.py:61-104`,
   `alembic/versions/15f45e64a7c0_gh903_versioning_db_model.py:140-167`)

### The formulas 🟢 CONFIRMED

```
GRAVITY        = 9.81            mass_cg_service.py:20
CG_TOLERANCE_M = 0.01            mass_cg_service.py:21

W        = m · g
W/S      = W / S_ref                                     [N/m²]
V_stall  = sqrt(2·W / (ρ · S_ref · CL_max))               [m/s]
q        = ½·ρ·V²
CL_req   = W / (q · S_ref)
CL_margin= CL_max − CL_req            > 0 ⇒ above stall

CG_agg:  m_tot = Σ mᵢ
         cg_k  = Σ (mᵢ · kᵢ) / m_tot     for k ∈ {x, y, z}
         m_tot ≤ 0  ⇒  (None, None, None, None)

CG comparison:  Δx = cg_x_design − cg_x_components
                within_tolerance = |Δx| < 0.01 m
```

`compute_design_metrics` rejects every non-positive input (`mass_kg`, `s_ref`,
`cl_max`, `rho`, `velocity`) with a `ValidationError` before computing —
there is no silent clamp. `get_s_ref_for_aeroplane` additionally rejects a
zero/negative `s_ref` with the actionable message *"add wings first"*.

🟡 INFERRED — `GRAVITY = 9.81` here diverges from `G = 9.80665` used by
`endurance_service`, `powertrain_performance` and
`powertrain_solution_space_service`. The 0.007 % difference is numerically
irrelevant but it means there is no single gravity constant in the codebase.

### Two mass producers, one assumption 🟢 CONFIRMED

The `mass` design assumption has **two** writers, and they are *last-write-wins*
on the same `calculated_value` column:

| Producer | Trigger | `calculated_source` |
|---|---|---|
| `sync_weight_items_to_assumptions` | any weight-item POST/PUT/DELETE (`weight_items_service._try_sync_assumptions`) | `"weight_items"` |
| `sync_component_tree_to_mass` | any component-tree mutation (`component_tree_service._sync_aircraft_mass`) | `"component_tree"` |

Both follow the identical five-step shape:

```
1. resolve the aeroplane by UUID                       → NotFoundError
2. if no design_assumptions row named "mass" exists    → return (no-op)
3. aggregate  → total_kg  (None when the source is empty)
4. update_calculated_value(db, uuid, "mass", total_kg, source,
                           auto_switch_source=True)
5. mark_ops_dirty(aeroplane.id)  +  publish AssumptionChanged(mass)
```

Step 2 is what makes the sync safe on a freshly created aircraft that has not
been seeded yet. Step 4's `auto_switch_source=True` is the documented UX
decision: *"Mass is **always** calculated from the component tree by default …
users who want a manual override can flip the source back to ESTIMATE"*
(`mass_cg_service.py:174-186`). Step 5 is what makes a mass edit propagate —
the `AssumptionChanged` event drives retrim and the V_stall recompute in
`assumption_compute_service`.

The component-tree roll-up itself (`get_aircraft_total_weight_kg`,
`component_tree_service.py:381-403`) sums **root nodes only** (`parent_id IS
NULL`) and recurses through children, with a three-tier per-node weight ladder:

```
_calculate_own_weight(node):
  1. node.weight_override_g            → source "override"   (user wins)
  2. COTS component mass × quantity    → source "cots"
  3. CAD shape volume × material ρ     → source "calculated"
  4. otherwise                         → (None, "none")      mass unknown
total_kg = Σ roots (own + children) / 1000 ;  0 ⇒ None
```

Returning `None` (rather than `0.0`) for an empty tree is deliberate — the
caller then clears `calculated_value` instead of asserting a 0 kg aircraft.

Both call sites swallow their exceptions on purpose: `_try_sync_assumptions`
catches `NotFoundError`/`SQLAlchemyError` and `_sync_aircraft_mass` catches
`Exception` — *"a failed mass sync should NOT block the original CRUD
operation"*. The trade-off is that a persistently failing sync is invisible
except in the log.

### 🔴 GAPs

* **`compute_recommended_cg` has no caller.** The top-down CG rule
  `x_np − SM·MAC` is implemented and unit-tested here, but production reads it
  from `loading_scenario_service.compute_stability_envelope` /
  `assumption_compute_service` instead. Two implementations of the project's
  central CG rule coexist.
* **`RecommendedCGRequest` / `RecommendedCGResponse` are dead schemas.** They
  are declared in `app/schemas/mass_cg.py:8-23` but no endpoint returns them
  (`mass_cg.py` exposes only `design_metrics` and `cg_comparison`).
* **`get_effective_assumption_value` diverges from the documented single source
  of truth.** `design_assumptions_service.get_effective_assumption` falls back
  to `PARAMETER_DEFAULTS` when no row exists and returns `None`; the mass_cg
  copy raises `NotFoundError` instead. Two aircraft in the same DB can
  therefore behave differently depending on which resolver a caller picks.
* **Two mass producers overwrite one another silently.** An aircraft that has

  component, so a battery entered as a weight item and the same battery placed
  in the component tree are unrelated rows — double-counting is possible and
  undetected.
* **CG_agg ignores `y`/`z` downstream.** `aggregate_weight_items` computes all
  three axes but only `cg_x` reaches the computation context; lateral and
  vertical CG are returned by the API and then dropped.

### The component library — one table, a dynamic schema 🟢 CONFIRMED

`components` is a **single table for every hardware type**. The discriminator
is `component_type` (indexed String) and all type-specific fields live in a
JSON `specs` blob. Fixed columns are only the ones every component shares:
`name`, `manufacturer`, `description`, `mass_g`, `bbox_{x,y,z}_mm`,
`model_ref`.

The per-type contract is itself data: `component_types.schema` (mapped as
`schema_def` because `schema` collides with a Pydantic attribute name — see
`component_type.py:28`) holds a JSON list of `PropertyDefinition` objects
(`name, label, type ∈ {number,string,boolean}, unit, required, min, max,
options`). `validate_specs` (`component_type_service.py:240-271`) is called on
every `create_component` / `update_component` and enforces:

```
unknown component_type            → ValidationError ("use GET /component-types")
required property missing          → ValidationError (reason "missing_required")
number: non-numeric / bool         → ValidationError
number: < min  or  > max           → ValidationError
string / boolean: wrong python type→ ValidationError
options list present, value not in → ValidationError
unknown keys in specs              → ACCEPTED (never rejected)
```

12 types are seeded by `seed_default_types` (`:682`, idempotent, called at
startup and by the test fixture) with `deletable=False`:
`material`, `servo`, `brushless_motor`, `battery`, `esc`, `propeller`,
`receiver`, `spar_tube`, `veneer`, `strip`, `triangular_strip`,
`grooved_strip`. Of those the powertrain proper uses
`brushless_motor / battery / esc / propeller`; `servo` belongs to the wing
module and the wood/tube types to construction.

Two guards protect the taxonomy: a seeded type cannot be deleted
(`deletable=False` → 409), and any type still referenced by ≥ 1 component
cannot be deleted (409 with the reference count). `update_type` may change
`label`, `description` and `schema` but **not** `name` or `deletable`.
`_patch_schema_fields` (`:710`) additively merges newly added schema fields
onto already-seeded rows so an existing DB gains e.g. the gh-1006 `rm_ohm`
field without a rebuild.

(`"Durchmesser"`, `"Steigung"`, `"Blätter"`, `"Dauerstrom"`, `"Leerlaufstrom
Io"`, `"Halterungsdicke"`, …) while the rest of the API is English. These

### The propeller polar database 🟢 CONFIRMED

`propeller_polars` (header, keyed by `(manufacturer, name)`) +
`propeller_polar_samples` (measurement rows, cascade-deleted) hold the APC
PER3 dataset. The physics definitions are documented on the model
(`prop_polar.py:71-82`):

```
J   = V / (n·D)          advance ratio          [–]
Ct  = T / (ρ·n²·D⁴)      thrust coefficient     [–]
Cp  = P / (ρ·n³·D⁵)      power coefficient      [–]
Pe  = Ct·J / Cp          propulsive efficiency  [–]   (0 at J = 0)
plus dimensional PWR_W, Torque_Nm, Thrust_N
```

**Ingestion is a three-stage, network-free pipeline** whose durable source is a
committed snapshot, never the raw vendor files:

```
data/apc_raw/**/PER3_*.dat   (gitignored, ~58 MB)
        │  scripts/parse_apc_props.py
        ▼
data/cots/apc_props.json.gz  (committed, ~8 MB)  ← the reimport source
        │  scripts/enrich_apc_snapshot_pe0.py  (+ PE0 weight/inertia/geometry)
        ▼
        │  scripts/import_apc_props.py → prop_polar_import.import_prop_polars
        ▼
propeller_polars + propeller_polar_samples
        │  scripts/seed_propeller_components.py → prop_component_seed
        ▼
components (component_type='propeller', keyed on model_ref)
```

Parser details that matter (`scripts/parse_apc_props.py`):

* Diameter / pitch / variant come from **header line 1**, not the filename —
  that is the only way to read `PER3_105x45` as 10.5 × 4.5 in and to catch
  variant suffixes (`10x10E` → `E`, `10x10M-JK` → `M-JK`). Filename parsing is
  the logged fallback.
* Only the **SI** columns are kept (`PWR` W, `Torque` N·m, `Thrust` N) plus the
  dimensionless `J, Pe, Ct, Cp`; the imperial Hp/In-Lbf/Lbf columns are
  discarded. Column indices are fixed constants (`_COL_J=1 … _COL_THRUST_N=10`)
  and rows with `< 11` fields are skipped.
* Blade count (gh-1004): `_BLADE_COUNT_RE = -([3-9])$` on the *variant*.
  `""`→2, `"E"`→2, `"-4"`→4, `"E-3"`→3, and crucially `"M-JK"`→2 — letter
  suffixes (marine `M-JK`, `MRF-RH`, `P-LH`, `R-RH`) are **not** blade counts.
* `model_ref = "apc/<designation>"` with `.` → `p` (`10.5x4.5` → `apc/10p5x4p5`).
  This slug is the join key between polar and component.

Import semantics (`prop_polar_import.py`):

* Upsert by `(manufacturer, name)`; `component_type` must be `"propeller"` or
  the record is rejected into `ImportResult.errors`.
* `_records_equal` is a **freshness proxy, not deep equality**: it compares
  `source_version`, `source_url`, `variant` (so pre-gh-999 rows gain their
  variant) and "row lacks `weight_g` but the snapshot has one" (so the gh-1000
  PE0 enrichment is not silently skipped). The docstring states the
  limitation explicitly — *if APC corrects polar data without bumping
  `source_version` the change is skipped; run with `force=True`.*
* `_upsert_samples` **deletes all** samples for the propeller and re-inserts —
  there is no per-sample diff.

PE0 enrichment (`prop_polar_enrich.py`) matches PE0 files to snapshot records
by `(diameter, pitch, variant)` and writes `weight_g`, `inertia_kg_m2` and a
per-station `geometry` list. Its one physical guard is
`MIN_PLAUSIBLE_WEIGHT_G = 1.0`: a parsed weight below 1 g is treated as a
kg→g conversion error, **rejected** and counted in `unit_warnings` rather than
written. Unmatched PE0 rows are logged, never dropped silently.

The component mirror (`prop_component_seed.seed_propeller_components`) is
idempotent on `model_ref` and has three explicit mass rules:
`mass_g` is populated from `weight_g` on create (both are grams — no
conversion); a **NULL** `mass_g` is backfilled once the polar gains a weight;
a **non-null** `mass_g` is never clobbered (user-entered mass wins). Polars
without a `model_ref` are skipped. `component_service._resolve_polar_id`
closes the loop, so `ComponentRead` carries `has_polar` / `polar_id` — and
`list_components` batch-resolves them to avoid an N+1 query.

### Performance model — the two motor models 🟢 CONFIRMED

`powertrain_performance.compute_performance_curve` sweeps
`np.linspace(v_min, v_max, n_points)` and produces `(V, T, P_shaft, η_prop, J,
rpm, estimated)` per point. Constants: `RHO_SEA_LEVEL = 1.225`,
`G = 9.80665`, `_VOLTS_PER_LIPO_CELL = 3.7`, `_DEFAULT_ETA_MOTOR = 0.85`.

**Model A — fixed-RPM power-limited chain (gh-615, when `rm_ohm` is absent):**

```
V_bat   = cells · 3.7 V                     ← LOADED nominal, NOT 4.2 V peak
                                              (4.2 V would inflate power by 13 %)
n       = output_kv · V_bat · throttle      ← RPM is FIXED, not load-dependent
output_kv = kv_rpm_per_volt / (gear_ratio or 1)     ← gear-aware; never use raw KV
P_elec_max = min(  max_current_a · 3.7 · cells_lipo_max ,      motor limit
                   (cap_mAh/1000) · C_rate · (cells·3.7) )     battery limit
P_shaft_max = P_elec_max · η_motor          η_motor = efficiency_pct/100 else 0.85

per V:  J   = V / (n·D)
        Ct, Cp, Pe ← interpolated at J from the nearest-RPM row group
        T   = Ct·ρ·n²·D⁴                 clamped ≥ 0
        P   = clip(Cp·ρ·n³·D⁵, 0, P_shaft_max)
        η_prop = clip(Pe, 0, 1)          J-dependent — NOT a flat 0.65
        estimated = True
```

**Model B — QPROP 3-parameter torque balance (gh-1006, when `rm_ohm > 0`):**

```
Kv_si   = output_kv · 2π/60      [rad/s per volt];  Kt = 1/Kv_si   [Nm/A]
back-EMF:   ω/Kv_si = V_term − I·Rm      ⇒   I(n) = (V_term − ω/Kv_si)/Rm
motor:      Q_motor(I) = (I − I₀)/Kv_si                I₀ = io_no_load_a or 0
prop:       Q_prop(n)  = Cp·ρ·n²·D⁵ / (2π)             Cp at J = V/(n·D)
solve:      Q_motor − Q_prop = 0  by BISECTION, 80 iterations
            bracket: rpm_hi = free-run  V_term·Kv_si·60/2π   (I → 0)
                     rpm_lo = the back-EMF floor set by max_current_a
            r_lo ≤ 0 → clamp to rpm_lo ; r_hi ≥ 0 → clamp to rpm_hi
η_motor  = (V_term − I·Rm)(I − I₀) / (V_term·I)        clipped to [0,1]
P_shaft  = Q·ω                                          estimated = False
```

Model B is solved **per velocity point** — RPM becomes load-dependent, which
is the whole point of the refinement. `V_terminal = V_bat · throttle`.

Interpolation rules (`interpolate_ct_cp_pe`, l.278):

* rows are sorted by `J`; `np.interp` on `Ct` and `Cp`.
* `J` is **clamped** to `[J_min, J_max]` and an `extrapolation_warning` flag is
  raised — the curve never runs off the dataset silently; the response gets a
  human-readable warning listing the affected sweep.
* `Ct` is clamped at 0 — the slightly-negative tail past zero thrust is
  discarded; **windmilling drag is out of scope**.
* `Pe` is recomputed as `Ct·J/Cp` rather than read from the stored column
  (0 when `Cp ≤ 0` or `J = 0`).
* Callers that know the RPM (`compute_prop_operating_point`,
  `compute_performance_curve`, `_prop_torque_demand`) **pre-filter to the
  nearest-RPM row group**; the J-only helper merges all RPMs because Ct(J) is
  nearly RPM-independent for standard APC props.

Torque is always derived as `P/(2π·n)`, **never** from the stored `Torque_Nm`
column, which loses precision at 3 decimals for low-RPM rows.

Degenerate and edge behaviour: `prop_rpm ≤ 0` returns an all-zero curve with
*"Computed RPM is zero — check motor KV and battery voltage"*; both power
limits unknown falls back to `V_bat × 100 A` with a warning;
`P_shaft_max < 0.1 W` emits an infeasibility warning. `_air_density` is the
exponential approximation `1.225·exp(−h/8500)` — **not** the ISA model used
by AeroSandbox elsewhere.

### Solution space — required specs, not a catalog sweep 🟢 CONFIRMED

`powertrain_solution_space_service.compute_solution_space` (gh-975) inverts the
question: instead of "which parts do I own that fit", it computes "what must I
shop for". It is deliberately **pure Python** (no CadQuery, no AeroSandbox) so
it runs in the CI fast tier.

```
C_L(V)   = 2·m·g / (ρ·V²·S_ref)
C_D(V)   = cd0 + C_L² / (π·e·AR)
P_aero(V)= ½·ρ·V³·S_ref·C_D(V)
P_elec(V)= P_aero / (η_prop·η_motor·η_esc)
E_Wh     = P_elec(V_cruise) · t_target_h / DoD

per cell count S:
  V_nom = S·3.7        V_sag = S·3.5       (CELL_V_NOM / CELL_V_SAG)
  I_peak  = P_top_elec / V_sag        ← P_top_elec is ALREADY battery power;
                                        dividing again by η would double-count
                                        (gh-978 BLOCKER)
  cap_mAh = E_Wh / V_nom · 1000
  C_min   = (I_peak / (cap_mAh/1000)) · c_margin
  ESC_min = I_peak · esc_margin
  KV ≈ RPM_target / (V_nom · load_rpm_factor),
       RPM_target = V_top / (D · pitch/D) · 60,  D = 0.30 m  ← Phase-1 FIXED
  motor_peak_shaft_w = P_aero(V_top)    / η_prop_mid    ← SHAFT power, so the
  motor_cont_shaft_w = P_aero(V_cruise) / η_prop_mid      catalog comparison
                                                          is apples-to-apples
```

Every row is computed three times — at mid, low and high `η_prop` — to produce
a **band**, with the deliberate inversion `p_cruise_lo_w = p_cruise_hi_e`
(high η ⇒ *lower* power needed, i.e. the low end of the power range). The
feasible region is a sampled C-rate hyperbola `C = I_peak/(cap/1000)` over
`[cap_floor, 4·cap_floor]` in `_HYPERBOLA_SAMPLES = 40` points.

Input resolution reads the gh-924 context first and warns on every fallback:
`s_ref_m2 → 0.25 m²`, `e_oswald → 0.75`, `aspect_ratio → 7.0`,
`v_cruise (or v_md) → 15 m/s`, `mass → PARAMETER_DEFAULTS 1.5 kg`,
`cd0 → context, then the design assumption, then 0.03`. Domain validation
raises `ValidationDomainError` when `t_target_min ≤ 0` or
`V_top ≤ V_cruise` (default `V_top = 1.4·V_cruise`).

### Catalog sweep — sizing recommendations 🟢 CONFIRMED

`powertrain_sizing_service.size_powertrain` is the older, catalog-facing path:
a full **motor × battery cross-product** (ESCs are matched, not swept).

```
per combo:
  total_mass = airframe_mass + motor.mass_g/1000 + battery.mass_g/1000
  η_total    = η_prop · η_motor · η_esc          defaults 0.65 · 0.85 · 0.94
  P_cruise   = endurance_service._power_required(ρ, V, cd0, e, AR, m, S, η_total)
  I_cruise   = P_cruise / V_pack
  reject if  I_cruise > max_current_draw_a
  t_flight   = (cap_Ah / I_cruise) · 0.8 · 60 min      ← 80 % usable capacity
  ESC        = FIRST esc with continuous_current_a ≥ I_cruise   (list order!)
  confidence = min(t_flight / t_target, 1.0)           ← gh-992: no cliff
sort by confidence desc, return top 10
```

The physics are **delegated** to `endurance_service._power_required`
(gh-490 Model A) so there is one drag polar in the codebase, not three. The
legacy `_required_power_w` shim (l.55) now raises `NotImplementedError` by
design — an estimate-only mode without geometry is no longer allowed.

Aero parameters use a documented 3-tier priority (gh-960): explicit request
field → `assumption_computation_context` → RC-typical default
(`cd0 0.03`, `e 0.8`, `AR 8.0`, `S 0.5 m²`) with a per-parameter warning
naming the missing field. Battery voltage resolution walks
`voltage_v → voltage → nominal_voltage → cells·3.7 → 11.1 V` so a
schema-valid battery is not mis-read as 3S (gh-992). An empty catalog returns
**explicit warnings**, never a silent empty table.

`powertrain_sizing_modal_service` is the UI pre-fill sibling: same fallback
pattern for `cd0` / `s_ref_m2`, `DEFAULT_MOTOR_ETA = 0.85`,
`DEFAULT_ETA_PROP = 0.65`, and a motor list sorted by name where
`efficiency_pct` defaults to 85 %. It deliberately shows the **raw** motor KV
(not `output_kv`) because the designer is picking a motor, not an output shaft.

### 🔴 GAPs

* **`_find_matching_esc` returns the first ESC in query order,** not the
  smallest/lightest one that fits. Query order is `db.query(...).all()` with no
  `ORDER BY`, so the recommendation is effectively arbitrary and unstable.
* **Motor mass is counted but propeller mass is not.** `size_powertrain` adds
  motor + battery mass to `airframe_mass_kg`; the propeller (whose mass is now
  known, gh-1000/1017) never enters the total.
* **The solution-space KV is derived from a fixed 0.30 m propeller.** The
  module documents it as a Phase-1 approximation to be replaced by APC data
  (#615), but the *whole* prop database is already present in the same service
  layer.
* **`prop_component_seed` bypasses `validate_specs`.** It writes
  `ComponentModel` rows directly, so a polar with a NULL `diameter_in` /
  `pitch_in` produces a component that violates the seeded `propeller` type
  schema (both are `required`) and will 422 on the first API `PUT`.
* **`specs["variant"]` is not in the `propeller` type schema.** It is written
  by the seed and silently accepted because `validate_specs` never rejects
  unknown keys — meaning the schema is not a complete contract.
* **Two ESC/battery spec-key vocabularies coexist.** The sizing service reads
  `continuous_current_a` with a `max_continuous_a` fallback; the solution space
  reads `max_current_a` with a `continuous_current_a` fallback and
  `c_rating`/`discharge_c`, while `BatterySpec` reads `c_rate`. A battery
  imported with `c_rating` is invisible to the performance model.
* **Windmilling drag is out of scope** — `Ct` is clamped at 0, so a
  power-off/descent point silently reports zero drag from the propeller.
* **`_air_density = 1.225·exp(−h/8500)`** is a private approximation duplicated
  in three services (`powertrain_performance`, `powertrain_sizing_service`,
  and implicitly in the solution space's fixed `rho`) while the aero stack uses
  `asb.Atmosphere`. Above a few hundred metres the two disagree.
* **`Rm` is absent from the D-Power catalog,** so the QPROP path is dormant for
  every seeded motor; the shipped model is the fixed-RPM approximation whose
  own docstring calls it a simplification.

### The data model — a DAG of aeroplane rows 🟢 CONFIRMED

Versioning is **row copy**, not JSON snapshot. Every version is a real
`aeroplanes` row with its own full subgraph, tied together by four columns:

```
root_id         → the lineage root aeroplane (the first node ever created).
                  The root points at ITSELF.
predecessor_id  → self-referential: the node this one was forked from.
branch_id       → FK to branches.id: which branch this node belongs to.
is_immutable    → True = frozen snapshot; False = editable head.
```

plus five metadata columns: `version_label`, `version_note`, `created_by`
(`'human' | 'ai'` per the comment), `provenance_message_id`
(FK → `copilot_messages.id`) and `preview_png` (base64 thumbnail).

`branches` is `(root_id, head_id, name, is_main, created_by, created_at)`.
`root_id` and `head_id` both FK into `aeroplanes.id`; `aeroplanes.branch_id`
FKs back into `branches.id` — a genuine **circular FK dependency**, resolved
with `use_alter=True` on all four constraints so Alembic emits them as
separate `ALTER TABLE` statements.

### The invariants 🟢 CONFIRMED

1. **Exactly one `is_main` branch per lineage root.** Enforced at the DB level
   by a *partial* unique index, declared identically in the model and the
   migration so `create_all` (tests) and a migrated production DB have the same
   schema:
   ```
   Index("uq_branches_one_main_per_root", "root_id", unique=True,
         sqlite_where=text("is_main = 1"),
         postgresql_where=text("is_main = true"))
   ```
   `adopt_branch` therefore demotes the old main **and flushes** before
   promoting the new one — the comment at `aeroplane_version_service.py:277`
   spells out why: *"demote FIRST so the partial unique index never sees two
   `is_main=True`"*.
2. **An immutable node can never be mutated.** `_guard_immutable` raises
   `ValidationError` (→ 422) and is applied on `snapshot`. `restore` enforces
   the mirror rule: it *requires* `is_immutable=True`, because restoring from a
   live head is just `create_branch`.
3. **Every aeroplane is a node.** See the cluster preamble — `create_aeroplane`
   and the gh-903 backfill produce the same shape. Legacy rows with
   `branch_id IS NULL` remain visible (`list_aeroplanes_heads_only`).
4. **Branch names are unique per lineage — at application level only.**
   `rename_branch` queries for a same-`root_id` name collision and raises
   `ConflictError`; there is no DB constraint, so `create_branch` can still
   produce duplicates.
5. **The clone registry must be exhaustive.** Every table with a (transitive)
   FK to `aeroplanes` must appear in exactly one of `CLONED_TABLES` /
   `EXCLUDED_TABLES`, asserted by `test_aeroplane_clone_coverage.py` (which
   also asserts the two sets are disjoint and every exclusion carries a
   non-empty reason).

### Operations 🟢 CONFIRMED

| Function | Semantics |
|---|---|
| `snapshot(db, node_id, label, note, provenance_message_id)` (l.125) | clone the head into an **immutable predecessor**; the head keeps editing |
| `create_branch(db, from_node_id, name, created_by)` (l.186) | clone into a mutable head + new `BranchModel` row |
| `adopt_branch(db, branch_id)` (l.244) | promote to `is_main`, demote the old main (409 if already main) |
| `restore(db, snapshot_node_id, name, created_by)` (l.291) | `create_branch` from a frozen node; default name `restore/<label>` |
| `discard_branch(db, branch_id)` (l.324) | delete branch + its exclusive nodes (guarded) |
| `rename_branch(db, branch_id, name)` (l.459) | strip + per-lineage uniqueness |
| `compare(db, a, b)` (l.396) | read-only, returns both `_metrics_payload`s |
| `list_tree(db, root_id)` (l.415) | all nodes + branches for a lineage |
| `list_aeroplanes_heads_only(db)` (l.515) | heads + legacy rows, for the picker |

**`snapshot` is the counter-intuitive one.** It does *not* freeze the head and
create a new editable copy — it does the reverse, inserting the frozen copy
*behind* the head:

```
before:   [old_pred] ← [head (mutable, id=H)]
after:    [old_pred] ← [snapshot (immutable, id=S)] ← [head (id=H, unchanged)]
```

The head keeps its identity (id, UUID, all inbound references), which is why
the UI never has to re-point after a snapshot. `resolved_root_id =
head.root_id or head.id` handles the root-snapshots-itself case, and the
snapshot inherits the head's *old* `predecessor_id` before the head is
re-pointed at it. `created_by` is hard-coded to `"human"` on the snapshot node
(l.172) regardless of who triggered it.

**`discard_branch` has to fight the FK graph.** Its ordering is deliberate and
commented:

```
1. guards: is_main → 409 ;  only branch of the lineage → 409
2. collect nodes WHERE branch_id = branch_id
3. NULL out every predecessor_id pointing INTO that set
   (predecessor_id is use_alter/deferred, but SQLite has no deferrable FKs)
4. db.delete(branch) FIRST  — otherwise SQLAlchemy nulls branches.head_id
   via the relationship and violates its NOT NULL constraint
5. db.delete(node) for each node — ORM cascade removes the owned subgraph
```

### The clone engine 🟢 CONFIRMED

`clone_aeroplane_subgraph(db, source, *, immutable, branch_id,
predecessor_id, root_id)` deep-copies 17 tables in a fixed order, flushing
after each group so auto-generated PKs are available for FK re-keying. It
never commits — `get_db()` owns the boundary.

```
1  aeroplanes           new uuid4; name, total_mass_kg, xyz_ref,
                        assumption_computation_context deep-copied;
                        flight_profile_id KEPT (shared library ref);
                        version_label/note/created_by/provenance/preview = None
2  weight_items         + builds  weight_id_map: str(old_id) → str(new_id)
3  wings → wing_xsecs → wing_xsec_details
     → spares · turbulator (1:1, gh-1069) · TED → ted_servo
       (servo.component_id KEPT — shared COTS ref)
4  fuselages → fuselage_xsecs      step_path / solid_step_path → NULL
5  mission_objective    (1:1)
6  design_assumptions   estimate + calculated + active_source + divergence
7  aircraft_computation_config (1:1)
8  stability_results    including computed_at and geometry_hash
9  loading_scenarios    component_overrides REMAPPED via weight_id_map
10 component_tree       aeroplane_id = str(clone.uuid); parent_id remapped
```

Two re-keying subtleties:

* **`_remap_component_overrides`** walks `toggles`, `mass_overrides` and
  `position_overrides` and rewrites each `component_uuid` through
  `weight_id_map`. Values *not* in the map pass through unchanged — they are
  COTS component UUIDs, which are shared references. A clone whose loading
  scenarios were not remapped would silently reference the *source's* weight
  items.
* **`_clone_component_tree`** is a two-pass topological copy: pass 1 inserts
  every node with `parent_id=None` collecting `old_id → new_id`; pass 2 issues
  an `UPDATE` per node to restore the parent link. A parent that is not in the
  map (cross-aeroplane reference or corrupt data) leaves `parent_id = None`
  and logs a **warning naming both ids** — explicitly chosen over silent data
  loss. Note this table is found by its **string** `aeroplane_id` (a UUID
  VARCHAR, not an integer FK).

`CLONED_TABLES` carries a prominent **coverage-test blind-spot note**: the
coverage test introspects SQLAlchemy `ForeignKey` objects, so any table whose
aeroplane reference is a plain `String` is invisible to it and must be
maintained by hand. Three tables are in that category today —
`component_tree` (cloned), `construction_plans` and `construction_parts`
(both excluded).

`EXCLUDED_TABLES` groups its 18 entries by reason: shared library
(`rc_flight_profiles`, `components`, `component_types`, `airfoils`,
`airfoil_low_re`, `mission_presets`), transient/recomputed
(`operating_points`, `operating_pointsets`, `flight_envelopes`),
conversation (`copilot_messages` — *"provenance captured via note + cursor"*),
versioning meta (`branches`), construction artefacts (file-backed, stale
paths), caches (`tessellation_cache`, `avl_geometry_files` — *"copying would
carry stale `is_user_edited` flags"*), and `alembic_version`.

### Provenance — human vs AI 🟢 CONFIRMED

Three writers set `created_by`, and they do **not** agree on a vocabulary:

| Writer | Value written |
|---|---|
| `aeroplane_service.create_aeroplane` (main branch) | `"human"` |
| `aeroplane_version_service.snapshot` (snapshot node) | `"human"` (hard-coded) |
| `versioning.py` REST (`BranchRequest.created_by`) | `"human"` by default; schema documents `'human' \| 'ai'` |
| `copilot_apply_service.get_or_open_proposal` | **`"copilot"`** |

The AI proposal lifecycle (`copilot_apply_service.py:107-241`, detail belongs
to Cluster E) is the only automated consumer:

```
get_or_open_proposal(db, live_aeroplane_id, message_id)
  root_id = node.root_id or node.id
  reuse the FIRST branch WHERE root_id=? AND is_main=False
                          AND created_by='copilot'
                          AND name LIKE 'copilot-proposal%'      ← ONE open
  else create_branch(from live head, name='copilot-proposal[-<msg_id>]',
                     created_by='copilot')
discard_open_proposal(db, live_aeroplane_id)
  db.flush() → db.expunge_all() → re-resolve → discard_branch
```

The `expunge_all()` is not cosmetic: `apply_edits` calls
`put_wing_as_wingconfig`, which does delete-then-reinsert in the *same*
session, leaving stale `WingXSecSpareModel` instances in the identity map;
the subsequent cascade delete then raises
`InvalidRequestError: Can't attach instance … already present in this session`.

`provenance_message_id` is the AI **cursor**: the id of the last
`copilot_messages` row at snapshot time. It is accepted by
`SnapshotRequest`, written by `snapshot()`, returned on `VersionNode` — and
that is its entire lifecycle; nothing reads it back.

`spar_insert_service` (`:485-497`, gh-1058) is the one non-copilot automated
caller: a **destructive** spar commit (segment split or spare REPLACE) takes an
automatic immutable snapshot labelled `"Before spar insert"` *before* mutating
anything, and aborts the whole commit if the snapshot fails — *"never mutate
without a recovery point"*. The snapshot id is returned in `SparInsertResponse`
so the UI can offer one-click revert.

### 🔴 GAPs

* **The `design-versions` REST surface is dead but still mounted.** All five
  routes (`GET/POST/GET/DELETE/diff` under
  `/aeroplanes/{id}/design-versions`) are registered in
  `aeroplane/__init__.py:41` and every one of them calls a
  `design_version_service` stub that unconditionally raises `NotFoundError`.
  The service header says *"TODO(gh-905): replace all functions below"* — but
  gh-905 shipped the parallel `/lineages`, `/branches` surface instead. Callers
  get a plausible 404 rather than a 410/501.
* **`created_by` has no enum and four writers disagree.** The column comment
  and `BranchRequest` say `'human' | 'ai'`; the copilot writes `'copilot'`.
  Any UI filtering on `'ai'` will miss every copilot branch.
* **`provenance_message_id` is write-only.** Nothing reads it; there is no
  route, tool or query that resolves a snapshot back to the conversation turn
  that produced it.
* **Branch names are only unique on rename.** `create_branch` performs no
  collision check, so two branches in one lineage can share a name and only a
  later `rename_branch` will complain.
* **`discard_branch` deletes by `branch_id` alone.** A snapshot node created on
  branch A and then adopted into a different logical timeline is still deleted
  with A. Nothing checks whether another node's `predecessor_id` chain still
  needs it — those links are simply nulled (step 3), silently truncating the
  lineage of surviving nodes.
* **`list_tree` cannot find orphaned nodes.** It filters on
  `id == root_id OR root_id == root_id`; a node whose `root_id` was left NULL
  (a legacy row, or a clone created with `root_id=None`) is invisible in the
  version graph even though it exists.
* **No storage-growth control.** Every snapshot is a full row-copy of the
  entire design subgraph (wings, xsecs, details, spares, TEDs, servos,

### The turn loop 🟢 CONFIRMED

`run_turn` (`copilot_service.py:446`) is an `AsyncGenerator[dict, None]` with
`MAX_LOOP_ITERATIONS = 6`. Per iteration it streams one completion, accumulates
text deltas and tool-call chunks by `index`, then:

| `finish_reason` | Action |
|---|---|
| `"stop"`, or no tool-call chunks and not `"tool_calls"` | `turn_complete = True`, break |
| no tool-call chunks (anything else) | `turn_complete = True`, break |
| `"tool_calls"` | execute all calls, append results, continue |

Exhausting all 6 iterations while the model still wants tools yields
`done` with `truncated: true`, which the endpoint forwards so the UI can say
the turn was cut off.

**Tool execution is off-loop.** `await asyncio.to_thread(copilot_tools.execute,
name, db, aeroplane_id, **args)` — the comment at l.609-612 spells out the
reason: inside the worker thread there is no running event loop, which is
precisely what lets `_run_analysis` call `asyncio.run(...)` for the async
AeroSandbox coroutine. Any exception from a tool becomes `{"error": str(exc)}`
and the loop continues; the model self-corrects.

**Malformed tool arguments degrade silently.** `json.JSONDecodeError` on the
accumulated `arguments` string sets `args = {}` and the tool is still invoked
(`copilot_service.py:602-604`). 🟡 INFERRED risk: a truncated stream can call a
write tool with no ops rather than reporting a protocol error.

### History replay — the gh-922 fix 🟢 CONFIRMED

A turn is persisted as **one** assistant row carrying both `tool_calls` and
`tool_results` (there are no separate `tool` rows in practice). Both the OpenAI
and Anthropic tool protocols require every assistant `tool_call` to be
immediately followed by a matching `tool` message, so `_history_to_openai`
(`copilot_service.py:396`) *reconstructs* them:

```
results_by_id = {tr["tool_call_id"]: tr for tr in m.tool_results or []}
for tc in m.tool_calls:
    content = json.dumps(results_by_id[tc["id"]]["result"])
              if present else json.dumps({"error": "tool result unavailable"})
    emit {"role": "tool", "tool_call_id": tc["id"], "content": content}
```

Without this the replayed history contains an orphaned `tool_use` and *"the hub
400s on every turn after the first tool use"*. The placeholder error object is
deliberate — dropping the message would break the pairing again.

### Error sanitisation 🟢 CONFIRMED

`_sanitize_error` (`copilot_service.py:44`) runs on every hub/stream exception
before it reaches the browser: it replaces any literal occurrence of the
configured API key with `[REDACTED]`, then substitutes a **category** message
when the text mentions auth/key/token/secret/credential (`"<Type>:
authentication or configuration error"`) or connectivity
(`"<Type>: hub connection error"`). Only otherwise is the redacted raw text
forwarded. The endpoint's own catch-all is even stricter — it emits the flat
string `"Internal server error"`.

### The tool registry 🟢 CONFIRMED

`TOOL_REGISTRY` (`copilot_tools.py:828`) holds **6** entries — deliberately not
the 76-tool MCP surface. The module header states the rule: *"only the tools
that are safe, fast, and meaningful for an advisory interaction"*.

| Tool | Kind | Returns |
|---|---|---|
| `get_design_snapshot` | read | `_metrics_payload(node)` — the versioning module's dict |
| `get_wing_geometry(wing)` | read | hybrid editable/derived block, **mm + degrees** |
| `run_analysis(kind)` | read | polar or stability summary, SI |
| `get_version_tree` | read (never retargeted) | nodes + branches for the lineage |
| `apply_design_edits(ops)` | write | branch id, applied/rejected, metrics diff |
| `discard_proposal` | write | `{"discarded": bool}` |

Contract per the module docstring: signature `fn(db, aeroplane_id, **kwargs) ->

Units are SI/metres except `get_wing_geometry`, which is an intentional
exception returning mm/degrees to mirror the edit-op units.

#### Read-retargeting (gh-938)

`execute` (`copilot_tools.py:866`) resolves an *effective* target id before
dispatch. For `{get_design_snapshot, get_wing_geometry, run_analysis}` it calls
`_effective_target_id`, which finds the open proposal branch and substitutes
`branch.head_id` — so while iterating, the copilot reads **its own edits**.
`get_version_tree` and the two write tools always get the live id. Any
exception inside the lookup is swallowed (`except Exception: pass`) and falls
back to the live id. 🟡 The failure is invisible: the model would then read the
live design while believing it reads the proposal.

#### `get_wing_geometry` — hybrid read (gh-958)

Returns two blocks:

* **`editable`** — per segment: `chord_root_mm`, `chord_tip_mm`, `length_mm`,
  `sweep_mm`, `dihedral_rel_deg`, `incidence_deg`, `airfoil`. Sourced from the
  validated `WingConfig` (mm).
* **`derived`** — per station: `xyz_le_mm`, `chord_mm`, `twist_deg`,
  `accumulated_dihedral_deg`, `te_x_mm = LE_x + chord`; plus wing-level
  `projected_semi_span_mm` and `tip_xyz_le_mm`.

The derived block is read from the **persisted** `WingXSecModel.xyz_le`
(metres × 1000), not re-walked from the segments — the docstring is explicit
that this is what keeps it from diverging from the canonical `cad_designer`
frame (which seeds the dihedral accumulator with the root-airfoil dihedral).
Accumulated cant is recovered from the geometry itself:
`atan2(Δz, Δy)` between consecutive LE points.

The `note` field carries a warning the schema cannot express:
`chord_root_mm` is **read-only** — a segment's root chord follows the previous
segment's tip chord (continuity), so tapering means setting `chord_tip_mm`.

#### Deterministic arithmetic — the anti-hallucination core

`_drag_breakdown(cl, cd_total, ar, e)` (`copilot_tools.py:242`) computes the
induced/parasitic split in Python because *"the LLM is unreliable at this
arithmetic (it has produced both physically-impossible splits and 10x
errors)"*:

```
CD_i        = CL² / (π · AR · e)          # lifting-line
CD_parasite = CD_total − CD_i             # ONE source, never mixing snapshot cd0
```

Guards: returns `None` when any input is missing or `AR ≤ 0 / e ≤ 0 /
CD_total ≤ 0`; and when the split is physically impossible (`cd_i < 0`,
`cd_par < 0`, `cd_i > cd_total`) it returns a **`note`-carrying dict with the
raw inputs** instead of a wrong split. `_polar_drag_breakdown` picks the
max-L/D point via `nanargmax(CL/CD)` and pulls `aspect_ratio` / `e_oswald` from
`assumption_computation_context` — the same source as the polar's `e`.

`_run_polar_async` runs AeroBuildup over α ∈ [−10°, +15°], 26 points, V = 20
m/s, h = 0 and reports `cl_max`, `cl_min`, `cd_min`, `cl_cd_max`,
`drag_breakdown`, and four characteristic points renamed for the model
(`best_glide`, `min_drag`, `cl_max_point`, `stall`).

`_run_stability_async` carries the gh-924 single-source-of-truth rule in code:
it evaluates at the **cruise design point** (α = 0, `v_cruise_mps` from the
context, fallback 20 m/s) and then **overrides** the freshly computed neutral
point with `ctx["x_np_m"]`, recomputing static margin as
`(x_np − cg_x)/MAC × 100`. The comment explains that the two stability paths
normalise `x_np` against different reference chords, so a fresh run would
surface a second divergent value (0.109 m vs the dashboard's 0.080 m).
*One op-point → one neutral point.*

`run_analysis` is wrapped in `asyncio.wait_for(..., DEFAULT_ANALYSIS_TIMEOUT_S
= 60.0)`; on expiry it returns `{"status": "timeout", "note": …}` rather than
an error, so the model tells the user to check the Analysis tab.

### The edit-op DSL 🟢 CONFIRMED

`app/schemas/copilot_edits.py` defines a Pydantic discriminated union on
`type` with 7 members: `SetAssumption`, `SetXsec`, `SetSegment`, `AddXsec`,
`RemoveXsec`, `SetWingParam`, `ReplaceWingConfig`. All chord/span fields are
**millimetres**; angles are degrees.

`edit_ops_array_schema()` (l.240) is a gh-938 workaround worth noting: it
builds an `anyOf` of every op model's `model_json_schema()` because *"without
them [the per-op fields] it guesses field names (span_mm, cant_deg,
wing_index, …) and the ops get rejected"*. The op models are deliberately flat
(no nested `BaseModel`) so each schema inlines without `$ref`s.

Index semantics — the source of most rejections:

```
n segments  ⇒  n + 1 cross-sections (stations)
station 0        = root of seg[0]
station i (0<i<n)= tip of seg[i-1] AND root of seg[i]   ← BOTH are written
station n        = tip of seg[n-1]
```

`SetXsec` addresses a **station** and touches both neighbours; `SetSegment`
addresses a **segment** and touches only its tip airfoil. `RemoveXsec` accepts
only interior stations (`1 … n_xsecs−2`) and merges `seg[i-1]` with `seg[i]`
(lengths added, **sweeps added** — the code comment says "weighted avg" but the
implementation is a plain sum 🔴).

### `apply_edits` — the apply engine 🟢 CONFIRMED

`apply_edits(db, proposal_aeroplane_uuid, ops)` (`copilot_apply_service.py:248`)
never raises for a bad individual op; it collects `applied: list[str]` and
`rejected: list[{op, error}]`. Its central design decision is the **per-wing
in-memory cache**: geometry ops mutate `wing_config_cache[wing]` (a mm dict)
and the wing is written exactly once after the loop via
`put_wing_as_wingconfig(..., scale=0.001)`. That makes multiple ops on one wing
composable. `ReplaceWingConfig` breaks the pattern deliberately — it validates
and writes immediately, evicts the cache entry and calls `db.expire_all()`.

Two session-hygiene calls are load-bearing and commented as such:

* `db.expire_all()` after the wing writes — `put_wing_as_wingconfig`
  deletes-then-reinserts, leaving stale `WingModel` identities that would make
  the metrics payload (and a same-turn `get_wing_geometry`) read pre-edit
  geometry.
* `db.expunge_all()` in `discard_open_proposal` — see below.

The `AddXsec` tip-append path additionally **strips `tip_type` from every
trailing segment** (l.517-520) because `create_wing_configuration()` splits
segments into a middle pass (`tip_type is None`) and a tip pass; leaving
`tip_type="flat"` on the old last segment would process the new winglet first
and physically reorder the cross-sections.

`recompute_assumptions(db, proposal_uuid)` runs synchronously at the end and is
explicitly non-fatal (`logger.warning`, continue).

### Proposal-branch lifecycle 🟢 CONFIRMED

### The system prompt as executable policy 🟡 INFERRED (documented behaviour)

`SYSTEM_PROMPT` is ~270 lines and is not decorative — it encodes rules that
have no code enforcement:

* **Propose, never mutate.** "You NEVER change the live design directly … say
  'I've prepared a proposal on a branch'". There is deliberately **no adopt
  tool** — only the human adopts, in the Versions panel.
* **Fresh before/after for performance numbers.** L/D, `v_stall`, `v_cruise`,
  `v_min_sink` must come from `run_analysis`, never from
  `diff_proposal_branch` / `diff_vs_live`.
* **Physics direction checks.** Lower mass ⇒ *all* characteristic speeds drop
  (V ∝ √(W/S)); a speed that rises on a mass decrease must be flagged as an
  artifact, not reported.
* **Never mix data sources.** Snapshot `cd0`/`e_oswald` (coarse estimate) must
  never be combined with the polar's `CD` in one expression.
* **Static margin from one source**, CG always *derived*
  (`x_CG = x_NP − SM_target × MAC`), never a raw band passed through.
* **Audience rules** — gloss MAC/AR/Re/Oswald e/SM/NP on first use, translate
  L/D into a glide ratio, lead with a plain-language takeaway.
* **Design warnings to raise proactively** — winglet at span < ~2 m (Re < ~80 000),
  taper ratio < ~0.4 (tip stall, recommend 1–2° washout), `v_min_sink ≈ v_stall`
  within ~5 %, cruise < 1.2 × stall.
* **Provisional knowledge tables** — static-margin bands per mission
  (RC trainer 15–25 %, sport 8–15 %, aerobatic 0–8 %, UAV 5–15 %, light GA
  5–15 %), V_H bands, L/D benchmarks, first-flight CG. Labelled *"until RAG is
  available"*.
* **Language** — reply in the user's language (German if they write German);
  UI chrome and code comments always English.

`{context_hint}` is interpolated per turn from the request body (e.g. *"Active
tab: Wing Editor · Aircraft: MyGlider"*).

### Persistence 🟢 CONFIRMED

`copilot_messages` is a flat per-aeroplane thread ordered by `sort_index`.
`append_message` computes the next index as `COUNT(*)` for that aeroplane —
which is **not** collision-safe: two concurrent appends (or an append after a
`delete_message`) produce duplicate or reused indices. 🔴 `parent_id` exists
for message branching but is never set by any writer and never read.

`clear_history` iterates `list(aeroplane.copilot_messages)` — the `list()` is
annotated as required to avoid mutating during iteration.

The table is in `EXCLUDED_TABLES` of the clone registry with the reason
*"provenance captured via note + cursor"*, so branching an aircraft does not
copy its conversation.

* **`COPILOT_EMBEDDING_MODEL` is dead configuration.** No embedding, vector
  store or RAG code exists; `.env.example` records that gh-929 superseded the

* **`provenance_message_id` is never read**, and `get_or_open_proposal`'s

  a version back to a chat turn are both inert.
* **`diff_vs_live` is a misleading alias.** It carries the proposal's own

* **`sort_index` derived from `COUNT(*)`** is not concurrency- or delete-safe.

* **A JSON-decode failure on tool arguments silently becomes `{}`** and the

* **The SSE endpoint holds the request-scoped session open for the whole

* **`created_by="copilot"` vs the documented `'human' | 'ai'`** — the

### Registration pattern 🟢 CONFIRMED

A two-stage pattern separates *declaration* from *installation*:

```python
@dataclass(frozen=True)
class MCPToolSpec: name: str; description: str; handler: Callable

TOOL_SPECS: list[MCPToolSpec] = []

def mcp_tool(name, description):            # l.86 — decorator only RECORDS
    def decorator(fn):
        TOOL_SPECS.append(MCPToolSpec(name, description, fn))
        return fn                            # handler returned unchanged
    return decorator

def create_mcp_server() -> FastMCP:          # l.1503 — installation
    mcp = FastMCP(name="da3dalus-cad-tools")
    for spec in TOOL_SPECS:
        mcp.tool(name=spec.name, description=spec.description)(spec.handler)
    mcp.resource("img://{asset_id}",  …)(read_image_asset)
    mcp.resource("data://{asset_id}", …)(read_data_asset)
    return mcp
```

`MCP_TOOL_NAMES` (l.1500) is the frozen tuple of names — the introspection
surface the tests assert against. `get_mcp()` memoises the server into the
module global; `mcp = get_mcp()` at l.1548 means the server is built at **import
time**, before `create_app()` runs.

FastMCP derives each tool's JSON input schema from the **handler signature**,
so the Pydantic types in the coroutine parameters (`UUID4`,
`OperatingPointSchema`, `AlphaSweepRequest`, `AssumptionWrite`,
`RCFlightProfileCreate`, …) are the contract. The decorator's `description=`
string is the only prose the agent sees — there are no docstrings on the tool
functions.

### REST ↔ MCP reuse 🟢 CONFIRMED

`_call_endpoint` (l.96) is the whole bridge:

```python
async def _call_endpoint(endpoint_fn, **kwargs):
    with SessionLocal() as db:
        if "db" in inspect.signature(endpoint_fn).parameters:
            kwargs["db"] = db
        result = endpoint_fn(**kwargs)
        if inspect.isawaitable(result): result = await result
        return _normalize_result(result)
```

It imports the FastAPI **endpoint function** and calls it as a plain callable —
no routing, no `Depends`, no middleware, no exception handlers. Consequences:

1. **No transaction commit — writes are lost.** REST gets its commit from
   `get_db()`; here a bare `with SessionLocal() as db:` is used, and
   `Session.__exit__` calls `close()`, which *rolls back* the pending
   transaction. Verified against a concrete write path:
   `aeroplane_service.create_aeroplane` flushes four times and its docstring
   states *"No db.commit() is called — get_db() owns the transaction
   boundary"*, so `create_aeroplane_tool` returns a populated
   `AeroplaneModel` whose row never reaches the database. Only the handful of
   services that commit themselves (`retrim_service`,
   `operating_point_generator_service`, `tessellation_service`) persist through
   MCP. The tests cannot catch this: `test_mcp_server_tools.py:89` monkeypatches
   `_call_endpoint` wholesale and `test_mcp_server_extended.py:643-673`
   exercises it with fake local functions — no test drives a real endpoint
   through a real session. 🔴
2. **Signature-based injection.** `db` is passed only if the parameter exists —
   other `Depends(...)` parameters (e.g. `settings`) must be supplied by hand,
   which several tools do (`settings=get_settings()`), and some pass
   `request=None` where the endpoint expects a `Request`.
3. **Service exceptions surface raw.** The `ServiceException → HTTP` handler is
   registered on the FastAPI app, not on this path, so a `NotFoundError`

### The asset registry 🟢 CONFIRMED

Binary results cannot travel as MCP tool JSON, so three tools
(`get_aeroplane_three_view`, `download_export_zip`,
`analyze_alpha_sweep_diagram`) route their output through an in-process
registry:

```
AssetEntry(asset_id, kind, file_path, mime_type, public_url, filename)
ASSET_REGISTRY: dict[str, AssetEntry]      guarded by ASSET_REGISTRY_LOCK (threading.Lock)
```

* `register_file_asset(path, …)` — if the file is **not** already under `tmp/`
  it is copied to `tmp/mcp_assets/external/<uuid4hex>_<name>`; MIME is guessed
  from the name, kind defaults to `img` for `image/*` else `data`.
* `register_bytes_asset(content, …)` — writes to
  `tmp/mcp_assets/<kind>/<asset_id[:2]>/<name>` (a 2-hex-char fan-out).
* `_asset_payload(entry)` returns `resource_uri` (`img://<id>` / `data://<id>`),
  **`url_from_docker_container`** (derived from the live request), and
  **`url_for_webui`** / `url` (from `settings.base_url`) — the dual-URL answer
  to "the agent and the browser see the service at different addresses".
* `read_image_asset` / `read_data_asset` resolve a `ResourceResult`; a missing
  id, a kind mismatch (`img://` on a `data` entry) and a vanished file all raise
  `fastmcp.exceptions.NotFoundError`.

`resolve_public_base_url(ctx)` tries the MCP `Context` request URL, then
`fastmcp.server.dependencies.get_http_request()`, then falls back to
`settings.base_url`; `_base_url_from_request_url` strips a trailing `/mcp` from
the path prefix so a reverse-proxied deployment produces correct `/static` URLs.

### 🔴 GAPs

* **MCP writes are silently discarded.** `_call_endpoint` never commits and
  `Session.__exit__` rolls back, so every tool whose service relies on
  `get_db()`'s commit — `create_aeroplane`, `set_aeroplane_total_mass`, all
  wing / cross-section / fuselage / control-surface mutations, all design
  assumptions — returns a success payload while persisting nothing. Confirmed
  by reading `aeroplane_service.create_aeroplane` (flush-only, explicit "no
  commit" docstring) and by the absence of any test that drives a real endpoint
  through a real session.
* **`ASSET_REGISTRY` is process-local and unbounded.** It is never evicted, so
  it grows for the life of the process; files under `tmp/mcp_assets/` are never
  cleaned up; and an asset id from one worker is a 404 in another. Multi-worker
  deployment is silently broken for assets.
* **No authentication or authorisation on `/mcp`.** Combined with
  `allow_origins=["*"]`, the full 76-tool surface — including destructive
  `delete_aeroplane`, `delete_all_wing_cross_sections` — is reachable by anyone
  who can reach the port.
* **The MCP surface has drifted behind REST.** Versioning, the copilot,
  components/COTS, construction plans, powertrain and OpenVSP import — every
  module added after the initial geometry/analysis core — have no MCP tools.
* **Service exceptions are not translated.** `NotFoundError` and friends escape
  as raw Python exceptions instead of structured MCP errors.
* **`_normalize_result` returns `{"status": "ok"}` for `None`**, so a delete
  that silently failed is indistinguishable from one that succeeded.
* **`register_file_asset` copies files without a size cap** and
  `_normalize_result` base64-encodes image bodies fully in memory.
* **`run_mcp_server` hard-codes `0.0.0.0:8001`**, bypassing `UVICORN_HOST`.

### Persistence layer 🟢 CONFIRMED

`Base` is 11 lines: `@as_declarative` with an implicit
`id = Column(Integer, primary_key=True, index=True)` and
`__tablename__ = cls.__name__.lower()`. Because that default would produce
`aeroplanemodel`, essentially every model overrides `__tablename__` — the
convenience is inherited but unused.

The engine adds SQLite-specific `connect_args={"check_same_thread": False,
"timeout": 30}` and an `Engine.connect` listener setting
`journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=30000`. The comment
gives the reason: long-running async writers (assumption recompute) hold a
transaction open for several seconds while AeroBuildup runs, so without WAL a
parallel write fails with *"database is locked"*.

`SessionLocal` uses `expire_on_commit=False`, `autocommit=False`,
`autoflush=False`. **`autoflush=False` is significant**: services must flush
explicitly before a query can see their pending writes, which is why
`db.flush()` appears throughout the version and copilot services.

`get_db()` is the transaction boundary — `yield` → `commit` on success,
`rollback` on exception, `close` in `finally`. The contract (repeated in the
root `CLAUDE.md`, `app/CLAUDE.md` and the Cluster-A preamble) is that services
never call `commit()` or `begin()`. Four paths legitimately own their own
session: the two lifespan seeders, `_recompute_sync`,
`JobTracker._run_backfill_for_names` — and one that arguably should but does
not commit, `mcp_server._call_endpoint`.

### Error contract 🟢 CONFIRMED

```
ServiceException(message, details)
├── NotFoundError(entity=…, resource_id=…)   → 404 "not_found"
├── ValidationError                           → 422 "validation_error"
│   └── ValidationDomainError                 → 422 "validation_error"
├── ConflictError                             → 409 "conflict"
└── InternalError                             → 500 "internal_error"
(bare ServiceException)                       → 500 "service_error"
```

`NotFoundError` has a convenience constructor that builds
`"{entity} not found"` and stuffs `{"id": str(resource_id), "entity": entity}`
into `details`. The global handler emits a uniform envelope

```json
{"error": {"code": "...", "message": "...", "details": ... | null}}
```

with `details` passed through
`jsonable_encoder(..., custom_encoder={BaseException: str})` so an exception
stored in `details` serialises instead of crashing the handler. 4xx are logged
at INFO, 5xx with `logger.exception`.

Two more handlers exist, and both emit **German** user-facing messages in an
otherwise English codebase: `IntegrityError → 409 "name existiert bereits"`
(which assumes *every* integrity violation is a duplicate name) and
`RequestValidationError → 422 "Ungültige Eingabedaten"`. 🔴

Note the parallel, **non**-global pattern: several endpoint modules
(`copilot_history.py`, `versioning.py`, …) define their own local `_raise_http`
+ `_call` helpers that convert `ServiceException` to `HTTPException`, producing
FastAPI's `{"detail": …}` shape instead of the `{"error": {…}}` envelope. Two
error contracts coexist. 🔴

### Non-finite float safety 🟢 CONFIRMED

`NonFiniteSafeJSONResponse` (`core/json_safe.py`) is set as
`default_response_class` on routers whose payloads carry solver output — today
that is **exactly one**: `aeroanalysis.py:43`. Every other router that can
return AeroSandbox numbers (`operating_points`, `section_aoa`, `airfoils`, the
powertrain and speed-polar routers) uses the plain `JSONResponse` and is
therefore still exposed to the crash this class exists to prevent. 🔴
Starlette renders with `json.dumps(allow_nan=False)`, so a NaN from a
degenerate geometry (`length³/volume` with zero volume) or `log10(0)` would
otherwise become an unhandled 500. `_sanitize` recurses dicts/lists/tuples,
handles `np.floating` explicitly (numpy floats are **not** `float` subclasses),
converts non-finite values to `null` and logs a WARNING with the replacement
count. The module docstring states the philosophy: `null` is *"an honest 'no
value', never a fabricated fallback number that would hide the underlying
design problem"*.

### Event bus and background jobs 🟢 CONFIRMED

`EventBus` (`core/events.py`) is a synchronous in-process pub/sub with a
`dict[type[DomainEvent], list[Callable]]`. `publish` wraps every handler in
`try/except` and only logs — a broken subscriber can never break the publishing
request. Two events: `GeometryChanged(aeroplane_id, source_model)` and
`AssumptionChanged(aeroplane_id, parameter_name)`.

`invalidation_service.register_handlers()` wires four subscribers:

| Event | Handler | Guard |
|---|---|---|
| `GeometryChanged` | `schedule_retrim` | — |
| `GeometryChanged` | `schedule_recompute_assumptions` | — |
| `AssumptionChanged` | `schedule_retrim` | `param ∈ {mass, cg_x}` |
| `AssumptionChanged` | `schedule_recompute_assumptions` | `param ∈ {target_static_margin, mass}` |

`_RECOMPUTE_TRIGGERING_PARAMS` deliberately excludes `cg_x`, `cd0` and `cl_max`
— the comment explains that including them would create a
recompute → `AssumptionChanged(cg_x)` → recompute loop.

`mark_ops_dirty` is a bulk `UPDATE operating_points SET status='DIRTY' WHERE
aircraft_id = ? AND status NOT IN ('DIRTY','COMPUTING')`. Note **who** calls it:
not the event handlers, but the *publishers* — `mass_cg_service` (×2),
`loading_scenario_service`, `assumption_compute_service`,
`design_assumptions_service` (×2) and the two SQLAlchemy listener modules
`models/avl_geometry_events.py:52` and `models/stability_events.py:52` — each
immediately **before** `event_bus.publish(...)`. The handlers only schedule
jobs, while their log lines read *"OPs marked DIRTY"*, describing work the
caller already did. Marking and notifying are therefore two separate
responsibilities that every publisher must remember to pair by hand. 🟡

`JobTracker` (`core/background_jobs.py`) is a module singleton with
`debounce_seconds = 2.0` and two parallel job families (retrim, recompute),
each a `dict[aeroplane_id → Job]` plus a `dict[aeroplane_id → asyncio.Task]`.
Status: `DEBOUNCING → COMPUTING → DONE | FAILED`.

The scheduling code has a deliberate ordering — **create the new task first,
only then cancel the old one**:

```
new_task = self._create_task_safe(...)
if new_task is None: return          # nothing was clobbered
if existing_task and not done: existing_task.cancel()
self._jobs[id] = Job(...); self._debounce_tasks[id] = new_task
```

because `_create_task_safe` can legitimately return `None` (no bound loop, unit
test context) and cancelling first would strand the job in `DEBOUNCING` with no
task to fire it. `_create_task_safe` handles the worker-thread case by posting
`call_soon_threadsafe(_make_task)` onto the bound main loop and waiting on a
`threading.Event` with a **2.0 s timeout** — on timeout it returns `None` and
the schedule is silently dropped. 🔴

`schedule_retrim` short-circuits while a job is already `COMPUTING`;
`schedule_recompute_assumptions` does not. A third family,
`schedule_airfoil_low_re_compute(names)`, runs a NeuralFoil backfill for newly
imported airfoils in a worker thread — it is fire-and-forget, untracked, and
imports `scripts.backfill_airfoil_low_re._compute_geometry_stats` from
application code (l.362). 🔴

### Architecture — a client-only SPA inside the App Router 🟢 CONFIRMED

`app/layout.tsx` is the only meaningful server component: it loads `Geist`,
`Geist_Mono` and `JetBrains_Mono` through `next/font/google`, sets the metadata
and applies the font CSS variables. `app/page.tsx` is five lines. Everything
under `/workbench` is `"use client"`.

There are **no route handlers** (`app/**/route.ts` does not exist), no server
actions and no server-side fetching. This directly contradicts
`frontend/CLAUDE.md:12-13` — *"All API calls go through server-side route
handlers or server actions to avoid CORS"* — and explains why the backend has
to run `allow_origins=["*"]`: every request is a cross-origin browser fetch to
`http://localhost:8001`. 🔴

`app/workbench/layout.tsx` is the whole shell and mounts, on **every** tab:

```
Suspense
└ AeroplaneProvider                     (selection + URL/localStorage sync)
  └ UnsavedChangesProvider
    ├ Header(onOpenHistory)
    ├ WorkbenchImportWarningBanner
    ├ main → {children}                 ← the active tab
    ├ VersionGraphOverlay               (conditional, key={rootId})
    ├ MetricsDashboardContainer         (gh-881, docked)
    ├ CopilotStrip(onOpenHistory)       (docked)
    ├ UnsavedChangesModal
    └ AeroplanePickerHost
```

### The enforced layering 🟢 CONFIRMED

`.dependency-cruiser.cjs` codifies `app → components → hooks → lib`:

| Rule | Severity | Meaning |
|---|---|---|
| `no-circular` | **error** | no cycles anywhere |
| `no-components-import-app` | **error** | components must not reach into routes |
| `no-hooks-import-app` | **error** | hooks must not reach into routes |
| `no-hooks-import-components` | warn | invert the dependency instead |
| `no-lib-import-components` | warn | `lib/` stays pure |
| `no-orphans` | info | unimported files (`page.tsx`, `layout.tsx`, `.d.ts`, tests excluded) |

`tsPreCompilationDeps: true`, `e2e/` and `.features-gen` excluded. Run with
`npm run deps:check`; `npm run deps:graph` renders an SVG.

### Data fetching 🟢 CONFIRMED

```ts
// lib/fetcher.ts
const API_BASE = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:8001";
export async function fetcher<T>(path: string): Promise<T>      // GET, the SWR fetcher
export async function putJson<T>(path: string, body): Promise<T>
```

Hook convention (48 files, ~30 use `useSWR` directly):

```ts
const path = id !== null ? `/lineages/${id}/tree` : null;   // null key = disabled
const { data, error, isLoading, mutate } = useSWR<TreeOut>(path, fetcher);
return { tree: data, isLoading, error, mutate };            // renamed, never raw `data`
```

The **null-key guard** is the universal "nothing selected yet" idiom. Writes go
through `putJson` / `lib/api.ts` and then call the hook's own `mutate()`; cross
-hook invalidation uses `useSWRConfig().mutate(key)` (e.g. every version action
revalidates both the lineage tree and the aeroplanes list). There is **no
global `SWRConfig` provider** — no shared `refreshInterval`,
`revalidateOnFocus` policy, error retry policy or global `onError`. 🔴

**Two HTTP clients coexist.** `lib/api.ts` is the richer one — a typed
`ApiError(status, message, details)`, `Content-Type` header, `204 → undefined`
— but the SWR hooks use `lib/fetcher.ts`, which throws a plain
`Error("404 Not Found: <body>")`. `lib/parseApiError.ts` exists to paper over
the difference. 🔴

**SSE is parsed by hand.** `lib/sseStream.ts` reads `response.body` as a
`ReadableStream` because *"the browser's built-in `EventSource` only works with
GET requests"* and both streams here are POST. It buffers the trailing
incomplete record across chunk boundaries and falls back to the raw string when
a `data:` payload is not JSON. Two consumers: the copilot stream and the
OpenVSP import progress (gh-737).

### State management 🟢 CONFIRMED

No Redux / Zustand / Jotai. Four mechanisms:

1. **React context** — `AeroplaneContext` (aeroplaneId, selectedWing,
   selectedXsecIndex, selectedFuselage, selectedFuselageXsecIndex,
   `treeMode: "wingconfig" | "asb" | "fuselage"`, pickerOpen,
   lastImportWarnings, `hydrated`) and `UnsavedChangesContext`.
2. **URL search params** — `?aeroplane=<uuid>` is the source of truth;
   `setAeroplaneId` does a `router` replace and mirrors to `localStorage`.
3. **SWR cache** — all server state.
4. **`localStorage`** — `da3dalus_aeroplane_id`, plus per-feature keys in
   `CopilotStrip`, `WorkbenchImportWarningBanner`, `ImportWarningBanner`,
   `StabilityOverlay` and `lib/versionGraphViewState.ts` (version-graph
   pan/zoom).

`hydrated` is exposed so pages don't flash "no aircraft selected" on the first
client render.

### The 3D viewer 🟢 CONFIRMED

`CadViewer.tsx` imports the CSS **statically** (`import
"three-cad-viewer/css"`, l.6) and the library **dynamically at runtime**
(`const tcv = await import("three-cad-viewer")`, l.90). That asymmetric pattern
is deliberate and fragile — the project memory records that it must never be
changed without real browser testing.

`next.config.ts` aliases `three` to one resolved path in **both** the webpack
and the turbopack resolver, so the app and `three-cad-viewer` share a single
three.js instance.

`useTessellation` keeps a **module-level `Map`** keyed by
`` `${aeroplaneId}/${wingName}` `` and validates it against the aeroplane's
`updated_at` before reuse; `invalidateTessellationCache(id, wing)` is exported
so a geometry save restores the "Preview 3D" affordance. The cache is per-tab
and unbounded (no eviction, no size cap). 🟡

### 🔴 GAPs

* **The documented CORS strategy is not implemented.** `frontend/CLAUDE.md`
  says all API calls go through server-side route handlers or server actions;
  there are none, and every call is a direct browser → FastAPI fetch. The
  backend's wildcard CORS is the consequence, not an independent choice.
* **Two HTTP clients with two error shapes** (`lib/fetcher.ts` plain `Error`
  vs `lib/api.ts` typed `ApiError`), bridged by `lib/parseApiError.ts`.
* **No global `SWRConfig`** — no shared revalidation policy, retry policy or
  error handler; each of the 48 hooks decides for itself.
* **Backend response types are hand-mirrored.** Only `types/versioning.ts` and
  `types/versionGraph.ts` are shared; every other interface is redeclared
  inside its hook (`useCopilot.ts` comments *"mirror
  app/schemas/copilot_history.py"*). Nothing is generated from
  `/openapi.json`, so a backend schema change is caught only by `tsc` against
  hand-written fixtures — the exact failure mode the CI note warns about.
* **`react-plotly.js` is an unused dependency.**
* **Seven components exceed 1 000 lines** (`AnalysisViewerPanel` 1 567,
  `MatchingChartTab` 1 518, `AeroplaneTree` 1 197, `PowertrainTab` 1 190,
  `VersionGraphOverlay` 1 117, `OperatingPointsPanel` 1 076,
  `AnalysisConfigPanel` 1 063) — the tab pages are thin, the panels are not.
* **`components/ui/` holds a single primitive.** There is no design-system
  boundary; shared primitives sit flat among feature components, which is why
  `frontend/CLAUDE.md` needs an explicit "reuse before creating" checklist.
* **`metricsMock.ts` ships inside the metrics-dashboard component folder** —
  mock data in the production tree. 🟡
* **The tessellation cache is module-level and unbounded**, keyed without a
  size or age limit; only an `updated_at` mismatch evicts an entry.
* **`useCopilot.TOOL_LABEL_MAP` covers 3 of 6 copilot tools**
  (`get_wing_geometry`, `apply_design_edits`, `discard_proposal` fall through
  to `Calling <name>…`) — the two write tools, whose activity matters most to
  the user, are the unlabelled ones.
* **Plotly dark theming is duplicated per figure** instead of a shared layout
  template.
* **Dark theme only** — no light mode, no `prefers-color-scheme` support.
* **`next` is pinned to a canary build** (`16.2.1-canary.33`, matched by
  `eslint-config-next`), and `frontend/AGENTS.md` warns that this Next.js
  differs from documented/trained behaviour.
* **The frontend never touches `/mcp`** — MCP is for external agents only; the
  in-app AI path is the copilot SSE endpoint.
