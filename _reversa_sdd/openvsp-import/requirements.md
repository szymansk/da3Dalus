## Overview

`openvsp-import` turns a NASA OpenVSP `.vsp3` file into a new da3Dalus
aeroplane: it drives the `openvsp` SWIG bindings to read the model, dispatches
each geom to a type-specific handler, derives wing planforms and fuselage
cross-sections, generates or exports the airfoil `.dat` files the rest of the
stack needs, detects and normalises the source length unit, applies an optional
RC rescale, persists everything through the ordinary aeroplane/wing/fuselage
services, and exports a per-geom STEP artefact (plus a sewn solid) for the CAD
pipeline. Its scope is deliberately **"RC-scaling inspiration"** — geometry and
mass *positions* only. 🟢

The module's defining characteristic is its **error policy**: an import is a
best-effort, lossy translation, and almost nothing aborts it. Everything the
importer cannot represent becomes a structured `ImportWarning` that reaches the
frontend banner. 🟢

## Responsibilities

- Read a `.vsp3` file through the optional `openvsp` binding, resetting the
  library's **process-global** model before every read. 🟢
- Canonicalise each geom's type token and dispatch it to a registered handler,
  warning (and marking the component lossy) for the 14 unsupported types. 🟢
- Derive a wing planform — cumulative leading-edge position, dihedral, twist and
  leading-edge sweep — from VSP's per-section parms. 🟢
- Derive fuselage superellipse cross-sections, optionally refined by slicing the
  exported STEP. 🟢
- Resolve each x-section's airfoil to a `.dat` file: generate NACA 4-/5-/6-/16-
  series geometry, export a Selig file verbatim, or fall back — **never
  raising**. 🟢
- Turn `BLANK` geoms into weight items and resolve the vehicle CG. 🟢
- Detect a non-metre source length unit by measurement (OpenVSP 3.50 stores
  none) and convert the whole aeroplane to metres before anything else. 🟢
- Apply one optional, bounded, mutually exclusive rescale (`target_span_m` XOR
  `scale_factor`) to lengths only. 🟢
- Persist the result as a new aeroplane, per-record best-effort. 🟢
- Export a per-geom surface STEP forced to metres, sew it into a closed solid,
  and clean both up when the aeroplane is deleted. 🟢
- Collect every loss, approximation and conversion as a structured warning, and
  stream progress over SSE. 🟢

**Explicitly NOT this module's responsibility:** the fuselage slicer internals
and superellipse fitting (→ `fuselage-design`; this module only *gates* and
*consumes* the slicer), the wing station/segment model and the terminal-station
rule BR-5 (→ `wing-design`; this module is a *client* of it), airfoil catalogue
storage, classification and scoring (→ `airfoil-catalog`), aeroplane and
weight-item persistence semantics (→ `aeroplane-core`, `mass-and-balance`), the
CAD construction pipeline that consumes the STEP artefacts
(→ `cad-generation`, `construction-plans`), and any aerodynamic analysis of the
imported aircraft (→ `aero-analysis`). Deliberately out of scope by ADR 0018:
propulsion, inertia tensors, control-surface group gains, VSPAERO validation and
leading-edge devices.

### Scope and error policy

- **BR-73 — Import scope is "RC-scaling inspiration".** 🟢 Geometry and mass
  *positions* only. An OpenVSP model of a full-size aircraft carries propulsion
  definitions, inertia tensors, control-surface group gains and VSPAERO setups
  that are meaningless or actively wrong once the airframe is scaled to a 1.5 m
  span and 2 kg mass; importing them would produce numbers that *look*
  authoritative and are not. [ADR 0018](../adrs/0018-openvsp-import-scope-is-rc-scaling-inspiration.md).
- **BR-74 — Nothing aborts an import except three errors.** 🟢 Only
  `ImportError` (the `openvsp` package is missing), `FileNotFoundError` (the
  upload vanished) and `ScaleValidationError` (bad scaling inputs) propagate.
  Handler failures, post-pass failures, per-record persistence failures,
  undetectable units, unavailable or rejected slicer output and failed sewing
  all degrade into structured warnings
  (`openvsp_importer.py:401-410`; `openvsp_import_service._record_persist_failure`).
- **BR-OV4 — Every loss is a structured warning, never a silent drop.** 🟢
  `ImportContext.add_warning` (`openvsp_importer.py:98-141`) appends an
  `ImportWarning(component_type, component_name, reason, severity)` with
  `severity ∈ {info, warning, error}` validated on write; `mark_lossy(gid)`
  maintains a **de-duplicated** `lossy_components` list. Both reach the frontend
  banner (gh-648). `_UNSUPPORTED_REASONS` (l.242-260) supplies a user-facing
  reason for 14 geom types: `PROP`, `DISK`, `MESH`, `CONFORMAL`, `NGON_MESH`,
  `HUMAN`, `POD`, `BOR`, `STACK`, `ELLIPSOID`, `WIRE_FRAME`, `HINGE`,
  `PT_CLOUD`, `GEAR`.

### The OpenVSP binding is process-global

- **BR-OV1 — `ClearVSPModel()` before every `ReadVSPFile`.** 🟢 The `openvsp`
  SWIG module owns a **single native VSP model** for the whole process. Without
  the explicit clear, `ReadVSPFile` **merges** the new file into whatever is
  already loaded, so a second import would silently inherit the first aircraft's
  geoms. This is the first step of the gh-640 critical sequence
  (`openvsp_importer.import_vsp3:324-420`).
- **BR-OV2 — Importer state survives `uvicorn --reload`; the process must be
  restarted.** 🟢 `openvsp_adapter` memoises the optional import in three module
  globals — `_cached_module`, `_import_attempted`, `_import_error` (l.53-55) —
  with `reset_for_tests()` (l.92-97) as the **only** reset;
  `openvsp_importer` adds `_handlers_loaded`, `_HANDLERS`, `_POST_PASSES`
  (l.181-182, 284); and the SWIG module holds the native model. Editing importer
  code and relying on `--reload` therefore tests the *old* code. This is an
  operational rule, not a footnote.
- **BR-OV3 — Geom types must be canonicalised before dispatch.** 🟢
  `GetGeomTypeName(gid)` returns **Title-Case display names** (`"Wing"`,
  `"BodyOfRevolution"`) while `AddGeom` / `GetGeomTypes` use **UPPERCASE
  tokens**. `_DISPLAY_TO_CANONICAL` (`openvsp_importer.py:194-211`, 16 entries)
  normalises, falling back to `.upper()` for unknown names. Verified against
  OpenVSP 3.50.4.
- **BR-OV15 — Persistence is per-record best-effort.** 🟢 Each wing, fuselage
  and weight item is written inside its own `try/except`; a failure becomes a
  `WING` / `FUSELAGE` / `WEIGHT_ITEM` warning via `_record_persist_failure` and
  the remaining records still persist
  (`openvsp_import_service._persist_aeroplane:804-1020`).

### Units and scaling

- **BR-76 — Source units are measured, not trusted (gh-808).** 🟢 OpenVSP 3.50
  removed both `SetLengthUnit` and the `Vehicle_Info/LengthUnit` parm, so a
  `.vsp3` file carries **no unit at all** and a feet model would import 3.28×
  too large. The importer exports the largest-X-span fuselage to STEP (which VSP
  always writes metric), measures its bounding box, and treats
  `metric_span / handler_span` as the unit factor
  (`_detect_source_scale_to_meters`, `openvsp_import_service.py:147-201`).
- **BR-OV10 — The two scaling options are mutually exclusive and bounded.** 🟢
  `SCALE_FACTOR ∈ (0.001, 10.0)`, `TARGET_SPAN ∈ (0.1, 50.0) m`
  (`openvsp_import_service.py:78-81`). Supplying both is a **request-shape**
  error → HTTP **400**; an out-of-range value, or `target_span_m` on a wingless
  aeroplane, raises `ScaleValidationError` → HTTP **422**.
  `_compute_max_wing_span` uses `2·max|y_le|` for a symmetric wing and
  `max|y_le|` otherwise.
- **BR-75 — Scaling never touches angles or masses.** 🟢
  `_scale_aeroplane_lengths` (l.254-293) scales wing `xyz_le` and `chord`,
  `aeroplane.xyz_ref` and weight-item `x_m/y_m/z_m`. It deliberately does **not**
  scale twist (angular), masses (the ADR 0018 "Variante B" decision), or
  fuselages. A scaling run **always** appends an `info` warning saying the masses
  were left untouched (`_make_scaling_warning`).
- **BR-OV11 — The scaling order is load-bearing.** 🟢
  1. Source-unit conversion of the **whole** aeroplane, including fuselages
     (`_convert_aeroplane_to_metres`) — before anything else, so target-span
     resolution and the slicer both work in metres.
  2. `_resolve_scale_factor` + `_scale_aeroplane_lengths` — wings, `xyz_ref` and
     weight positions only.
  3. Fuselage x-secs scaled **last**, inside `_persist_aeroplane`, *after* the
     slicer refinement, so the slicer keeps running in the **unscaled** STEP
     frame (gh-765); the stored STEP files are then rescaled with
     `scale_geom_step` (gh-769).
  Getting this order wrong silently mismatches the schema and the STEP artefact.

### Wing planform derivation

- **BR-OV5 — Dihedral accumulates trigonometrically (gh-755).** 🟢 The span
  advance is projected, not taken flat:

  ```
  cum_x += Span · tan(Λ_LE)
  cum_y += Span · cos(cum_dihedral)      ← NOT `+= Span`
  cum_z += Span · sin(cum_dihedral)
  ```

  The pre-gh-755 small-angle shortcut `cum_y += span` mis-placed every station
  on winglets and V-tails above ~5° dihedral
  (`openvsp_wing_handler.py:985-989`). A re-implementation must not reintroduce
  it. Dihedral and twist honour the per-wing `RelativeDihedralFlag` /
  `RelativeTwistFlag`: relative ⇒ accumulate, absolute ⇒ assign.
- **BR-OV6 — Sweep is absolute per section; the reference must be changed
  explicitly.** 🟢 VSP stores sweep at a per-section `Sweep_Location`, with no
  relative flag and no accumulation (comment cites `WingGeom.cpp:1111`).
  Converting it to leading-edge sweep uses

  ```
  tan(Λ_to) = tan(Λ_from) − (xref_to − xref_from)·(c_root − c_tip)/span
  ```

  and returns `Λ_from` unchanged when `span ≤ 0` (`sweep_at_le`).
- **BR-OV7 — The last x-section must carry no segment data.** 🟢 The wing
  handler sets `x_sec_type = None` on the final x-section
  (`openvsp_wing_handler.py:994-1005`) precisely so that
  `AsbWingSchema.validate_last_xsec_has_no_segment_details` accepts the payload.
  This module is a **client** of `wing-design`'s BR-5 terminal-station rule, not
  its owner.
- **BR-OV18 — A degenerate section is skipped, not repaired.** 🟢 `Span ≤ 0`
  produces a warning, `mark_lossy`, and the section is skipped;
  `Root_Chord ≤ 0` warns and defaults to `1.0 m`
  (`openvsp_wing_handler.py:902-910`). `_read_section_parm` (l.109-121) tries
  group `XSec_{i}` first, falls back to `XSec_{i-1}`, and returns `0.0` when the
  parm is absent.

### Airfoils

- **BR-OV8 — Airfoil resolution never raises.** 🟢
  `import_airfoil_from_xsec` (`openvsp_airfoil.py:963-1180`) switches on
  `vsp.GetXSecShape(xs_id)` and always yields a usable `.dat`, degrading through
  generation → verbatim Selig export → sampled export → the last-resort
  `./components/airfoils/naca0012.dat`. Approximations (6-series, 16-series,
  CST) emit an `info` warning stating what is exact and what is not.
- **BR-OV9 — Generated `.dat` files are deduplicated and content-addressed.** 🟢
  `write_imported_airfoil_dat` (l.731-750) runs
  `_dedup_consecutive_points(tol=1e-9)` — the gh-789 fix for AeroSandbox's
  `repanel()` duplicate-point crash — then hashes the coordinates and **skips
  the write** when the content is unchanged, so repeated imports do not churn
  the airfoil directory.

### STEP artefacts

- **BR-OV13 — STEP export is forced to metres.** 🟢
  `_set_step_export_length_unit_metres` sets `STEPSettings.LenUnit = LEN_M`
  before `vsp.ExportFile(target, SET_USER, EXPORT_STEP)`
  (`openvsp_step_export_service.py`). `_VSP_USER_SET = 3`. This is what makes
  BR-76's measurement trustworthy.
- **BR-OV14 — Sewing is a two-tolerance ladder and never aborts.** 🟢
  `BRepBuilderAPI_Sewing` at `_SEW_TOLERANCE_TIGHT = 0.001` (1 mm in the STEP's
  metre units); if no shells come out, retry at `_SEW_TOLERANCE_LOOSE = 0.005`
  (5 mm — the documented ceiling before the nose cap would stitch itself to the
  tail). Then `ShapeFix_Solid` behind a `BRepCheck` gate, reversing when the
  resulting volume is negative, merging or compounding multiple solids, and
  writing `<stem>_solid.stp`. Failure leaves `solid_step_path` **NULL** rather
  than aborting (`openvsp_solid_sewing_service.py:68-74`).
- **BR-77 — Prefer the surface STEP over the sewn solid for slicing (gh-812).**
  🟢 The sewn solid carries internal seam faces at sharply curved loft regions
  (the Romo nose-body fillet) that fragment a section cut and drift the section
  centre laterally into a kink. `_select_xsec_slice_source`
  (`openvsp_import_service.py:562-575`) therefore prefers the surface STEP. The
  solid is still produced for the construction download — 🟢 **Detect the unusable solid, record the state, and fall back to a solid lofted from the stored superellipse x-secs** (`Q-VI-4`, maintainer-answered). The maintainer needs a valid solid for the Creator classes — not for Fusion360 — and must be able to tell when one is defective.
- **BR-OV12 — Fuselage refinement is gated four ways.** 🟢
  1. `_is_x_dominant_fuselage` (l.494-520): refine only when the **handler**
     x-sec positions give `extent_x ≥ 1.2·extent_y` **and** `≥ 1.2·extent_z`.
     Using the handler schema rather than the STEP bounding box is essential —
     a `symmetric=True` geom's STEP contains both halves and looks Y-dominant.
  2. Station budget `min(80, max(15, n + 5·(n−1)))` for `n` handler x-secs, fed
     to `vsp_anchored_x_stations`: VSP-defined stations are mandatory anchors,
     intermediates distributed weighted by shape change (gh-732).
  3. Slice source per BR-77.
  4. `_slicer_frame_matches_handler` (l.543-559): accept only when
     `0.5 ≤ x_span(refined)/x_span(handler) ≤ 2.0`
     (`_SLICER_FRAME_RATIO_MIN/MAX`, gh-803); otherwise the handler schema wins.
  Sewing and refinement are both nested under a successful surface export — no
  surface STEP means no solid and no refinement. 🟢

### Known-inert paths — all now wired (🟢 `Q-VI-1`, `Q-VI-2`)

- 🟢 **Wired fully — registration AND the write path** (`Q-VI-1`, maintainer-answered). Previously dead twice over:
  1. `openvsp_ss_control.register()` is **never called in production**. It is
     absent from `_ensure_handlers_loaded` (`openvsp_importer.py:287-321`) and a
     repository-wide grep finds exactly one caller,
     `app/tests/test_openvsp_ss_control.py:24`. The gh-644 SS_CONTROL →
     `TrailingEdgeDevice` post-pass therefore never runs during a real import,
     while the unit tests pass because they register it themselves.
  2. Even if it ran, the TED could not survive persistence:
     `_persist_aeroplane` writes wings through `AsbWingGeometryWriteSchema`
     (`app/schemas/aeroplaneschema.py:695-708`, `extra="forbid"`) whose
     `WingXSecGeometryWriteSchema` (l.592-630) carries only `xyz_le`, `chord`,
     `twist`, `airfoil`, `x_sec_type`, `tip_type` and
     `number_interpolation_points` — **no `trailing_edge_device` field at all**
     (`openvsp_import_service.py:846-865`).
  Imported aircraft consequently arrive with **no control surfaces**, and fixing
  only the registration would not change that.
- 🟢 **`validate_geometry` is wired in** (`Q-VI-2`, maintainer-answered): the gh-647 cross-check is what would have caught the whole class of import defects, including the unit errors. Previously shipped but inert:
  `openvsp_validation.validate_geometry` — the gh-647 span / area / MAC /
  fuselage-length cross-check against VSP's own `TotalSpan`,
  `TotalProjectedArea` (fallback `TotalArea`), `TotalChord` (fallback `MAC`) in
  the `WingGeom` group and `Length` in `Design`, at
  `DEFAULT_REL_TOL = 0.01` — is referenced only from
  `app/tests/test_openvsp_validation.py`. Its own module docstring shows the
  intended wiring (`result.warnings.extend(mismatches)`), which does not exist
  in `import_vsp3`.
- 🟡 **A failed handler registration is reported, not swallowed** (`Q-VI-7`, derived from `P-WARN-0`). Previously swallowed. Each of the four
  handler imports in `_ensure_handlers_loaded` sits in its own
  `try: … except ImportError: pass`, so a broken handler module degrades into
  "every geom of that type is unsupported" with no diagnostic at all.

## Acceptance Criteria

```gherkin
Feature: Importing a .vsp3 file

  Scenario: A well-formed model imports as a new aeroplane
    Given the openvsp bindings are installed
    And a valid "cessna172.vsp3" with 2 wings and 1 fuselage
    When I POST it to /api/v2/import/openvsp
    Then the response status is 201
    And aeroplane_name is "cessna172"
    And n_wings is 2 and n_fuselages is 1
    And a new aeroplane row exists with that uuid

  Scenario: A non-vsp3 upload is rejected before any parsing
    Given the openvsp bindings are installed
    When I POST a file named "model.stl"
    Then the response status is 400
    And no aeroplane is created

  Scenario: The bindings are missing
    Given the openvsp package is not installed
    When I POST a valid .vsp3 file
    Then the response status is 503
    And the detail points at docs/md/openvsp-import-setup.md

  Scenario: A second import does not inherit the first model
    Given I have already imported model A in this process
    When I import model B
    Then the created aeroplane contains only B's geoms
    # ClearVSPModel() runs before ReadVSPFile — without it VSP MERGES

Feature: Lossy translation is reported, never hidden

  Scenario: An unsupported geom becomes a warning
    Given a .vsp3 containing a PROP geom
    When I import it
    Then the response status is 201
    And warnings contains an entry with component_type "PROP"
    And lossy_components contains that geom id

  Scenario: A degenerate wing section is skipped
    Given a wing section whose Span is 0
    When I import the file
    Then that section is absent from the persisted wing
    And a WING_XSEC warning names it
    And the geom id is marked lossy

  Scenario: A failing post-pass does not fail the import
    Given a post-pass that raises
    When I import the file
    Then the response status is 201
    And a warning with component_type "POST_PASS" is present

Feature: Wing planform derivation

  Scenario: Dihedral is accumulated trigonometrically
    Given a wing section with Span 1000 and cumulative dihedral 30 degrees
    When the planform is derived
    Then the station advances by Span * cos(30 degrees) in y
    And by Span * sin(30 degrees) in z
    # The pre-gh-755 shortcut advanced y by Span and must not return

  Scenario: The terminal x-section carries no segment data
    Given any imported wing
    When it is validated as an AsbWingSchema
    Then validate_last_xsec_has_no_segment_details passes
    And the last x-section's x_sec_type is null

Feature: Source-unit detection

  Scenario: A feet model is converted to metres
    Given a fuselage whose metric STEP span is 0.3048 times the handler span
    When I import the file
    Then the whole aeroplane is multiplied by 0.3048
    And a UNITS warning of severity "warning" names "ft"

  Scenario: An undetectable unit leaves the import unchanged
    Given a model with no fuselage
    When I import the file
    Then no unit conversion is applied
    And no UNITS warning is emitted
    # 🟡 **No silent scale — unit resolution follows the declared unit; a wing-only model without one is reported, not guessed** (`Q-VI-3`, derived).

Feature: Optional rescaling

  Scenario: Rescaling to a target span leaves masses alone
    Given a model whose largest wing span is 10 m
    When I import it with target_span_m=2.0
    Then every wing xyz_le and chord is multiplied by 0.2
    And every weight item mass is unchanged
    And an info SCALING warning states that masses were not scaled

  Scenario: Supplying both scaling parameters is a request-shape error
    When I POST with target_span_m=2.0 and scale_factor=0.5
    Then the response status is 400
    And the detail says they are mutually exclusive

  Scenario: An out-of-range scale factor is a semantic error
    When I POST with scale_factor=20.0
    Then the response status is 422

Feature: STEP artefacts

  Scenario: A fuselage yields a metric surface STEP and a sewn solid
    Given a clean single-body fuselage geom
    When I import the file
    Then the fuselage row has step_path under openvsp_imports/<uuid>/
    And it has a solid_step_path ending in _solid.stp

  Scenario: An unsewable geom still imports
    Given a fuselage whose faces cannot be sewn at 1 mm or 5 mm
    When I import the file
    Then the response status is 201
    And solid_step_path is null
    And step_path is still set

Feature: Control surfaces (currently unreachable)

  Scenario: An SS_CONTROL sub-surface becomes a trailing-edge device
    Given a wing carrying one SS_CONTROL sub-surface with LE_Flag 0
    When I import the file
    Then the inboard x-section of the mapped segment has a trailing_edge_device
    And its rel_chord_root equals 1 - Length_C_Start
    # 🟢 **Wired fully — registration AND the write path** (`Q-VI-1`, maintainer-answered). (fails today: never registered, and the persistence
    #    write schema has no trailing_edge_device field (BR-OV16)
```

## Priority (MoSCoW)

| Requirement | MoSCoW | Rationale |
|-------------|--------|-----------|
| The `import_vsp3` critical sequence (RF-05…RF-07) | Must | `ClearVSPModel` ordering and type canonicalisation are the two things that silently corrupt an import when wrong |
| Wing planform derivation (RF-08…RF-12) | Must | The whole point of the import; the gh-755 dihedral bug shipped once already |
| Airfoil resolution with a total fallback chain (RF-13/RF-14) | Must | Every downstream aero and CAD path needs a readable `.dat`; a raise here would abort an otherwise good import |
| Source-unit detection and conversion (RF-16/RF-17) | Must | Without it a feet model is 3.28× wrong with no signal at all |
| Bounded, mutually exclusive rescaling in the documented order (RF-18…RF-20) | Must | Order errors mismatch the schema against the STEP artefact; ADR 0018 forbids scaling masses |
| Best-effort persistence and the three-exception error policy (RF-21, BR-74) | Must | The module's defining contract — an import is a lossy translation, not a transaction |
| Upload guards and the 503/400/413/422 mapping (RF-02…RF-04) | Must | Cheap, and they keep a missing optional dependency out of the 5xx bucket |
| Surface STEP export forced to metres (RF-22) | Must | Both the CAD pipeline and BR-76's measurement depend on it |
| Solid sewing (RF-23) | Should | Only the construction download needs it; NULL is an accepted outcome, and #814 means the output is not always usable anyway |
| Fuselage x-sec refinement gates (RF-24) | Should | A refinement — the handler schema is a correct fallback in all four rejection cases |
| BLANK → weight items and the vehicle-CG post-pass (RF-15) | Should | Mass *positions* are in scope, but an aircraft imports usefully without them |
| SSE progress streaming (RF-27) | Should | UX for a slow operation; the non-stream endpoint is the contract of record |
| STEP filename sanitisation and artefact cleanup (RF-25/RF-26) | Should | Hygiene; a leaked directory is not user-visible |
| Wiring SS_CONTROL end to end (RF-29) | **Must** | 🟢 wired (`Q-VI-1`) — registration **and** the write path; previously two independent blockers (BR-OV16); the user can re-tag control surfaces in the UI afterwards, which was always the intent (`role = OTHER`) |
| Wiring `validate_geometry` (RF-30) | **Must** | 🟢 wired (`Q-VI-2`); previously shipped and tested but inert. It adds confidence, not capability |
| Propulsion, inertia tensors, CS-group gains, VSPAERO validation, leading-edge devices | Won't | Deliberately out of scope by ADR 0018 — importing them would produce authoritative-looking wrong numbers |
| `XS_GENERAL_FUSE` / `XS_FILE_FUSE` / `XS_EDIT_CURVE` polyline sampling; STEP fallback for CUSTOM / CONFORMAL / NGON_MESH | Won't (this iteration) | Open epic #638, B5 and B6 |
