## R2-01 — Does downloading an STL of a STEP-stored part leak a temp file on every request?

**Context:** `construction-plans` — `download` (`construction_part_service.py:276-280`).
Requesting `format=stl` for a part stored as STEP regenerates the mesh into a
`tempfile.mkstemp` file, returns it to the client, and **never removes it**. Every such
download leaves a file behind for the process lifetime.
**Spec affected:** [`construction-plans/construction-parts/requirements.md`] (BR-CP7)
**Question:** Delete after send (a background task or a streaming response that cleans
up), or cache the regenerated STL next to the STEP under `ARTIFACTS_BASE_DIR` so the
second request is free?
**Impact:** Caching also answers whether STL is a derived artefact or a transient view.

**Answer:** **✅ Answered by the maintainer, 2026-08-16** (option b) — **cache the regenerated STL next to its STEP under `ARTIFACTS_BASE_DIR`; the second request is free.**

This settles a question the spec left open: **STL is a derived artefact, not a transient view.** Once it is one, `Q-CP-9 ②`'s containment helper covers it like every other artefact, and the leak disappears by construction — there is no temp file to clean up because nothing writes to `tempfile.mkstemp` any more.

**Consequences to carry into the implementation:**
- The cached STL is **invalidated with its STEP**. A part whose geometry is regenerated must not serve a stale mesh — that would be an undeclared substitution (ADR 0020).
- It joins the retention question `Q-VS-2` owns for snapshots: derived meshes accumulate per part and per format.
- The mesh parameters (deflection, angular tolerance) become part of the cache identity, or a request for a finer mesh silently returns the coarse one.

## R2-02 — After the Alembic migration, can a legacy plan root still arrive?

**Context:** `construction-plans` — `_migrate_tree_json` currently rewrites the legacy
root shape **lazily on read**. `Q-CP-7` converts it to a one-off Alembic data migration.
**Spec affected:** [`construction-plans/plan-template-lifecycle/design.md`]
**Question:** Once the migration has run, is the lazy path **dead** (delete it,
`P-DEAD-0`), or can a legacy root still enter through an import, a restored backup or a
hand-written plan JSON — in which case it stays as a validating guard?
**Impact:** Decides delete-vs-keep for a code path, and whether stored plans need the
schema version that `cad-designer-topology` flagged (`TM-03`).

**Answer:** **✅ Answered by the maintainer, 2026-08-15** (option a) — **once the Alembic migration has run, the lazy path is dead and is deleted** (`P-DEAD-0`).

`Q-CP-7` converts `_migrate_tree_json` into a one-off data migration, after which no stored row carries the legacy root shape. Keeping a read-time rewriter for a shape that cannot exist is the *inert* state `P-DEAD-0` forbids.

> **One guard the deletion requires, recorded rather than assumed.** If a legacy root *does* arrive later — a restored pre-migration backup, a hand-written plan JSON, an import — the decoder currently answers with a bare `AttributeError` naming only the missing class (`cad-designer-topology`, `$TYPE` dialect). With the rewriter gone that becomes the *only* response. Per **`P-WARN-0`** it must instead be a legible error naming the plan, the step and the unrecognised shape, and saying that it predates the migration. The deletion is safe; the diagnostic is what makes it safe.

This also settles the related `TM-03` note in `cad-designer-topology`: a schema version on stored plans is **not** needed to solve this particular problem, because the migration removes the variant rather than teaching the reader to distinguish it.

## R2-03 — Should one unconvertible wing degrade the plan, or fail the run?

**Context:** `construction-plans` — `execute_plan` (`:650-654`). A per-wing
`wing_model_to_wing_config` failure logs and **continues**, so the plan executes against a
silently reduced aircraft. `Q-CP-3` decided the failure emits a `DesignWarning`; it did
not decide whether degrading is right at all.
**Spec affected:** [`construction-plans/plan-execution/requirements.md`]
**Question:** Is a partially converted aircraft a legitimate result (warn and continue),
or should the run fail so the user fixes the wing first?
**Impact:** A construction plan produces *physical parts*. A silently missing wing yields
a buildable but incomplete set.

**Answer:** **✅ Answered by the maintainer, 2026-08-16** (option a) — **a plan run fails when a wing cannot be converted. Degrading is withdrawn.**

`Q-CP-3` had decided the failure emits a `DesignWarning`; this decides that warning is not enough. **The distinction is that a construction plan produces physical parts.** A degraded *analysis* still informs — the user sees a number and can judge it. A degraded *plan* yields a complete-looking, buildable part set with a wing missing: the warning is in the response body, and the laser-cut pattern is not.

`execute_plan` (`:650-654`) therefore stops logging-and-continuing. A per-wing `wing_model_to_wing_config` failure aborts the run and reports which wing failed and why, so the user fixes it and re-runs.

**The `DesignWarning` from `Q-CP-3` is not discarded** — it remains the mechanism for degradations that *are* legitimate elsewhere in the module. It simply no longer applies to this one, because this one is now an error.

## R2-04 — Branch names: `rename` checks for collisions, `create` does not.

**Context:** `versioning` — `rename_branch` runs a name-collision query;
`create_branch` runs none. Two branches can therefore be created with the same name, and
only a later rename complains.
**Spec affected:** [`versioning/branch-model/requirements.md`]
**Question:** Should `create_branch` enforce the same uniqueness (per `root_id`), or are
duplicate branch names acceptable because the UUID is the identity — as decided for
`aeroplanes.name` in `Q-AC-2`?
**Impact:** If names must be unique, it is a constraint plus a migration; if not, the
rename check is the outlier and should go.

**Answer:** **✅ Answered by the maintainer, 2026-08-16** (option b) — **branch names are unique per `root_id`. `create_branch` gains the check, backed by a partial unique index.**

_This is the opposite of my recommendation, and the maintainer's reason is the deciding one:_ *"Branch-Namen sollten eindeutig sein. IDs kann ich als Benutzer nicht sehen und mir auch nur schwer merken."*

**Why this does not contradict `Q-AC-2`**, which ruled that `aeroplanes.name` must stay **non**-unique. The two look alike and are structurally different:

| | duplicated by | can be unique? |
|---|---|---|
| `aeroplanes.name` | **construction** — a version is a real `aeroplanes` row and `aeroplane_clone_service.py:187` copies `name=source.name`, so a unique constraint would make every snapshot fail | **no** |
| branch name | nothing — it is a user-chosen label; **verified: no automatic operation duplicates one** | **yes** |

And the argument for uniqueness is a *usability* one, which is exactly where identity should live for an object a human picks from a list: the UUID is the technical identity, but a user never sees it and cannot recall it. A list with two entries called `experiment` is unusable regardless of what the rows are keyed on.

**No conflict with the copilot either:** `Q-CO-12` replaces `name LIKE 'copilot-proposal%'` with a typed `branch_kind` column and enforces **at most one open proposal per `root_id`**, and `Q-CO-1` puts the message id into the branch name — so proposal branches are distinct by construction and never rely on duplicate names.

**Implementation:** partial unique index on `(root_id, name)`; `create_branch` raises `ConflictError` → **409**, matching `Q-FD-1`'s discriminator (a create colliding with persisted state). The existing `rename_branch` check stops being the outlier and becomes the same rule applied to a second path.

## R2-05 — Should the versioning diff be computed server-side?

**Context:** `versioning` — the diff endpoint is **read-only**: it returns two payloads
and performs no comparison. Every consumer diffs them itself.
**Spec affected:** [`versioning/branch-model/design.md`]
**Question:** Should the server compute the diff? Note `Q-CO-6` already decided the
copilot gets a **real live-vs-proposal diff** — if that logic is built there, this is the
same computation with a second implementation (ADR 0022).
**Impact:** Decides whether one diff engine serves both, or the copilot's stays private.

**Answer:** **✅ Answered by the maintainer, 2026-08-15** (option a) — **one server-side diff engine; both the versioning endpoint and the copilot use it.**

Straight application of **ADR 0022**: a diff between two design subgraphs is one computation, and `Q-CO-6` has already committed to building it for the copilot (*"the field is made to match its name"*). Building it twice would give two answers to *"what changed?"* that drift the moment either side gains a field.

**Consequences:**
- The versioning endpoint stops being read-only. It keeps returning the payloads where a caller wants them, but gains the computed diff as the primary result.
- The copilot's `diff_vs_live` becomes a **caller** of that engine rather than an implementation. Its live-vs-proposal semantics are a parameter choice — which two nodes to compare — not separate logic.
- The engine must be aware of what `Q-VS-5` excludes (`construction_parts` are not cloned) so a diff does not report their absence as a change.

## R2-06 — Cloning a design does not clone its conversation.

**Context:** `versioning` — `EXCLUDED_TABLES` omits the copilot history; a note and a
cursor stand in for it.
**Spec affected:** [`versioning/aeroplane-clone-subgraph/requirements.md`]
**Question:** With conversation branching now planned (`Q-CO-5` — *"branching at a
snapshot should let the chat roll back too"*), should cloning a design also branch its
conversation, or does the chat branch **only** on an explicit user action?
**Impact:** This is the seam between the two branching models. Getting it wrong produces
either orphaned conversations or duplicated ones.

**Answer:** **✅ Answered by the maintainer, 2026-08-15** (option a) — **the conversation branches only on an explicit user action. A design clone leaves it untouched.**

**The decisive consequence:** the copilot clones a **full subgraph per proposal** (`Q-CO-12`). If cloning a design also branched its conversation, every proposal would fork the chat — producing a conversation tree nobody asked for, growing at the rate the copilot works rather than the rate the user decides.

**So the two branching models stay deliberately asymmetric:**

| trigger | design | conversation |
|---|---|---|
| copilot proposal | cloned subgraph | untouched |
| user branches at a snapshot | new branch | **may be rolled back with it** (`Q-CO-5`) |
| user clones a design | cloned subgraph | untouched |

The chat follows the design **only** when the user says so. `EXCLUDED_TABLES` therefore keeps the copilot history, and the note-plus-cursor stand-in stays — with `Q-CO-1`'s provenance link making the cursor resolvable back to the turn that produced the version.

## R2-07 — Snapshot immutability: is a database constraint wanted as well?

**Context:** `versioning` — `Q-VS-1` decided the guard moves into a write-resolver plus a
session-level check. Today immutability is a **checked convention**; only `snapshot`
guards it, and direct SQL bypasses everything.
**Spec affected:** [`versioning/snapshot-immutability/requirements.md`]
**Question:** Is the application-level guard sufficient, or should the database also
refuse writes to a snapshot row (trigger / partial constraint)?
**Impact:** ADR-0020 shape: an application guard that can be bypassed is a declared
protection with an undeclared hole.

**Answer:** **✅ Answered by the maintainer, 2026-08-16** (option c) — **defer to the PostgreSQL decision; `Q-CC-7` deliberately leaves that open.**

`Q-VS-1`'s application-level guard — the write-resolver plus a session-level check — ships now and is the working protection. A database-level trigger is **not** decided against; it is decided **later**, when the engine question is settled.

The reasoning: a trigger written for SQLite would very likely be rewritten for PostgreSQL, and `Q-CC-7` explicitly kept the engine open while migrating the three soft references to real foreign keys *for reasons that exist today under SQLite*. Immutability enforcement has no such today-reason — the application guard covers every path the application owns.

**What the spec must state plainly, so this is a declared boundary and not a silent hole (ADR 0020):** direct SQL bypasses snapshot immutability. That is accepted, and it is the same class of statement as the component-tree cascade in `Q-AC-10`, which stays in the DDL as a net the service never relies on.

## R2-08 — Cloning issues one UPDATE per node. Does it need to scale?

**Context:** `versioning` — the clone re-points ids with `WHERE id = id_map[node.id]`,
one statement per node. The copilot clones a **full subgraph per proposal** (`Q-CO-12`),
so this runs often.
**Spec affected:** [`versioning/aeroplane-clone-subgraph/design.md`]
**Question:** Is per-node UPDATE acceptable at your tree sizes, or should it be a bulk
update? What is the largest component tree you expect?
**Impact:** Purely non-functional — but it compounds with proposal cloning.

**Answer:** **✅ Answered by the maintainer, 2026-08-16** (option a) — **per-node `UPDATE` is acceptable; not changed.** Assumption stated: *"ein Flugzeug wird nicht mehr als 200 Komponenten haben."*

**Measured against the live database, and the headroom is large:** the biggest component tree holds **10 nodes**; the mean is **4.5**. The 200-component ceiling is roughly **20× the largest tree that exists**, so per-node statements are far from being the constraint even when the copilot clones a full subgraph per proposal (`Q-CO-12`).

> **⚠ The trigger I named was wrong, and the maintainer corrected it.** I assumed a
> rib-by-rib wooden wing under the planned `WingCreator` would push the tree into the
> hundreds. It will not: **the wing is defined in the tree, the ribs are not.** Ribs are a
> *manufacturing output* — a DXF with many ribs nested onto one board for the laser,
> exactly as STL/STEP carry many printed parts onto one plate. The tree holds the wing;
> the file holds the pieces.
>
> **And the part count is bounded by a design principle, not just by today's data:**
> *"Bei 3D-Druck-Flächen sollte sich die Anzahl der Komponenten auch klein halten. Jedes
> Zusammenfügen erzeugt eine Schwachstelle im Flügel."* Minimising parts is a
> **structural** goal, so the tree is small by intent rather than by coincidence.
>
> Distribution measured over all 135 tree-bearing rows (aircraft **and** their versions):
> 46 carry 3 nodes, 28 carry 4, the maximum is **10**. There is no realistic growth path
> to the hundreds, so per-node `UPDATE` is not an assumption awaiting a trigger — it is
> simply adequate.

## R2-09 — Export concurrency is limited per aeroplane, not globally.

**Context:** `cad-generation` — `cad_service.py:159-176` limits concurrent exports **per
aeroplane**. Exporting five aircraft at once runs five CAD jobs in parallel.
**Spec affected:** [`cad-generation/wing-export-task/requirements.md`]
**Question:** Intended, or should there be a global cap? On a single-user desktop
(ADR 0024) the machine is the limit, and CadQuery is memory-hungry.
**Impact:** One acceptance criterion, and it interacts with `Q-CP-1` routing plan
execution through the same pool.

**Answer:** **✅ Answered by the maintainer, 2026-08-16** (option b) — **one global cap; the per-aeroplane limit is removed.**

_This is not the option I recommended (I proposed keeping both), and the maintainer's choice is better founded._ The per-aeroplane limit existed to stop two exports of the same aircraft colliding in the shared `./tmp/exports` directory. **`Q-CG-2` removes that collision properly** by giving each execution its own directory under `ARTIFACTS_BASE_DIR`. With the race fixed at its source, the per-aeroplane limit guards nothing and only adds a second concurrency rule to reason about.

What remains is the real constraint: **the machine**. OCCT is memory-hungry, a finely meshed loft runs into gigabytes, and `Q-CP-1` routes plan execution through the **same** pool — so exports and plan runs now compete for the same four workers. A single global cap expresses exactly that and nothing else.

**Consequence, stated so it is not a surprise:** two exports of the *same* aeroplane may now run concurrently. That is safe because their outputs no longer share a directory — the safety comes from `Q-CG-2`, not from serialisation.

## R2-10 — CORS is wide open, with a comment admitting it was copied.

**Context:** `platform-core` — `app/main.py:234-237`:
`allow_origins=["*"], allow_methods=["*"], allow_headers=["*"]`, with the comment
*"copied from other python backends to resolve the cors origin problem"*.
**Spec affected:** [`platform-core/app-bootstrap-lifespan/contracts.md`]
**Question:** Keep it wide open — defensible under ADR 0024, since the tunnel is the
boundary and there is no authentication to protect — or narrow it to the frontend origin
now that `Q-FW-1` confirmed **SPA-direct is the architecture**?
**Impact:** Wide-open CORS plus the ngrok tunnel means any page a browser visits can call
your API while the tunnel is up. That is a real exposure, not a theoretical one.

**Answer:** **✅ Answered by the maintainer, 2026-08-15** (option a) — **narrow `allow_origins` to concrete origins: the dev frontend (`localhost:3000`) plus the ngrok domain, configurable through the merged `Settings` class (`Q-CC-4`).**

**Why this is not merely tidying.** ADR 0024 makes the tunnel the boundary, and that holds for *inbound* access. It does not hold for CORS, because CORS governs which **other websites** a browser will let read your API's responses. With `allow_origins=["*"]` and the tunnel up, any page the browser visits can call the API; the oauth2-proxy session rides along and the response is readable by the calling page. That is the ordinary route to data behind a login, and it is available for as long as the tunnel runs.

`Q-FW-1` removes the last argument for keeping it open: **SPA-direct is the architecture**, so there is exactly one legitimate origin per environment, and it is knowable.

**Implementation note:** the origin list belongs in the merged settings (`Q-CC-4`), not as a literal in `main.py` — the dev origin and the tunnel origin differ, and a hard-coded list would be edited per environment, which is how it drifted to `"*"` in the first place. The existing comment (*"copied from other python backends to resolve the cors origin problem"*) is deleted with the value it explains.

**Incidental finding, worth recording:** with `allow_origins=["*"]`, `allow_credentials=True` is **ignored by the browser** — the spec forbids the combination. So today's configuration is less exposed than it reads, by accident rather than design. Narrowing the origins makes `allow_credentials` meaningful again, so it must be set deliberately at that point.

## R2-11 — A cross-thread schedule that times out after 2 s is dropped silently.

**Context:** `platform-core` — `job_tracker` schedules onto the bound loop with a 2 s
timeout; on expiry it returns `None` and **the schedule is dropped with no error**.
**Spec affected:** [`platform-core/background-jobs-invalidation/requirements.md`]
**Question:** Should the drop raise, or emit a `DesignWarning` (`P-WARN-0`), or is 2 s
generous enough that expiry means the loop is already broken — in which case the right
answer is to fail loudly at that point, as `Q-PC-7` does for `bind_loop`?
**Impact:** A dropped schedule means a recompute or retrim never runs, and nothing says so.

**Answer:** **✅ Answered by the maintainer, 2026-08-16** (option a) — **a schedule that cannot reach the loop fails loudly, exactly as `bind_loop` does (`Q-PC-7`).**

Two seconds is extremely generous for a `call_soon_threadsafe`. If it expires, the loop is not *slow* — it is **gone or broken**, and in that state every background job is already being silently swallowed. Returning `None` and dropping the schedule hides the one condition under which the user most needs to know.

This is the same disposition rule `Q-CC-8` states for this signature and `Q-PC-7` applies to `bind_loop`: *failing loudly at the boundary is preferable to silent, data-dependent breakage*. A dropped schedule means a recompute or retrim never runs, and today nothing anywhere records it.

**Not adopted:** a `DesignWarning` and continue (option b). A warning is right for a degraded *result*; here there is no result at all — the work was never queued.

## R2-14 — Is dark mode a supported contract or an accident?

**Context:** `frontend-workbench` — styling reacts to `prefers-color-scheme`, but the
project describes a **dark theme with orange accent** as *the* design. Whether a light
system preference is supported, tested or intended is unclear.
**Spec affected:** [`frontend-workbench/workbench-shell-and-routing/requirements.md`]
**Question:** Is the workbench dark-only (and the `prefers-color-scheme` hook should go),
or is light mode a supported variant that needs testing?
**Impact:** It decides whether the design-system extraction (`Q-FW-4`) needs one token set
or two — cheaper to settle before that work than after.

**Answer:** **✅ Answered by the maintainer, 2026-08-15** (option a) — **the workbench is dark-only. The `prefers-color-scheme` hook is removed and the design system carries one token set.**

The project's stated design is a dark theme with an orange accent (`#FF8400`); reacting to a light system preference was never a supported variant, only an unremoved default. Keeping it would mean every component has two appearances of which one is untested — and layout tests already need a real browser (they cannot be verified in jsdom), so doubling the surface doubles the expensive kind of test.

**This is decided *before* `Q-FW-4`'s design-system extraction on purpose:** the token set is what that work produces, and adding a second one afterwards means revisiting every extracted component. One set now, cheaply.

**Scope of the removal:** the `prefers-color-scheme` media queries go, and the dark values become the values — not a `[data-theme]` fallback, which would leave the second set alive in spirit while pretending otherwise.
